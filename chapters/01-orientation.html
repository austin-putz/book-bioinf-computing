1  Orientation: computers and where you compute

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Open a terminal on your computer and run a command you were given.
  2. Download a FASTQ file, check that it arrived intact, look at its first records, and count its reads.
  3. Find how many logical CPUs, how much RAM, and how much free disk your computer has.
  4. Estimate a file’s size from its read count, and name the resources (CPU, RAM, disk, I/O) a job can be limited by.
  5. Decide whether a job belongs on a laptop, a cluster, or the cloud.

1.1 What this chapter does

By the end of this chapter you will have run your first commands on a real sequencing file: you will download it, check it, look inside it, and count its reads. Then we step back and look at the machine that did the work, and at the other machines you will use.

In bioinformatics, “the computer” is usually not the one in front of you. It is most often someone else’s Linux machine, such as a university or USDA cluster, that you reach from your laptop. Your laptop is still where you edit, look at results, and run small analyses. This chapter starts on the laptop, because that is where everything begins.

1.2 Opening a terminal

Three words first. The operating system is the software that runs the computer: macOS, Windows, or Linux. The terminal is a window where you type commands. The shell is the program inside that window that reads each command, runs it, and prints the result.

Opening a terminal is the one step that really differs between systems. Pick yours; every other tabbed box on this page will follow your choice.

  • macOS
  • Windows (WSL2)
  • Linux

Open Terminal: press Cmd-SpaceCmd-Space, type Terminal, and press ReturnReturn. (It lives in Applications → Utilities.)

ImportantKey idea: switch your Mac from zsh to bash first

A new Mac’s Terminal runs zsh. Every command, output, and explanation in this book assumes bash, as on Linux and on clusters. Do all five setup steps below before the guided first session, then check that echo "$BASH_VERSION" prints 5 or higher. If you skip this, some commands and outputs will not match the book.

This book uses bash, the shell on Linux and on clusters, everywhere. A Mac needs a one-time setup to match: a new Mac’s Terminal runs a different shell (zsh), its built-in bash is version 3.2 from 2007, and its everyday tools (ls, sed, grep, …) are BSD versions whose options differ from the GNU versions on Linux (Chapter 7 explains the differences). You will install Homebrew, a package manager for macOS, use it to install a current bash and the GNU tools, and make bash your shell. Allow 15–30 minutes.

  1. Install Homebrew. Paste the install command from brew.sh:

    Terminal (laptop)
    /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

    It asks for your Mac password (nothing appears as you type; that is normal) and may install Apple’s Command Line Tools first. When it finishes, it prints a Next steps section. If that section lists commands, run them: on Apple silicon Macs they let the shell find brew. Check with brew --version, which prints Homebrew’s version.

  2. Install bash and the GNU tools.

    Terminal (laptop)
    brew install bash coreutils findutils gnu-sed gnu-tar grep gawk gzip

    This installs a current bash; GNU coreutils (ls, wc, nproc, and about a hundred more); and GNU find, sed, tar, grep, awk, and gzip.

  3. Make Homebrew’s bash your shell. The first line adds it to the list of allowed shells; the second switches to it. Each asks for your Mac password.

    Terminal (laptop)
    echo "$(brew --prefix)/bin/bash" | sudo tee -a /etc/shells
chsh -s "$(brew --prefix)/bin/bash"

  4. Put the GNU tools first. Homebrew installs most GNU tools under names starting with g (gsed, gls), so they do not replace the Mac’s own. This command writes a small settings file, ~/.bash_profile, that bash reads each time Terminal opens. It makes brew available and puts each tool’s plain-named GNU version (sed, ls) ahead of the Mac’s, and does the same for their manual pages, so man sed describes the sed you actually run (Chapter 4). Copy all of it, from cat to the final EOF:

    Terminal (laptop)
    cat >> ~/.bash_profile <<'EOF'
# Homebrew, then GNU tools ahead of the macOS versions (Chapter 1)
if [ -x /opt/homebrew/bin/brew ]; then
  eval "$(/opt/homebrew/bin/brew shellenv)"
elif [ -x /usr/local/bin/brew ]; then
  eval "$(/usr/local/bin/brew shellenv)"
fi
for tool in coreutils findutils gnu-sed gnu-tar grep gawk; do
  PATH="$HOMEBREW_PREFIX/opt/$tool/libexec/gnubin:$PATH"
  MANPATH="$HOMEBREW_PREFIX/opt/$tool/libexec/gnuman:$MANPATH"
done
export PATH MANPATH
# Read ~/.bashrc too, as Linux terminals do
if [ -f ~/.bashrc ]; then . ~/.bashrc; fi
EOF

  5. Quit Terminal (Cmd-QCmd-Q), open it again, and check:

    Terminal (laptop)
    echo "$BASH_VERSION"
sed --version | head -n 1
    5.3.15(1)-release
sed (GNU sed) 4.10

    Your version numbers may be newer. If the first line starts with 3.2, step 3 did not take effect; if the second says sed: illegal option, check step 4.

From now on your Mac behaves like the Linux machines in this book.

Optional: iTerm2. Many Mac users swap Terminal for iTerm2, a free terminal app. Both run the same bash with the same settings, so every command in this book works the same in either. iTerm2 adds conveniences that help once you work on a cluster all day: one window split into several panes (say, your laptop beside a login node), search through everything a pane has printed, and a history of what you pasted. To try it, install it with brew install --cask iterm2. This book never assumes you have it.

Windows does not run the book’s commands directly. Instead you install WSL2 (Windows Subsystem for Linux), which runs a real Ubuntu Linux system inside Windows. This takes longer than on the other systems: an install, a restart, and creating a Linux account. Allow 20–30 minutes.

  1. Open PowerShell as administrator: open the Start menu, type PowerShell, right-click Windows PowerShell, and choose Run as administrator.

  2. Run this one command, which installs WSL2 with Ubuntu:

    PowerShell (laptop, as administrator)
    wsl --install

  3. Restart Windows when it asks.

  4. Open Ubuntu from the Start menu. The first time, it asks you to make a Linux user name and password. Nothing appears while you type the password: no dots, no stars. That is normal. Type it, press EnterEnter, and type it again.

From now on, every command in this book runs in the Ubuntu window, not in PowerShell. Its shell is bash.

If the install is blocked, your laptop may be managed by your university; ask your IT office. Microsoft’s WSL install guide has the current official steps (Microsoft 2025). You may also have heard of Git Bash; it is a different tool, and this book does not support it.

You already have a terminal. On Ubuntu, press Ctrl-Alt-TCtrl-Alt-T; on other distributions, look for Terminal in the applications menu. The shell is usually bash.

WarningPitfall: Windows folders from WSL

In WSL, keep your work in your Linux home folder (~), not under /mnt/c/..., where Linux sees your Windows files. Windows folders are slow to use from Linux and invite line-ending and permission problems (Microsoft’s advice).

1.3 Guided first session

Now run some commands. Copy each one, paste it into your terminal, press EnterEnter, and compare what you see with the output shown below it. You do not need to understand every part yet: you will learn these commands properly in Part II. Seeing them work first makes that easier.

TipPasting into a terminal

Paste with Cmd-VCmd-V on macOS and Ctrl-Shift-VCtrl-Shift-V in most Linux and WSL terminals. In a terminal, Ctrl-CCtrl-C does not copy: it stops the running command.

The file we use is a FASTQ file, the standard format for sequencing reads: each read’s bases, plus a quality score for every base. It holds yeast (Saccharomyces cerevisiae) RNA-seq reads from an experiment by Wu et al. (2018), cut down to 50,000 reads for testing by nf-core, a community collection of bioinformatics pipelines. It is the running dataset of this book; its source and license are listed in the book’s data/README.md.

WarningPitfall: on a cluster, never on the login node

This session is meant for your laptop. If you do it on a cluster instead (say, you already have an account), do not run it on the login node, the machine you land on when you log in. Ask the scheduler for a compute node first, and run everything there, downloads included:

Terminal (login node)
srun --cpus-per-task=1 --mem=4G --time=01:00:00 --pty bash -l

This asks for 1 core, 4 GB of RAM, and 1 hour, and opens a shell on a compute node once they are free; it may take a moment. Run hostname: it should now print a different machine’s name than before. Do steps 1–6 there, then type exit to give the compute node back and return to the login node.

Many sites need more options, such as an account (-A) or a partition (-p); SCINet, for example, requires -A. Your site’s documentation lists them, and Section A.6 gives them for Nova and SCINet (Ceres and Atlas need -A <project>; Nova needs nothing extra). Elsewhere, ask your PI or your site’s support which to use. If curl cannot connect from a compute node, your site may block the internet there (Ceres, Atlas, and Nova do not); ask your research computing office where to download. Chapter 10 explains all of this properly.

Step 3. Check that the file arrived intact. First its size:

Terminal (laptop)

Your name, group, and date will differ. 2.2M means about 2.2 megabytes; the next section says exactly what M counts. Then test the compression:

Terminal (laptop)

This prints nothing if the file is intact. A damaged or incomplete download prints an error instead.

Step 5. Count the lines.

Step 6. Count the reads and save the result. Each read in this file takes four lines, as you saw in step 4, so 200,000 lines are 200,000 / 4 = 50,000 reads. This command does the same count, divides by 4, and writes one line to a file:

Terminal (laptop)
1echo "SRR6357070_1 reads: $(( $(gunzip -c SRR6357070_1.fastq.gz | wc -l) / 4 ))" > fastq_summary.txt
2cat fastq_summary.txt
1
$( ... ) runs the line count from step 5 and puts its result here; $(( ... / 4 )) divides it by 4; echo prints the sentence; and > sends that sentence into the file fastq_summary.txt instead of the screen.
2
cat prints the file, so you can check what was saved. 
SRR6357070_1 reads: 50000
WarningPitfall: stop at the first error

If any step prints an error, stop and fix it before going on. In particular, a summary that says reads: 0 means the download failed or the file is broken; the command still “succeeds”, because the shell does not stop on errors unless told to (Chapter 8).

nproc
free -h
df -h ~

These three numbers describe the parts in Figure 1.2:

  • CPU (central processing unit): the part that computes. It has several physical cores, each able to work on its own. On many Intel and AMD processors, each core appears to the system as two logical CPUs; the commands above count logical CPUs. (The example laptop has 8 physical cores and 16 logical CPUs.) A running program splits its work into threads, pieces of work that the system places onto CPUs. Many tools take an option that sets how many threads to use: --threads, -t, or -p, depending on the tool. More threads help only if the tool is written to use them.
  • RAM (memory): the fast working space a program uses while it runs. When a program stops, the system takes its share back for other programs; anything you want to keep must be saved to disk.
  • Disk (storage): slow, large, and permanent; it keeps your files. A file’s size on disk is not the RAM a program needs to read it. The count in step 6 streams through the file a few lines at a time and needs almost no memory, whatever the file’s size. Other tools, such as those that build a genome index (Chapter 31), hold a lot in memory at once.
  • I/O (input/output): reading and writing files, over the disk or the network. Simple steps over big files, such as copying them or counting their lines, often spend most of their time waiting for I/O. Heavier steps, such as aligning reads, are often limited by the CPU, and some by RAM.
  • GPU (graphics processing unit): a separate processor with thousands of small cores, built to do the same arithmetic on lots of data at once. Most tools in this book do not use one. Where you will meet GPUs: nanopore basecalling (Dorado), deep-learning models, and GPU versions of standard tools such as BWA-MEM, STAR, and DeepVariant (NVIDIA Parabricks). Clusters usually have a few GPU nodes, which you must ask the scheduler for. Chapter 37 covers them.

Figure 1.3 shows what threads do, and do not do, on a computer with 8 cores.

Whether code can use more than one core also depends on the language it is written in and the packages it uses (Table 1.3). Some packages use several processes (separate copies of a running program) instead of threads. The cores fill up the same way, but each process needs its own memory.

CautionMisconception: “More cores always makes it faster”

Reality. Only steps written to use several threads get faster, and only until something else limits them. Many steps use one core, and some are limited by disk, network, or memory rather than the CPU.

Each resource fails in its own way when it runs out (Table 1.4). You will meet these messages; recognising them saves hours.

ImportantKey idea

A job can be limited by CPU, RAM, disk space, or I/O. Extra cores help only when the work can use them.

Finding which one limits a real job is part of Chapter 10 (on a cluster) and Chapter 35.

Check yourself. A step keeps one core at 100% while seven sit idle. Will rerunning it with --threads 8 make it faster?

TipAnswer

Only if the tool supports threads. Many steps use one core whatever you ask for, and then nothing changes. Some are limited by disk or memory, not the CPU, and more threads will not help those either.

1.5 How big is the data?

Start with your own file. Our sample was sequenced paired-end: each fragment of RNA (copied to DNA) was read from both ends, so the sample has two mate files, one for read 1 (_1) and one for read 2 (_2). Your file is the read-1 file. It holds 50,000 reads and takes 2.2 MB compressed (12.8 MB uncompressed). A typical RNA-seq sample has around 30 million reads in each mate file, 600 times as many. If those reads are like ours, the file is about 600 times larger:

  • compressed: 2.2 MB × 600 ≈ 1.3 GB
  • uncompressed: 12.8 MB × 600 ≈ 7.7 GB

A paired-end sample has two such files. Ours does too: your file holds 50,000 reads, and its mate file SRR6357070_2.fastq.gz holds another 50,000, so the sample is 50,000 read pairs (100,000 reads).

This kind of scaling works only for the same kind of file. Read length, header style, and compression all change the result, so treat it as an estimate.

A note on units: in this book, 1 MB is 1,000,000 bytes and 1 GB is 1,000,000,000 bytes. Some tools count in powers of 2 instead (1 MiB = 1,048,576 bytes) and often still print M. ls -lh is one of them: your 2,239,317-byte file is 2.14 MiB, which GNU ls rounds up to 2.2M. (The ls built into macOS rounds to 2.1M.) Memory is sold in binary units too: a laptop sold with “64 GB” has 64 GiB.

An analysis pipeline is a fixed series of steps run in order; for RNA-seq, roughly: align the reads (find where each one came from in the genome), count the reads on each gene, and test which genes differ between groups. Part VI shows how to run whole pipelines. The files along the way fall into two groups (Table 1.5, Figure 1.4):

  • Read-level files (FASTQ, BAM) hold every read: gigabytes per sample in a real study. A BAM file holds the same reads after aligning, each with its place on the genome, and is often about as large as the compressed FASTQ files it came from, sometimes larger. Sorting it into genome order needs temporary disk space on top (samtools sort).
  • Summary files (count matrix, results table, and in DNA studies often a VCF of variants) hold one row per gene or variant: megabytes or less for RNA-seq, small enough for any laptop.
ImportantKey idea

Read-level files (FASTQ, BAM) are large; summary files (count matrices, results tables) are usually far smaller. Intermediate and temporary files raise the peak disk space a pipeline needs.

Check yourself. Our mate file holds 50,000 reads in 2.2 MB. About how large is a mate file of the same kind with 30 million reads?

TipAnswer

About 1.3 GB compressed: 30 million is 600 × 50,000, and 600 × 2.2 MB ≈ 1.3 GB. A paired sample has two such files.

1.6 Why Linux

Almost every cluster runs Linux, and most bioinformatics tools are written for it first. That is why this book teaches Linux commands. macOS is close enough that nearly all of them work unchanged, and WSL gives Windows a real Linux system. Where macOS or Windows differ, the book says so.

NoteBackground: Linux distributions

Linux comes in distributions that share the same core and commands but differ in how software is installed. You will most often meet Ubuntu on laptops and WSL, and Red Hat Enterprise Linux or Rocky Linux on clusters.

1.7 Where you compute: laptop, cluster, cloud

You will use up to three kinds of computer (Table 1.6).

A cluster, or HPC (high-performance computing) system, is many computers, called nodes, shared by many people (Figure 1.5). You connect from your laptop to a login node with ssh (secure shell, the standard way to log in to another computer). There you edit files and submit jobs: requests for some cores, memory, and time. A program called the scheduler (on most clusters, including SCINet and Nova, SLURM) holds each job in a queue until those resources are free, then runs it on a compute node. Your files sit on shared storage, which both the login node and the compute nodes can read. Chapter 9 covers connecting and Chapter 10 the scheduler.

CautionMisconception: “The cluster is just a faster computer”

Reality. A cluster is many ordinary computers shared by many people. You ask a scheduler for cores, memory, and time, and your job waits in a queue until they are free. A single step is often no faster than on a laptop; the gain is running many steps at once, with more memory.

WarningPitfall: heavy work on the login node

The login node is a shared doorway. Running an analysis there slows it for everyone, and many sites kill long-running processes on it. Run work on a compute node instead: interactively with srun (the box in Section 1.3), or as a submitted job (Chapter 10).

The cloud is computers you rent by the hour from a company. It costs money for every hour and every gigabyte, so for most readers it is the option for when a cluster cannot do the job. Chapter 38 introduces it.

Check yourself. Laptop, cluster, or cloud?

  1. Editing an analysis script.
  2. Aligning the reads of 48 samples.
  3. Running DESeq2 (an R package that finds genes whose expression differs between groups) on this book’s small yeast count matrix.
  4. A one-off job that needs 2 TB of RAM, more than any node of your cluster has.
TipAnswer
  1. Laptop (or the login node, if the script lives on the cluster).
  2. Cluster compute nodes, submitted as jobs.
  3. Laptop: the matrix is a few kilobytes.
  4. The cloud is one option if you have funding for it; another is a shared facility that has such nodes.

1.8 Getting a cluster account

Most readers will need a cluster account for the later chapters. Apply early, since approval can take days or weeks. Ask your PI or your institution’s research computing office which cluster you can use.

TipApply for an account now

ARS scientists and their collaborators can sign up for SCINet, USDA’s clusters. Universities run their own, such as Iowa State’s HPC clusters (Nova). Appendix A will add step-by-step details for both.

No cluster yet? Keep going: everything before Chapter 9 runs on your laptop.

1.9 Summary

  • A terminal runs a shell; this book uses bash on every system (on a Mac, after installing it with Homebrew). You type commands, and code blocks in this book leave out the prompt and say where they run.
  • You downloaded a FASTQ file, checked it, looked at its records, and saved a read count: SRR6357070_1 reads: 50000.
  • Your computer’s logical CPUs, RAM, and free disk are three commands away; a job can be limited by CPU, RAM, disk, or I/O, and more threads help only tools written to use them.
  • Read-level files (FASTQ, BAM) are large; summary files (count matrices, results) are small. File size scales with read count for files of the same kind.
  • Edit and run small analyses on a laptop; run heavy jobs on cluster compute nodes, never on the login node; rent the cloud when neither will do.

SRR6357070_1 reads: 50000
SRR6357070_2 reads: 50000

Yes. In a paired-end run each fragment is read from both ends, so read 1 and read 2 of a pair sit at the same position in the two files, and the counts must match. Equal counts do not by themselves prove that the pairs line up; Chapter 15 shows how to check.

Exercise 2. Would it fit? Fill in your column of Table 1.2. Would an uncompressed 30-million-read mate file (about 7.7 GB) fit in your RAM if a program loaded all of it at once, leaving room for the system and your other programs?

TipAnswer

It depends on your laptop: with 8 GB of RAM, no; with 32 GB, yes. But the count from step 6 never loads the file: it streams through it, so it works on any laptop. Some tools do need that much memory or more, which is one reason to use a cluster.

Exercise 3. How long would it take? Time the line count:

Terminal (laptop)
time gunzip -c SRR6357070_1.fastq.gz | wc -l

Find the elapsed time: the real line of the output. Estimate the time for a 30-million-read mate file (600 times larger), then name two reasons the real time could differ from your estimate.

TipAnswer

On the example laptop the count took 0.03 seconds, so 600 times that is about 20 seconds. Two reasons it could differ: for a file this small, the time is mostly spent starting the programs, and the file may already be in memory from step 5, so the small run is not a fair sample. And a big file may sit on a slower disk or a network filesystem, which makes reading it the limit. Measuring what limits a job is part of Chapter 10 and Chapter 35.
