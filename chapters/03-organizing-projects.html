3  Organizing projects and data

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Lay out a project folder that keeps raw data, reference, metadata, code, results, and logs apart, and name files so they sort well and avoid common path problems.
  2. Verify downloaded files with checksums, and protect raw data from accidental changes and deletion.
  3. Link shared data into a project with a symbolic link, and say what removing the link does and does not remove.
  4. Record where every input and output came from (source, version, checksum, script, software version, log) in files kept in the project.
  5. Say which of your storage locations are backed up, for how long, and who would restore them.

3.1 What this chapter does

A month from now, someone (your PI, a reviewer, or you) will point at a number and ask: which file is this, where did it come from, and how was it made? If the answer lives only in your memory, it is already fading. This chapter sets up a folder, and a few habits, that answer those questions without memory.

You will turn ~/bioinf-computing, the folder from Chapter 2, into the book’s project. By the end it holds:

  • the two FASTQ files from Chapter 1, moved in, checked, and protected from accidental changes;
  • a reference genome kept in a shared folder and linked in, not copied;
  • small tables that say which files belong to which sample;
  • a numbered script that counts the reads and writes a log of every run;
  • a README, a data record, and a notebook that say where everything came from.

Every later chapter starts from this folder. The commands are copy-and-run, as in Chapter 1; mkdir, mv, ln, chmod and the rest are explained properly in Part II (Chapter 5, Chapter 7). Practice files, and anything broken on purpose, go in a separate scratch folder, ~/bioinf-ch03, never in the project.

3.2 A folder for each project

Do this on your laptop (in WSL2’s Ubuntu terminal on Windows). Go to the book folder and make the empty folders of the layout:

Terminal (laptop)
cd ~/bioinf-computing
1mkdir -p data/raw data/meta src results logs
ls
1
mkdir makes folders; -p makes data/ on the way to data/raw, and says nothing if a folder already exists. 
data  logs  notes.txt  pixi.lock  pixi.toml  README.md  results  src

pixi.toml and pixi.lock are the book environment from Chapter 2; README.md and notes.txt are your editor practice from its exercises (delete notes.txt with rm notes.txt if you like). The hidden .pixi/ folder is there too; ls -a shows it.

7 directories, 15 files

tree sorts by name and, like ls, hides names that start with a dot, so .pixi/ is missing; tree -a shows it (and its thousands of files). tree -L 2 stops two levels down, which helps in big projects. Later chapters use tree to show a tool’s inputs and outputs; run it yourself to check your folder against the book.

The rules behind it, one sentence each:

  • One project, one folder. Everything an analysis needs, or points to, is inside it.
  • Inputs, code, and outputs apart. Raw data and metadata in data/, scripts in src/, results in results/, logs in logs/. You never write into data/raw/, and nothing in results/ is edited by hand.
  • Results can be rebuilt. Everything in results/ should come back if you rerun the code in src/ on the inputs in data/, with the same software. Exercise 4 tests it.
  • Paths inside the project are relative to its top folder (data/raw/SRR6357070_1.fastq.gz, not /home/you/bioinf-computing/data/…), so scripts keep working if the folder moves (more on moving in Section 3.5).

Table 3.1 lists the parts.

ImportantKey idea

Keep inputs, code, and outputs apart, so that every output can be rebuilt from preserved inputs, code, settings, and software records. That gives you the ingredients for reproducing an analysis; actually rebuilding it is the test.

This is one sensible layout, not the only one. Noble (2009) and Wilson et al. (2017) describe close relatives; pipelines add a work/ folder of their own (Chapter 25), and later books adapt the layout to their tools. What matters is that a stranger can find the raw data, the code, and the results, and tell them apart.

On a cluster the same layout goes in project storage (/project/<your-project>/ on SCINet, /work/<your-group>/ on Nova), not in your small home folder or in scratch space that is purged (Section 2.2). Large intermediate files may live in scratch while a job runs, with only the final results kept in the project (Chapter 10). Making folders and moving files is light work, fine on a login node; checksumming many large files is not.

Check yourself. You delete results/read_counts.tsv by mistake (you will make it later in this chapter). What do you need to get it back?

TipAnswer

Nothing but the project itself: rerun the script on data/raw/ with the same environment. A large published analysis is different: rebuilding it can take days of computing, or need a reference or a software version that is no longer available, which is why important final results are backed up too.

3.3 Names that work

Start with a puzzle. In the scratch folder, make seven empty files with names like the ones on many lab drives, then list them:

Terminal (laptop)
mkdir -p ~/bioinf-ch03/names && cd ~/bioinf-ch03/names
1touch run1.sh run2.sh run10.sh final.txt "Final FINAL (2).txt" "9-15-25 counts.csv" "10-2-26 counts.csv"
2ls -1
1
touch makes empty files. The quotes keep each name with spaces in one piece.
2
-1 (the digit one) lists one name per line. 
'10-2-26 counts.csv'
'9-15-25 counts.csv'
'Final FINAL (2).txt'
final.txt
run1.sh
run10.sh
run2.sh

(Captured on a Mac. On Linux with English language settings, run10.sh comes before run1.sh; the order depends on the system’s language settings, but the two problems below appear everywhere.) ls sorts names character by character, so run10.sh lands before run2.sh, and October 2026 (10-2-26) before September 2025 (9-15-25). ls puts quotes around names with spaces to warn you, and spaces break commands that are not quoted:

Terminal (laptop)
wc -l 10-2-26 counts.csv
wc: 10-2-26: No such file or directory
wc: counts.csv: No such file or directory
0 total

The shell split the name at the space and looked for two files. Quoting fixes it (wc -l "10-2-26 counts.csv"), and you will still learn to quote paths (Chapter 5), but names without spaces never need it. Table 3.2 gives the rules, each with a better name.

Number scripts in the order they run: 00_ for one-time setup such as downloads, then 01_, 02_, …, so ls src/ shows the analysis in order. Two exceptions to renaming. First, IDs that come from a facility or an archive (SRR6357070, WT_REP1) stay exactly as given, so they still match the records; rename only your own files. Second, a name whose meaning you do not know: is 11-3-25 counts.csv 3 November or 11 March, 2025 or 2011? Renaming cannot recover what you do not know. Ask whoever made it, then rename.

Check yourself. In what order does ls list run1.sh, run2.sh, and run10.sh, and how would you rename them?

TipAnswer

run1.sh, run10.sh, run2.sh (on Linux, possibly run10.sh first; run2.sh always comes after run10.sh). Pad the numbers and say what each step does: 01_download.sh, 02_trim.sh, 10_report.sh.

3.4 Raw data: move it in, check it, protect it

Move it in. The two FASTQ files from Chapter 1 are still in the scratch folder ~/bioinf-ch01. Move them into the project:

Terminal (laptop)
cd ~/bioinf-computing
1mv ~/bioinf-ch01/SRR6357070_1.fastq.gz ~/bioinf-ch01/SRR6357070_2.fastq.gz data/raw/
ls -l data/raw
1
mv moves files; the last name is where they go. Moving within one disk only changes where the file is listed, so it is instant. 
total 4368
-rw-r--r-- 1 you you 2239317 Nov 17 11:22 SRR6357070_1.fastq.gz
-rw-r--r-- 1 you you 2232117 Nov 17 11:22 SRR6357070_2.fastq.gz

From now on the files live here: if you go back to a command in Chapters 1–2, use ~/bioinf-computing/data/raw/ instead of ~/bioinf-ch01/. ~/bioinf-ch01 keeps fastq_summary.txt; you can delete it later.

TipMissing a file?

If mv says cannot stat … No such file or directory for a file (you skipped the read-2 exercise, or deleted ~/bioinf-ch01), the other file still moved. Download each missing one straight into data/raw/:

Terminal (laptop)
cd ~/bioinf-computing
curl -fL -o data/raw/SRR6357070_1.fastq.gz https://raw.githubusercontent.com/nf-core/test-datasets/9dd6d014f560e182047992834a8d267214fbccd1/testdata/GSE110004/SRR6357070_1.fastq.gz
curl -fL -o data/raw/SRR6357070_2.fastq.gz https://raw.githubusercontent.com/nf-core/test-datasets/9dd6d014f560e182047992834a8d267214fbccd1/testdata/GSE110004/SRR6357070_2.fastq.gz

Run only the line for the file you are missing. If a file is already in data/raw/ from an earlier visit to this chapter, leave it: the check below tells you whether it is intact.

Check it. A sequencing facility, or an archive such as ENA, gives you a checksum for every file: a short value computed from every byte of it. Here are the MD5 checksums of the two files, as the book recorded them. Make a file data/raw/checksums.md5 (code data/raw/checksums.md5 opens it in VS Code; nano works too), paste the two lines, and save:

data/raw/checksums.md5
d19f3c7a8b4016fa641458257b99a1a1  SRR6357070_1.fastq.gz
d126cc66ed169f69af2c07da0dd73e02  SRR6357070_2.fastq.gz

Each line is a checksum, two spaces, and a file name. Now check the files against it:

Terminal (laptop)
cd data/raw
1md5sum -c checksums.md5
cd ~/bioinf-computing
1
md5sum computes MD5 checksums; -c (check) reads a list of them, recomputes each file’s, and compares. 
SRR6357070_1.fastq.gz: OK
SRR6357070_2.fastq.gz: OK

The names in checksums.md5 have no folder, so the check runs inside the folder that holds the files. Facilities ship their lists the same way. Run it from the wrong folder and every file “fails”:

md5sum: SRR6357070_1.fastq.gz: No such file or directory
SRR6357070_1.fastq.gz: FAILED open or read
md5sum: SRR6357070_2.fastq.gz: No such file or directory
SRR6357070_2.fastq.gz: FAILED open or read
md5sum: WARNING: 2 listed files could not be read

Now name the idea (Figure 3.2). A checksum is a fingerprint of a file: the same bytes always give the same value, and changing a single byte gives a completely different one. A matching checksum means your copy is byte-for-byte the file the checksum was made from.

Run md5sum -c after every download or transfer, before any analysis (Chapter 9 reuses it after copying to a cluster). Two kinds of failure mean different things:

  • FAILED: the bytes differ, usually an incomplete or damaged copy. Download or copy the file again and recheck. Never “fix” the list by computing a new checksum from the damaged copy.
  • FAILED open or read with No such file or directory: the file is missing, misnamed, or you are in the wrong folder. Check that before assuming damage.

sha256sum works the same way (sha256sum -c) with a longer, stronger value (both are documented in the GNU coreutils manual); the book’s own data/README.md records both. MD5 is still what most facilities and ENA supply, and it is fine for catching damaged copies.

CautionMisconception: “If the checksums match, my data are correct”

Reality. A match proves your copy is identical to the file the checksum was made from. It says nothing about whether that file was the right sample, or good data: if a facility mislabels a file before computing its checksum, md5sum -c happily prints OK.

Protect it, first on a toy. Raw data is never edited, so make it read-only. Try it first on a practice folder with one small file:

Terminal (laptop)
mkdir -p ~/bioinf-ch03/practice/locked && cd ~/bioinf-ch03/practice
echo "first line" > locked/notes.txt
1chmod a-w locked/notes.txt locked
2echo "second line" >> locked/notes.txt
3rm -f locked/notes.txt
mv locked/notes.txt notes_moved.txt
touch locked/new.txt
1
chmod changes a file’s permissions; a-w removes (-) write permission (w) for all users (a). Here it locks both the file and the folder that holds it.
2
Try to add a line, then (next lines) to delete the file, move it out, and add a new file.
3
-f deletes without asking. Without it, rm may stop to ask about a read-only file; a job running unattended cannot answer. 
bash: locked/notes.txt: Permission denied
rm: cannot remove 'locked/notes.txt': Permission denied
mv: cannot move 'locked/notes.txt' to 'notes_moved.txt': Permission denied
touch: cannot touch 'locked/new.txt': Permission denied

All four were refused. Why lock the folder too? Deleting, moving, and adding files change the folder’s list of names, so the folder’s permission controls them, not the file’s. A read-only file in a writable folder can still be deleted:

Terminal (laptop)
mkdir -p open && echo "first line" > open/notes.txt
chmod a-w open/notes.txt
rm -f open/notes.txt
ls open

rm -f printed nothing and ls shows an empty folder: the read-only file is gone. (Without -f, rm asks before deleting a read-only file when its input is a terminal, even from a script you started there. With -f, or in a job running unattended, nothing asks.)

Now protect the real raw data, files and folder:

Terminal (laptop)
cd ~/bioinf-computing
chmod a-w data/raw/* data/raw
1ls -ld data/raw
ls -l data/raw
1
-d lists the folder itself instead of its contents. 
dr-xr-xr-x 2 you you 4096 Nov 17 11:22 data/raw
total 4372
-r--r--r-- 1 you you     112 Nov 17 11:22 checksums.md5
-r--r--r-- 1 you you 2239317 Nov 17 11:22 SRR6357070_1.fastq.gz
-r--r--r-- 1 you you 2232117 Nov 17 11:22 SRR6357070_2.fastq.gz

The w letters are gone. This guards against accidents (a script that writes to the wrong path, a slip of rm), not against you: as the owner you can always give write permission back. To add a file later, unlock the folder and the checksum list (the existing reads can stay locked), add the file and its line from the source’s checksum list, check, and lock everything again:

Terminal (laptop)
chmod u+w data/raw data/raw/checksums.md5
# add the new file and its line in checksums.md5, then:
cd data/raw && md5sum -c checksums.md5 && cd ~/bioinf-computing
chmod a-w data/raw/* data/raw

Chapter 7 explains permissions properly. Keep raw reads compressed, and never unzip them in place: every tool in this book reads .gz directly.

ImportantKey idea

Raw data is read-only: check it once with checksums, protect it, and never edit it. Every change happens in a script that writes somewhere else.

Check yourself. md5sum -c prints FAILED for a file you just copied from the cluster. What happened, and what do you do? What if it says FAILED open or read?

TipAnswer

FAILED: your copy’s bytes differ from the original, usually an incomplete transfer. Copy it again and recheck; do not analyse it. FAILED open or read: the file is missing or misnamed, or you ran the check from the wrong folder.

3.5 Shared data: link, don’t copy

On a cluster, a lab keeps one copy of each reference genome and big shared dataset in a shared folder, something like /project/<lab>/references/, and every project points to it. No one copies a 3 GB genome into each project, and no one’s quota pays twice. You will make a stand-in for such a folder in your home folder and link it into the project.

Make the shared folder. Download the test genome (yeast chromosome I only, 71 kB) and its annotation into it:

Terminal (laptop)
mkdir -p ~/bioinf-shared/references/yeast_R64-1-1_test
cd ~/bioinf-shared/references/yeast_R64-1-1_test
curl -fLO https://raw.githubusercontent.com/nf-core/test-datasets/9dd6d014f560e182047992834a8d267214fbccd1/reference/genome.fa.gz
curl -fLO https://raw.githubusercontent.com/nf-core/test-datasets/9dd6d014f560e182047992834a8d267214fbccd1/reference/genes.gtf.gz

Give it a checksum list, as the person who set up the folder would:

~/bioinf-shared/references/yeast_R64-1-1_test/checksums.md5
4222a07bf01b12782245e0ff774459fe  genome.fa.gz
504334f6741ee771c665ae845429087f  genes.gtf.gz
Terminal (laptop)
md5sum -c checksums.md5
genome.fa.gz: OK
genes.gtf.gz: OK

And a README, so anyone who finds the folder knows what it is:

~/bioinf-shared/references/yeast_R64-1-1_test/README.md
# Yeast test reference (stand-in for a lab's shared references)

- genome.fa.gz: S. cerevisiae R64-1-1, chromosome I only (one sequence, >I)
- genes.gtf.gz: matching gene annotation (test subset)
- Source: nf-core/test-datasets, rnaseq branch, folder reference/,
  commit 9dd6d014f560e182047992834a8d267214fbccd1
- Downloaded: 2026-11-17 (write your date)
- Checksums: checksums.md5 (MD5)
- License: MIT (nf-core/test-datasets)

Then protect the folder, as a lab would protect its shared references:

Terminal (laptop)
chmod a-w ~/bioinf-shared/references/yeast_R64-1-1_test/* ~/bioinf-shared/references/yeast_R64-1-1_test

Link it into the project:

Terminal (laptop)
cd ~/bioinf-computing
1ln -s ~/bioinf-shared/references/yeast_R64-1-1_test data/ref
ls -l data/ref
ls data/ref/
1
ln -s target name makes a symbolic link called name that points to target. 
lrwxrwxrwx 1 you you 53 Nov 17 11:22 data/ref -> /home/you/bioinf-shared/references/yeast_R64-1-1_test
checksums.md5  genes.gtf.gz  genome.fa.gz  README.md

ls -l shows the link itself: an l at the start, and an arrow to the path it holds (on a Mac the path starts with /Users/). ls data/ref/, with the slash, looks through the link and lists the shared folder’s files.

Now name the idea (Figure 3.3). A symbolic link (symlink) is another route to the same data, not a copy: a tiny entry that holds only a path. Programs that open data/ref/genome.fa.gz read the file in the shared folder.

See both halves of that on a toy link in the practice folder (never on the real reference). Writing through a link writes to the original, and removing the link leaves the original alone:

Terminal (laptop)
cd ~/bioinf-ch03/practice
mkdir -p target && echo "original line" > target/note.txt
ln -s target toylink
echo "added through the link" >> toylink/note.txt
cat target/note.txt
1unlink toylink
ls
cat target/note.txt
1
unlink removes one link (or file) and nothing else. 
original line
added through the link
locked  open  target
original line
added through the link

The line written through toylink landed in target/note.txt; after unlink, the link is gone and the target still holds both lines. (Try the same write on data/ref/README.md and you get Permission denied: the protection you added to the shared folder stops it, as step 3 of Figure 3.3 shows.) A link whose target is moved or renamed is broken: ls -l still shows the arrow (in red in many terminals), and opening a file through it says No such file or directory.

WarningPitfall: rm -r data/ref/ deletes the shared data

Remove a link with unlink data/ref or rm data/ref: no slash at the end, no -r. With a trailing slash, which TabTab completion adds for you, rm -r follows the link. On a Mac with GNU coreutils 9.11 (and with macOS’s own rm), this deleted the entire shared folder without a word, and left the link behind, now broken:

$ rm -r proj/ref/
$ echo $?
0
$ ls -l proj
total 0
lrwxr-xr-x 1 you staff 20 Nov 17 11:34 ref -> /home/you/shared/ref
$ ls -A shared/ref
ls: cannot access 'shared/ref': No such file or directory

(Captured in a test folder, with $ before each command: echo $? prints 0, the code for success, and the shared folder shared/ref is gone.) On Linux (Ubuntu 24.04, GNU coreutils 9.4) the result differs but is no better: rm deleted every file inside the shared folder, then stopped with rm: cannot remove 'proj/ref/': Not a directory, leaving the folder empty.

Do not run this. The shared folder you made survives it only because you protected it: rm then stops with Permission denied. A lab’s real shared folder may not be protected from you.

Moving the project. Relative paths in scripts let the project move, but a link is only a pointer: copy the project to another machine (say, laptop to cluster) and data/ref points at a path that does not exist there. Moving a project means three steps: copy the project’s files; reinstall the environment from pixi.toml and pixi.lock (Chapter 2); and recreate data/ref to point at that machine’s copy of the same reference, which data/README.md identifies by source, release, and checksums (Section 3.8). Transfer commands come in Chapter 9. And a link is not a backup of its target: someone (you, the lab, or the site) must look after the shared copy (Section 3.6). Which genome release to use, and why chromosome names differ between sources, is Chapter 20.

Check yourself. You run unlink data/ref. Is the reference genome gone? What must you do to use the project on a second machine?

TipAnswer

No, only the link is gone; the shared folder is untouched. On the second machine, recreate the link to that machine’s copy of the same reference, identified by its source, release, and checksums in data/README.md, and reinstall the environment from the lockfile.

3.6 Backups: where do your files really live?

Start with a question for each place you keep files: if you deleted a file there by mistake today, could you get it back? Table 3.3 answers it for a laptop and the two clusters this book uses as examples. Copy its rows for your own storage into your notebook (you will start it in Section 3.9) and fill them in from your site’s documentation.

WarningPitfall: scratch is purged and not backed up

Files in scratch space (/90daydata, /ptmp) are deleted automatically; on SCINet the deletion “is permanent and the files cannot be recovered”. Use scratch for files a job can make again, copy results you need into project storage, and find out which other areas are backed up, and for how long, before you trust them.

Then name the rule: 3-2-1. Keep three copies of anything you cannot recreate, on two kinds of storage, with one somewhere else (off site). For raw sequence data, the facility’s copy or the public archive (SRA or ENA, once you have submitted) can be one of the three, but only if you know it is kept and for how long. An archive of the original reads does not preserve a subset or a fix you made yourself.

A few points the table makes:

  • Cluster storage is often not a backup at all. SCINet says so for all of its cluster storage, and scratch is purged everywhere. Even storage with snapshots (Nova’s /work) should not be your only copy: Nova’s login banner says so.
  • A sync folder copies your mistakes too. Delete or overwrite a file and the change syncs everywhere. It is one copy in two places, unless version history is kept and you know for how long.
  • Git keeps the history of code (Chapter 21), but only a copy stored somewhere else, such as a remote repository (Chapter 22), protects it if your machine is lost.

What to back up: raw data, metadata, code, the notebook, logs, and the records that explain results; important final results too. A result you can rebuild in seconds, such as this chapter’s read counts, needs no backup of its own. A large or published analysis may need days of computing, a reference that is no longer online, or an old software version to rebuild, so keep it. Intermediate files that a pipeline can make again can follow a lighter rule. And test a restore once: a backup you have never restored from is a hope, not a backup.

CautionMisconception: “My Dropbox (or OneDrive) folder is my backup”

Reality. Sync copies deletions and overwrites to every device. It protects you only through version history, for as long as the service keeps it, which you need to check.

Check yourself. Your raw FASTQ files are in cluster scratch and in a OneDrive folder on your laptop. Is that a backup you can rely on? What would you check?

TipAnswer

Not as it stands: scratch is purged and not backed up, and OneDrive copies deletions. Check how long OneDrive keeps old versions, whether the facility or SRA keeps the original reads (and for how long), and put a copy in storage that is backed up.

3.7 Sample sheets and metadata

Now check the labels against the source. The runs are public, so the archive has a record for each. The lesson is general. A sample label is a claim: check it against the source record, and never infer the biology from names alone. (How to design an experiment with replicates is the Transcriptomics book’s subject.)

(The columns are separated by tabs, which the terminal shows as jumps to the next multiple of 8 characters, so they do not line up. Open the files in VS Code to see them as columns.) A real project has one row per run in reads.tsv and one per sample in samples.tsv; the sample column is how the two tables join (Chapter 14).

Now name the idea. Metadata is data, not a note on the side: kept beside the reads, checked, and changed only on purpose. The rules:

  • One row per run (or per sample), one column per property.
  • Plain CSV or TSV files, not spreadsheets with merged cells, colour coding, or notes in the margins (spreadsheet pitfalls: Chapter 14).
  • Sample IDs are spelled the same in every table: WT_REP1 in one and WT_rep1 or WT_REP1 (with a trailing space) in another are different IDs.
  • File-path columns point at the right files. Sample IDs and file names need not match (WT_REP1 and SRR6357070_1.fastq.gz): the table is what connects them.
  • Values come from the source record, with the record’s ID (GSM2879618) kept so anyone can check them.

nf-core’s own sample-sheet format, and how it merges runs, are covered in Chapter 26.

3.8 Provenance: where did this number come from?

In Chapter 1 you typed a read count into fastq_summary.txt by hand. Nothing in that file says which file was counted, with what, or when. Now make a result that records how it was made.

Add the script. Open a new file in VS Code (code src/01_count_reads.sh), paste the script below, and save. You run it in this chapter; Chapter 8 explains every line.

src/01_count_reads.sh
#!/usr/bin/env bash
# 01_count_reads.sh: check the raw FASTQ files, then count their reads.
# Run from the project folder:  pixi run bash src/01_count_reads.sh
set -euo pipefail

mkdir -p results logs
log="$(mktemp "logs/01_count_reads_$(date +%Y-%m-%dT%H%M%S)_XXXX.log")"

{
  echo "started:  $(date "+%Y-%m-%d %H:%M:%S %z")"
  echo "host:     $(hostname)"
  echo "script:   $(md5sum src/01_count_reads.sh)"
  echo "seqkit:   $(seqkit version)"
  echo "checking inputs against data/raw/checksums.md5:"
  (cd data/raw && md5sum -c checksums.md5)
  echo "command:  seqkit stats -T data/raw/*.fastq.gz"
  seqkit stats --quiet -T data/raw/*.fastq.gz > results/read_counts.tsv.tmp
  mv results/read_counts.tsv.tmp results/read_counts.tsv
  echo "output:   $(md5sum results/read_counts.tsv)"
  echo "finished: $(date "+%Y-%m-%d %H:%M:%S %z")"
} 2>&1 | tee "$log"

(Tab-separated again: -T asks seqkit for a plain table that other programs can read, without the commas and aligned columns of Chapter 2. num_seqs is 50,000 in each file.) What the script did, in plain words:

  1. Checked the inputs against checksums.md5, and would have stopped there if any failed.
  2. Recorded the date, the machine, the script’s own checksum, the seqkit version, and the command.
  3. Counted the reads into a temporary file, and only then moved it into results/. A run that fails half-way cannot replace a good result with an empty one.
  4. Recorded the output’s checksum.
  5. Saved everything it printed, including any messages from seqkit, in a new log in logs/, named by date and time plus four random characters (_7WFs; mktemp picks a name no other file has), so every run keeps its own log, even two runs in the same second.

The log is the run’s record. A log with no finished: line means the run failed, and its last lines say where (Chapter 4 starts from exactly that). When one input was corrupted on purpose, the run stopped at FAILED, kept the old result, and left the failure in its log.

The notebook. A script shows what was done; it does not show why, what you tried first, or what went wrong. That goes in a notebook. Make NOTEBOOK.md in the project and give it a first dated entry:

A plain Markdown file in the project is the book’s default; if your lab already uses an electronic lab notebook, use that. The habit matters, not the tool.

TipMarkdown in one box

README.md and NOTEBOOK.md are Markdown: plain text with a few marks. # starts a heading (## a smaller one), - starts a list item, and backticks mark code (`md5sum -c`). VS Code shows a preview with Cmd-Shift-VCmd-Shift-V (Ctrl-Shift-VCtrl-Shift-V on Windows and Linux). Quarto (Chapter 12) uses the same marks; see its Markdown basics.

FAIR, briefly. Funders and journals increasingly ask for data that is FAIR: Findable, Accessible, Interoperable, and Reusable (Wilkinson et al. 2016). Table 3.5 shows which habits from this chapter support each principle.

NoteBackground: the FAIR principles

A README and a tidy CSV do not by themselves make a project FAIR; that takes depositing data, with good metadata, in an archive that gives it identifiers (Chapter 20, Chapter 22). They make it much easier. And Accessible does not have to mean open to everyone: data behind a login are fine, as long as how to get access is clear. More on FAIR at GO FAIR.

Check yourself. Which FAIR principle does citing SRR6357070 and GSE110004 in your README support?

TipAnswer

Findable, through persistent identifiers (and Reusable, since others can trace and credit the data).

3.10 Summary

  • One project, one folder, with inputs (data/), code (src/), and outputs (results/, logs/) apart, so results can be rebuilt. Names without spaces, ISO dates, zero-padded numbers, scripts numbered in run order.
  • Raw data is checked with md5sum -c (in the folder that holds the files) after every download or transfer, then protected with chmod a-w on the files and the folder. FAILED means damaged; FAILED open or read means missing or the wrong folder.
  • Shared data is linked, not copied: ln -s target data/ref. Remove a link with unlink data/ref, never rm -r data/ref/. A link does not travel with the project; data/README.md says what to link on another machine.
  • Each result has a record of its provenance: the inputs’ sources and checksums (data/README.md, checksums.md5), the script, the software (pixi.lock), and a log of every run. README.md and NOTEBOOK.md say what the project is and why you did what you did.
  • Know which of your storage is backed up, for how long, and who restores it. Scratch is purged; a sync folder copies mistakes; 3-2-1 for anything you cannot recreate.

SRR6357070_1.fastq.gz: FAILED
