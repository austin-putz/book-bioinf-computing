4  Getting help

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Look up how to use a tool with --help, man, and its official documentation, and read a usage line.
  2. Read an error or warning: find which command printed it, what failed, and on what.
  3. Work through a short checklist (message, log, location, environment, inputs, resources, recent changes) before asking for help.
  4. Find the tools, versions, parameters, and reference reported in a paper’s methods section, and say what the passage does not report.
  5. Write a help request with the exact command, the complete message, versions, and a minimal example that still fails, with no passwords or private data, and check AI-suggested code before you run it.

4.1 What this chapter does

Things break, for everyone, every day: a typo in a file name, a flag that does not exist, a script run from the wrong folder, a download cut short. Experienced people do not avoid errors; they get from a message to a fix quickly, and they know when and how to ask. Most fixes take the steps in this chapter, not expertise.

You will use the book’s own files and environment throughout, so every error in the chapter is one you can reproduce yourself, or read in the captured output. You will finish able to:

  • ask a tool how to use it (--help, man, its website);
  • read an error message, and tell an error from a warning;
  • work through a short checklist that solves most problems on its own;
  • read a paper’s methods section for tools, versions, and parameters;
  • search well, and write a help request someone can answer;
  • check a command an AI assistant suggests before you trust it.

Asking for help is part of the job, not a sign that you are not good enough: some problems (a broken node, a full quota) only an administrator can fix, and a clear request is a skill in its own right.

Commands run on your laptop, from the book’s project folder, ~/bioinf-book (Chapter 3). Practice files go in a scratch folder, ~/bioinf-ch04, like Chapter 1’s ~/bioinf-ch01, so the project stays clean. Make it now:

Terminal (laptop)
cd ~/bioinf-book
mkdir -p ~/bioinf-ch04

Cluster readers can run the same commands on a login node: they are small and quick.

Documents  : http://bioinf.shenwei.me/seqkit

Please cite: https://doi.org/10.1002/imt2.191
...
Usage:
  seqkit [command]

Commands for Basic Operation:
  faidx           create the FASTA index file and extract subsequences
  ...

(... marks lines left out here; the real output is longer.) The top already answers three questions you will have often: which version you have (2.14.0), where the documentation is, and what to cite. SeqKit’s authors ask you to cite the SeqKit2 paper (Shen et al. 2024). Below that comes the list of subcommands: seqkit is one program with many tools inside, and stats, which you ran in Chapter 2, is one of them. Each subcommand has its own help:

Shen, Wei, Botond Sipos, and Liuyang Zhao. 2024. “SeqKit2: A Swiss Army Knife for Sequence and Alignment Processing.” iMeta 3 (3). https://doi.org/10.1002/imt2.191. 
Terminal (laptop)

Scroll to the Flags: part. Find the flag that prints a table for other programs to read, and the one that sets how many CPUs seqkit uses:

  -T, --tabular              output in machine-friendly tabular format
  ...
  -j, --threads int                     number of CPUs. can also set with environment variable
                                        SEQKIT_THREADS) (default 4)

Now a tool that came with the system. On Linux and WSL, gzip is GNU gzip; on a Mac it is the GNU gzip you installed in Chapter 1:

Terminal (laptop)
gzip --help
Usage: gzip [OPTION]... [FILE]...
Compress or uncompress FILEs (by default, compress FILES in-place).

Mandatory arguments to long options are mandatory for short options too.

  -c, --stdout      write on standard output, keep original files unchanged
  -d, --decompress  decompress
  ...
  -t, --test        test compressed file integrity
  ...
With no FILE, or when FILE is -, read standard input.

Most command-line programs also have a manual page, a longer description that opens in a pager:

Terminal (laptop)
man gzip

Move with SpaceSpace and the arrow keys, search with / followed by a word and EnterEnter, and quit with q (these are the keys of less, Chapter 5). Now try seqkit:

Terminal (laptop)
pixi run man seqkit
No manual entry for seqkit

Many bioinformatics tools have no manual page, only --help and a website. That is normal.

4.2.1 Reading a usage line

Help text uses a compact notation, shown in Figure 4.1.

The conventions, from Usage: gzip [OPTION]... [FILE]...:

  • Square brackets mark something optional. [FILE] means you may give a file; with none, gzip reads its input from elsewhere (Chapter 6).
  • ... means “may repeat”: any number of options, any number of files.
  • Capitals, or words in angle brackets such as <file>, commonly stand for a value you supply.
  • You never type the brackets or the dots. gzip -t reads.fastq.gz, not gzip [-t] [reads.fastq.gz]....

These are common conventions, not rules every tool follows, but most do. Flags come in a short form (-T, one dash, one letter) and a long form (--tabular, two dashes, a word); both mean the same, and the long one is easier to read later. Some flags take a value: -j 4 and --threads 4 both ask for four CPUs. Tools with subcommands, such as seqkit stats, samtools sort, or git commit, have help at each level. Not every tool answers --help: some use -h, some help, and some print their usage when run with no arguments at all.

Table 4.1 lists where to look.

Why the version matters. A website describes the latest release; your environment has the version in pixi.lock (pixi list shows it, Chapter 2). If a flag from the website is not in your --help, the website is probably ahead of your copy.

Tip--help always matches what you run

--help is printed by the program you actually run, so it matches your version. Online docs may describe a newer one, and on a Mac, man may show the page of a different program with the same name.

That last point is a macOS detail. After Chapter 1’s setup, ls and sed run the GNU tools, and the MANPATH lines you added there make man ls open the GNU page too. If a man page ever describes options your command rejects, trust --help.

Check yourself. In Usage: gzip [OPTION]... [FILE]..., must you give a file?

TipAnswer

No. [FILE] is in square brackets, so it is optional; with no file, gzip reads standard input, as the last line of its help says (Chapter 6).

4.3 Reading an error message

A diagnosis round first. Below are six commands that fail, each run on the book’s files with its real output (captured with seqkit 2.14.0, R 4.4.3, and pixi 0.84.2). For each one, say what went wrong before you open the answer. Two need a file you make first, a copy of the first read file cut short:

Terminal (laptop)
head -c 1000000 data/raw/SRR6357070_1.fastq.gz > ~/bioinf-ch04/broken.fastq.gz

(head -c 1000000 keeps the first million bytes, under half the file. It writes to the scratch folder, never into data/raw/.)

1.

Terminal (laptop)
seqkit stats data/raw/SRR6357070_1.fastq.gz
bash: seqkit: command not found

2.

Terminal (laptop)
pixi run seqkit stats data/raw/SRR6357070_l.fastq.gz
[ERRO] stat data/raw/SRR6357070_l.fastq.gz: no such file or directory

3.

Terminal (laptop)
pixi run seqkit stats –T data/raw/SRR6357070_1.fastq.gz
[ERRO] stat –T: no such file or directory

4.

Terminal (laptop)
pixi run seqkit stats --paired data/raw/SRR6357070_1.fastq.gz
Error: unknown flag: --paired
Usage:
  seqkit stats [flags]
...
unknown flag: --paired

5.

Terminal (laptop)
pixi run seqkit stats -T ~/bioinf-ch04/broken.fastq.gz
[ERRO] /home/you/bioinf-ch04/broken.fastq.gz: unexpected EOF
[ERRO]
file    format  type    num_seqs    sum_len min_len avg_len max_len

6.

Terminal (laptop)
pixi run Rscript -e 'read.csv("data/meta/samples.csv")'
Error in file(file, "rt") : cannot open the connection
Calls: read.csv -> read.table -> file
In addition: Warning message:
In file(file, "rt") :
  cannot open file 'data/meta/samples.csv': No such file or directory
Execution halted
TipAnswers
  1. command not found, printed by the shell (bash:): no program called seqkit is on this shell’s PATH, so it never started. The fix is pixi run (Chapter 2). If another copy of seqkit were installed somewhere else, the bare command would have run that copy instead, possibly a different version (Chapter 7).
  2. A typo. The file name has a lowercase letter l where the digit 1 belongs: _l.fastq.gz. ls data/raw/ shows the real names.
  3. An en dash. –T starts with an en dash (–), not a hyphen (-). This happens when a command is copied from a PDF or a word processor. seqkit does not recognise it as a flag, so it treats –T as a file name and cannot find it. Retype the dash.
  4. A flag that does not exist. seqkit stats has no --paired; it prints its usage to show what it does accept. (Section 4.8 comes back to where this flag came from.)
  5. A file cut short. The [ERRO] line says unexpected EOF (end of file): the gzip data stops in the middle. seqkit still printed the table’s header line, with no rows.
  6. The wrong file name. The error says only cannot open the connection; the warning below it says which file and why: there is no data/meta/samples.csv. The file in Chapter 3 is samples.tsv.

4.3.1 Who, what, and on what

You may have noticed a pattern. Figure 4.2 shows it on two of the messages.

  • Who printed it. A message starting bash: comes from the shell: it could not even start the program. Otherwise it usually comes from the program you ran, which you know from your command. [ERRO], Error, and WARNING are severity labels, not names. R’s Error in file(...) names the function that failed.
  • What failed: stat (looking a file up), cannot open, unknown flag, unexpected EOF.
  • On what: the file, flag, or object, often in quotes. Read it character by character; that is where _l and –T were hiding.

Not every message has all three. A program that runs out of memory may print only Killed; a crash may print almost nothing. Then the log and the checklist (Section 4.4) carry the diagnosis.

Read all of it. Long messages are common, and the last line is not always the one that matters. Look for the earliest relevant failure in this run: later lines are often consequences of the first one. But the useful detail can sit further down, as in R’s message, where the reason is in the warning after the error. And a log you append to may still hold errors from earlier runs; check the times.

ImportantKey idea

Look for who printed the message, what failed, and on what. Read all of it, and find the earliest relevant failure in this run. An exit status of 0 means “reported success”, not “right answer”.

4.3.2 Errors and warnings

An error reports that something failed. Whether the program or your script then stops depends on the program and the script (Chapter 8). A warning asks you to look: sometimes the result is still what you wanted, sometimes not. In R:

Terminal (laptop)
pixi run Rscript -e 'as.integer(c("12","7","n/a"))'
[1] 12  7 NA
Warning message:
NAs introduced by coercion

R turned "n/a" into NA (missing) and carried on. That is right if n/a really means “missing” in that column, and wrong if it was a typo for a number. Only you know which.

4.3.3 Exit status

Every command, when it finishes, reports a number to the shell: its exit status. 0 means the program reports success; anything else means it reports a failure. echo $? prints the status of the command just before it, so run it immediately after: any other command in between replaces the number.

Terminal (laptop)
seqkit version
echo $?
bash: seqkit: command not found
127

127 is the shell’s code for “command not found”. Now the truncated file from round 5:

Terminal (laptop)
pixi run seqkit stats -T ~/bioinf-ch04/broken.fastq.gz
echo $?
[ERRO] /home/you/bioinf-ch04/broken.fastq.gz: unexpected EOF
[ERRO]
file    format  type    num_seqs    sum_len min_len avg_len max_len
0

seqkit 2.14.0 printed an error and reported success. (SeqKit’s current documentation says read errors give a nonzero status, so a later version may behave differently.) That is the lesson, whatever the version: the exit status says what the program reported. It does not prove the output answers your question. Read the messages, and check the result against something you know: here, a table with no rows instead of 50,000 reads. How scripts and pipelines use exit status is Chapter 8.

CautionMisconception: “If no error appears, the result is right”

Reality. Warnings let runs continue, and some tool versions report success after printing an error (seqkit 2.14.0 on a truncated file). Check outputs against something you know: a read count, a file size, a number from the paper.

Other languages have their own common messages (R’s could not find function, Python’s ModuleNotFoundError); they come with Chapter 12 and Chapter 13.

Check yourself. A message starts bash: samtools: command not found. Did samtools run?

TipAnswer

No. The message comes from the shell (bash:), which could not find a program called samtools, so it never started. Check whether you need pixi run (or, on a cluster, module load).

4.4 Before you ask: a troubleshooting checklist

Two cases first.

Case 1: the wrong folder. Go to your home folder and run Chapter 3’s script, the way you ran it there:

Terminal (laptop)
cd ~
pixi run bash src/01_count_reads.sh
Error:   × could not find pixi.toml or pyproject.toml with tool.pixi at directory /home/you

pixi looks for pixi.toml in the folder you are in (and the folders above it) and finds none. (If some folder above yours held a pixi.toml, the message would differ: pixi would use that one, and the error would come later.) The fix is the folder, not the command:

Terminal (laptop)
pwd
cd ~/bioinf-book

Case 2: a pattern that matches nothing.

Terminal (laptop)
pixi run seqkit stats -T data/raw/*.fq.gz
[ERRO] stat data/raw/*.fq.gz: no such file or directory

The clue is the * inside the message. bash replaces a pattern such as *.fq.gz with the matching file names, but when nothing matches it passes the pattern on unchanged, and seqkit looks for a file literally called *.fq.gz. ls data/raw/ shows the files end in .fastq.gz, not .fq.gz. Why bash does this is Chapter 5.

Both cases are solved by a question you can ask of almost any problem. Figure 4.3 puts those questions in order.

  1. Read the message, all of it (Section 4.3).
  2. Find the log. The terminal may show only the last lines; a log can hold the first error. More below.
  3. Where am I, with what? pwd, hostname, ls; did you use pixi run? On a cluster, which modules are loaded?
  4. Do the inputs exist and look right? ls -l, head, gzip -t, md5sum -c (Chapter 3); do the names in your sample sheet match the file names?
  5. Are resources short? No space left on device, Disk quota exceeded, a time limit, Killed (Table 1.4).
  6. What changed since it last worked? New data, a new version, a new folder, a new machine?
  7. Make it small. Does it still fail on 100 reads, on one sample? (Section 4.7 shows how.)

Not every step is needed every time; stop when it is solved. If it is still not solved after step 7, the way out is to ask (Section 4.6, Section 4.7), with what you checked.

ImportantKey idea

Most problems are found by the same few questions: where am I, with which software, on which inputs, with enough resources, and what changed. Stop when it is solved.

Finding the log. Chapter 3’s script writes a log in logs/ every time it runs, one file per run, with everything it printed. Here is the log of a run that failed because a raw file had been moved out of data/raw/ (captured; the host name is replaced):

logs/01_count_reads_2026-11-17T122821_jlSC.log
started:  2026-11-17 12:28:21 -0600
host:     <laptop>
script:   76fa8eb6a7b90f212042cfbe6d95cfcc  src/01_count_reads.sh
seqkit:   seqkit v2.14.0
checking inputs against data/raw/checksums.md5:
SRR6357070_1.fastq.gz: OK
md5sum: SRR6357070_2.fastq.gz: No such file or directory
SRR6357070_2.fastq.gz: FAILED open or read
md5sum: WARNING: 1 listed file could not be read

No finished: line, so the run stopped early. The earliest relevant failure is the line naming SRR6357070_2.fastq.gz: who (md5sum), what (could not open it), on what (the R2 file). The run never reached seqkit stats, so results/ still holds the previous run’s counts: another reason to check the log, not only whether a results file exists. The log keeps all this after the terminal is closed, with the date, the machine, and the versions.

Not every program writes a log, and a log does not always name the cause. Later chapters add more places to look: a cluster job’s output file, slurm-<jobid>.out (Chapter 10), and a pipeline’s .nextflow.log and each task’s .command.err (Chapter 26). On a cluster, steps 3 and 5 matter more: which node you are on, which modules are loaded, and which quota is full.

When to ask. If you have made no progress for about an hour, that is a good point to stop and ask; your lab’s habits come first, and it is not a limit you must reach. Ask at once for anything about accounts, passwords, or keys; when a fix could damage data or affect other users; and when something that worked stops working in a way your own changes do not explain (a slow or missing filesystem, a module that will not load, a quota). You do not need to know whether the system is at fault: report what you saw and what you checked.

WarningPitfall: changing many things at once

Change one thing, rerun, and look. Three changes at once leave you not knowing which one fixed the problem, or which one broke something else.

Check yourself. A script worked yesterday and fails today with No such file or directory. Name two checklist questions to ask first.

TipAnswer

Where am I (pwd)? Do the inputs exist (ls -l)? And what changed: a moved folder, a renamed file?

4.5 Reading a methods section

When you want to repeat or build on an analysis, the paper’s methods section is where you find out which tools, versions, and parameters were used. The book’s running dataset comes from Wu et al. (2018), which is openly licensed (CC BY), so it can be quoted here. Open it in PubMed Central and find two places: the Software and Algorithms rows of the Key Resources Table, and the paragraph Differential Expression Analysis in the methods.

Four words you will meet there, one line each (the Transcriptomics book explains them):

  • Adapter trimming: cutting the sequencing adapters off the ends of reads.
  • Alignment: finding where in the genome each read comes from.
  • Counting: how many reads fall in each gene.
  • Differential expression: which genes change between conditions.

Your turn. Fill in Table 4.4 for the RNA-seq analysis from those two places, before you open the answer. The last two columns matter: what the paper prints, and what you would type.

TipAnswer
Step Tool Version Parameters as printed As you would type them Reference, data
Trim adapters cutadapt 1.9.1 –minimum-length=25–quality-cutoff=20 -a AGATCGGAAGAGC -A AGATCGGAAGAGC --minimum-length=25 --quality-cutoff=20 -a AGATCGGAAGAGC -A AGATCGGAAGAGC —
Align and quantify RSEM with STAR 1.3.0; STAR 2.5.2a –star-output-genome-bam–forward-prob 0, all else default --star-output-genome-bam --forward-prob 0 S. cerevisiae genes from Ensembl, assembly R64-1-1, release 90
Differential expression DESeq2 1.12.3, in R 3.3.1 not reported in this excerpt — —

Three things to notice.

The dashes and the spaces. The paper prints –minimum-length and –forward-prob with a single en dash: typesetting turned the two hyphens of -- into one –. Copied as printed, they fail exactly like round 3 of Section 4.3. Look again at the spacing, too: –minimum-length=25–quality-cutoff=20 and –star-output-genome-bam–forward-prob have no space between the two options, so a program would read each pair as one long, unknown word. Both faults need repairing before the command can run.

WarningPitfall: commands copied from PDFs and web pages

Typesetting turns -- into – and straight quotes (", ') into curly ones (“, ’). The command looks right and fails, or worse, does something else. Retype dashes and quotes when you copy from a paper.

The strandedness setting. --forward-prob 0 says how the library was made: which strand of the gene each read comes from (Chapter 26 and the Transcriptomics book explain strandedness). The nf-core test sheet the book uses (Chapter 3) says auto for our sample, WT_REP1. auto asks the pipeline to work out the strandedness from the reads; it does not state it, so it is not a second source for the paper’s value.

What this excerpt does not report. The STAR and RSEM index settings, DESeq2’s design and thresholds, and any code. Before saying the paper omits them, check its supplements and any deposited code. A complete methods section names the tool, the version, the parameters, the reference release, and where the code and data are: the same chain you recorded for your own project in Chapter 3.

Two cautions. First, the book later runs these reads through nf-core/rnaseq (Chapter 26). That is a different, newer analysis, not a reconstruction of the paper’s. Second, a methods section can describe several kinds of library: this paper also has single-end TSS-seq reads of 76 bases. Which paragraph describes our reads? Exercise 4 checks it against the run’s public record.

Check yourself. The excerpt says “STAR (version 2.5.2a)” but not the index options. Can you reproduce the alignment exactly from the excerpt?

TipAnswer

Not for certain: index settings can change the results. Check the supplements and any deposited code; then either assume the defaults (and say so) or ask the authors.

4.6 Searching, and choosing where to ask

Most errors have been seen before. Searching well means turning your message into one that matches other people’s. Take this one, from a truncated file on a cluster:

[ERRO] /home/<user>/proj/sample_17_R1.fq.gz: unexpected EOF

Remove what is yours (the path, the sample name), keep the distinctive part in quotes, and add the tool’s name:

seqkit "unexpected EOF"

Search the tool’s own GitHub issues too, for example seqkit’s, including closed ones: a closed issue often holds the answer. Reading issues is all you need here; filing one is 1.

TipSearch tip

Search the distinctive part of the message in quotes, without your paths and sample names, plus the tool’s name.

Where to ask depends on the kind of problem (Table 4.5). If your lab has local experts and asks them first, do that.

Judging an answer. How old is it, and which version does it assume? Is it from the tool’s authors or documentation? Does it explain why? And does it work on your small example? A 2015 answer may name flags that no longer exist.

Check yourself. Your job on the cluster cannot write to /project, and the quota command shows you at your limit. Where do you ask?

TipAnswer

Your cluster’s help desk, or your PI if the project’s quota is theirs to raise. Not Biostars: nobody there can change your quota.

4.7 Asking for help

Here is a request that is hard to answer:

seqkit doesn’t work on the cluster, help!!

[a screenshot of the last few lines of a terminal]

A helper cannot tell which command, which files, which version, or even which error: the screenshot cuts off the first line. They have to ask four questions before they can start. Figure 4.4 shows the same problem written so that someone can answer at once.

The book’s own Something doesn’t run form is a good starting model: where it ran (laptop, login node, or compute node; operating system; cluster), the exact command, copied, the complete message as text, and pixi info. A question about a tool also needs:

  • what you were trying to do, and what you expected;
  • what you tried already;
  • the failing tool’s version;
  • a small example that still fails.

Versions, each for its own question.

  • pixi info describes where and how: the platform, pixi’s version, the environment, and its folders. It does not list package versions.
  • pixi run seqkit version gives the version of the tool that failed. With pixi run, it reports the copy that actually ran.
  • pixi list shows every package’s version, when several might matter.
  • In R, pixi run Rscript -e 'sessionInfo()' (Chapter 12).

Do not paste the whole pixi.lock; it is thousands of lines.

4.7.1 A minimal reproducible example

A minimal reproducible example is the smallest input and the shortest command that still show the problem. Shrink until it still fails, and rerun after every cut, to check that it still fails the same way. Fewer files, one sample, the first 100 reads:

Terminal (laptop)
pixi run seqkit head -n 100 data/raw/SRR6357070_1.fastq.gz \
  -o ~/bioinf-ch04/small_R1.fastq.gz

That writes the first 100 reads (10,100 bases) to the scratch folder, never to data/raw/. Now the catch. Do the same with the truncated file, and check the small copy:

Terminal (laptop)
pixi run seqkit head -n 100 ~/bioinf-ch04/broken.fastq.gz \
  -o ~/bioinf-ch04/small_broken.fastq.gz
pixi run seqkit stats -T ~/bioinf-ch04/small_broken.fastq.gz
file    format  type    num_seqs    sum_len min_len avg_len max_len
/home/you/bioinf-ch04/small_broken.fastq.gz FASTQ   DNA 100 10100   101 101.0   101

No error. The first 100 reads of the broken file are intact; the damage is at its end. Shrinking removed the bug: this example is too small. That is why you rerun after every cut. Some failures need no real data at all (a wrong file name fails on any file), and often the shrinking finds the bug for you. In R, the reprex package builds such examples (reprex.tidyverse.org, Chapter 12).

4.7.2 Text, not screenshots

Paste commands and messages as text. Text can be searched, copied, quoted, and read by screen readers; a screenshot can do none of these, and it usually cuts off the first error. Put it in a Markdown code block, between lines of three backticks (Markdown, Chapter 3):

```
Error: unknown flag: --paired
```

A screenshot can add to the text when the problem is something on screen, such as a VS Code panel or a dialog. For a long log, post the relevant part with a few lines around it, and keep the full log to share if the venue asks for it.

4.7.3 Privacy and etiquette

Before you post, replace user names, paths, and host names you would rather not share with placeholders, and do it consistently (always <home>, always <user>). Keep the fault visible while you do: the relative layout, the extension, upper and lower case, the l vs 1, the en dash. pixi info, for example, prints paths in your home folder.

WarningPitfall: secrets in public

Never post passwords, SSH private keys, tokens, unpublished data, or data under a use agreement (ask your PI if unsure). Forums and issue trackers are public, and what you post is copied and indexed: deleting it later does not take it back.

Two habits of good askers: if you post the same question in two places, say so in each; and when it is solved, post the answer and mark it solved, for the next person who searches.

4.8 AI coding assistants

AI coding assistants can explain an error, suggest a command, or draft a help request. They can also be confidently wrong. Here is an answer to “count read pairs in my paired FASTQ files with seqkit”. It was written for this book to show a typical mistake, not captured from a particular assistant:

Use seqkit’s stats command with the --paired flag:

seqkit stats --paired data/raw/SRR6357070_1.fastq.gz data/raw/SRR6357070_2.fastq.gz

Check it, in three steps:

  1. Is the flag real? pixi run seqkit stats --help lists no --paired.

  2. Run it. You did, in round 4 of Section 4.3: Error: unknown flag: --paired.

  3. Fix it, then check what the answer means. Without the invented flag, the command runs:

    Terminal (laptop)
    pixi run seqkit stats data/raw/SRR6357070_1.fastq.gz data/raw/SRR6357070_2.fastq.gz

    It prints one row per file, each with 50,000 reads. The two files are the two mates of the same fragments (Chapter 1), so the run has 50,000 read pairs, not 100,000. A command that runs is not yet an answer to the question.

Rules for using an assistant:

  • Treat its suggestions as coming from a fast, confident colleague who is sometimes wrong.
  • Check every flag against --help for your version.
  • Test on small data with a known answer before real data.
  • Understand any command before you run it, above all ones that delete or overwrite (rm, >, mv). Never run those unread on raw data or on shared systems.
  • Paste error text and small toy examples. Never paste credentials, private or unpublished data, or anything your institution’s or your data agreement’s current policy restricts.
  • Follow your journal’s and your university’s rules on disclosing AI use.

Used this way, assistants are good at the two skills this chapter teaches: explaining an error message, and drafting a help request. As long as you check the result.

WarningPitfall: trusting an AI-suggested flag

Check every flag against --help, and test on data with a known answer, before you run an AI-suggested command on real data.

CautionMisconception: “Code from an AI assistant works; I can assume it has been tested”

Reality. It is generated text. Flags can be invented or belong to another version, and even code described as tested may have been tested on other inputs or another system. Check flags in --help and reproduce a known result.

4.9 Summary

  • --help comes from the program you run, so it matches your version; man pages and websites may not. In a usage line, brackets mean optional, ... means repeatable, and you type neither.
  • Read the whole message for who printed it, what failed, and on what, and find the earliest relevant failure. An exit status of 0 means the program reported success, not that the result is right.
  • Before asking, work through the checklist: message, log, where and with what, inputs, resources, what changed, a small example. Stop as soon as it is solved.
  • A methods section should give tool, version, parameters, and reference; retype its dashes, and say “not reported in this excerpt” until you have checked the supplements.
  • A good help request has the exact command, the complete message as text, versions, and a small example that still fails, with nothing private in it. Check every AI-suggested flag in --help and test on data with a known answer.

TipAnswer

seqkit checks its flags before it looks at files, so the faults appear in this order (exit status in brackets):

  1. Error: unknown flag: --paired, followed by the usage [255]. Delete --paired.
  2. [ERRO] stat –T: no such file or directory [255]. The en dash made –T a file name; retype it as -T.
  3. [ERRO] stat data/raw/SRR6357070_l.fastq.gz: no such file or directory [255]. Change the letter l to the digit 1.

The fixed line is seqkit stats -T data/raw/SRR6357070_1.fastq.gz data/raw/SRR6357070_2.fastq.gz, and it prints [0]:

file    format  type    num_seqs    sum_len min_len avg_len max_len
data/raw/SRR6357070_1.fastq.gz  FASTQ   DNA 50000   5050000 101 101.0   101
data/raw/SRR6357070_2.fastq.gz  FASTQ   DNA 50000   5050000 101 101.0   101
