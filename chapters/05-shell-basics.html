5  Shell basics

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Say what the shell does with a command line before a program runs, and tell a shell builtin from a program.
  2. Move around the filesystem with absolute and relative paths, ~, ., and .., and check where you are with pwd.
  3. Create, copy, move, rename, link, and delete files and folders, and avoid the commands’ silent overwrites and permanent deletes.
  4. Predict what a wildcard matches, quote names with spaces or special characters, and use tab completion and history to type less.
  5. Find files with find, and look inside files with less, head, tail, and file.

5.1 Why the command line

This chapter opens Part II, six chapters on the Linux command line. That is a large share of a bioinformatics book to spend on typing commands, so first, the reason.

Real work runs on Linux machines that you reach through a terminal. A university cluster such as Nova or SCINet’s Ceres runs Linux. You log in with ssh, and what you get is a prompt, not a desktop. Companies, and labs without a cluster, rent Linux servers in the cloud (Chapter 38) and reach them the same way. Your laptop is for editing, small tests, and writing up. The data and the long jobs live on those machines (Section 1.7). Section 1.6 explained why they run Linux; this part teaches you to work on them.

The command line also suits the work itself, not only the machines it runs on (Table 5.1).

Why bash. The shell is the program that reads what you type (Section 5.3). There are several shells. Bash is the default on nearly every Linux system and cluster, cluster job scripts are usually bash scripts, and tools’ install instructions assume it. So the book uses bash everywhere, including on a Mac, where you made it your shell in Chapter 1. Learn it once, and the same commands work on your laptop, the cluster, and a cloud server.

Part II builds up to running a real job on a cluster, one chapter at a time (Table 5.2).

5.2 What this chapter does

You have already run about thirty shell commands in Part I, mostly by copying them: mkdir -p … && cd …, ls -lh, cat, head, mv, cp, ln -s, chmod, touch. Each time the book said “explained in Part II”. This is that explanation. Once you know what each part of a command does, you can change it, predict what it will do, and spot the one character that is wrong.

The chapter covers what the shell does with a line before any program runs; how to move around the filesystem; how to copy, move, link, and delete without losing files; wildcards and quoting; find; looking inside files of any size; and recalling earlier commands instead of retyping them. Pipes and redirection (|, >) are Chapter 6; permissions, PATH, and your shell’s settings are Chapter 7; variables and scripts are Chapter 8. A few supplied commands here contain a |; copy those as they are.

Commands run on your laptop. In the book’s project, ~/bioinf-computing, you only look at files in this chapter; the one thing you write there is your own notes in NOTEBOOK.md, as in Chapter 3 and Chapter 4. Everything that creates, moves, or deletes happens in a scratch folder, ~/bioinf-computing-ch05, so a mistake cannot touch the project.

Build the practice folder. Paste the block below into your terminal in one go. It makes ~/bioinf-computing-ch05/share/, a stand-in for the kind of folder a former lab member leaves behind: reads in three run folders, one with spaces in its name; plots and a counts file; two sample tables; a stray temporary file; and a link that points nowhere. Chapter 6, Chapter 7, and Chapter 8 reuse this folder, so keep it.

Terminal (laptop)
mkdir -p ~/bioinf-computing-ch05
mkdir ~/bioinf-computing-ch05/share && cd ~/bioinf-computing-ch05/share && {
mkdir run1 run2 "Run 3 final" analysis meta
printf '@A.%s\nACGTACGTAC\n+\nIIIIIIIIII\n' 1 2 | gzip > run1/sample_A_R1.fastq.gz

printf '@B.%s\nACGTACGTAC\n+\nIIIIIIIIII\n' 1 2 3 | gzip > run2/sample_B_R1.fastq.gz
printf '@B.%s\nGTACGTACGT\n+\nIIIIIIIIII\n' 1 2 3 | gzip > run2/sample_B_R2.fastq.gz
cp run2/sample_B_R1.fastq.gz run2/sample_B_R1.fastq.gz.tmp
printf '@C.%s\nACGTACGTAC\n+\nIIIIIIIIII\n' 1 2 3 4 | gzip > "Run 3 final/sample_C_R1.fq.gz"
printf '@C.%s\nGTACGTACGT\n+\nIIIIIIIIII\n' 1 2 3 4 | gzip > "Run 3 final/sample_C_R2.fq.gz"
touch "analysis/plot 1.png" "analysis/plot 2.png"
seq 1 1000 > "analysis/counts FINAL.txt"
rows=(sample run_folder condition reads
  sample_C "Run 3 final" treated 12
  sample_A run1 control 9
  sample_B run2 control 30
  sample_E run5 treated 105

printf '%s,%s,%s,%s\r\n' "${rows[@]}" > meta/samples_from_excel.csv

It is safe to paste without understanding it yet. This chapter explains mkdir, cd, cp, touch, and ln -s; printf, gzip, and the | come in Chapter 6, and the rows=(…) list in Chapter 8. The read files are real, tiny gzipped FASTQ files (2, 3, and 4 reads for samples A, B, and C), so the tools you use on them behave as on real data. On a Mac, touch -d needs the GNU tools from Chapter 1’s setup.

Pasting the block a second time is safe: mkdir stops with File exists and nothing else runs, so it cannot undo changes you made. To rebuild the folder on purpose, rename the old one first and paste again: mv ~/bioinf-computing-ch05/share ~/bioinf-computing-ch05/share_old. The book never deletes a scratch folder for you.

5.3 What a shell is

Type these, one at a time:

Terminal (laptop)
cd ~
ls
lss
type cd
type mkdir
bioinf-computing       bioinf-computing-ch03  bioinf-computing-ch05
bioinf-computing-ch01  bioinf-computing-ch04  bioinf-shared
bash: lss: command not found
cd is a shell builtin
mkdir is /usr/bin/mkdir

Your home folder will hold other things too. lss gives the message from Table 4.2: no program has that name. (Ubuntu may add a suggestion: Command 'lss' not found, did you mean ….) type asks bash what a name is: cd is part of bash itself, while mkdir is a program stored in a file. On a Mac after Chapter 1’s setup, type mkdir shows the GNU copy, /usr/local/opt/coreutils/libexec/gnubin/mkdir or a path under /opt/homebrew. (Try type ls too: on many systems it says ls is aliased to …. Aliases are Chapter 7.)

Now name the parts. The terminal is the window. The shell is the program inside it that reads what you type and starts other programs; this book’s shell is bash. A command is either a program (ls, mkdir, seqkit) or a builtin, part of bash itself (cd, pwd, echo, type, history). cd has to be a builtin: a separate program runs as its own process, and changing its folder would leave your shell where it was.

Every line follows the shape you met in Chapter 4’s usage lines: the command first, then its options (-l, --help), then its arguments, usually names of files or folders. Whatever the command, bash first does the same work on the line (Figure 5.1):

  1. It reads the line into words, at spaces, but respecting quotes and backslashes: "Run 3 final" stays one word.
  2. It expands ~, wildcards such as *, and $… where quoting allows.
  3. It removes the quote characters themselves.
  4. It finds the command and starts it with the resulting arguments.

Quoting decides what happens in steps 1 and 2. A file name produced by a wildcard is one argument even if it contains spaces, as Section 5.8 shows. (Bash calls something else “word splitting”: splitting the result of a $… expansion, which is Chapter 8. Step 1 is just reading the line.) This is the frame for the whole chapter: quoting and wildcards are steps 1–3, and how bash finds a program in step 4 (PATH) is Chapter 7. The Bash manual gives the full order of expansions, for later.

ImportantKey idea

Before any program starts, bash reads your line into words (respecting quotes), expands ~, wildcards, and $… where quoting allows, and removes the quotes. The program gets only the resulting arguments. Most surprises in this chapter come from that step.

Bash, not zsh. A new Mac’s default shell is zsh, which is similar but not the same. Chapter 1 made bash your shell on every system, because clusters use it. Check:

Terminal (laptop)
echo "$BASH_VERSION"
5.3.15(1)-release

Any version from 4 up is fine; Ubuntu 24.04 has 5.2 and 26.04 has 5.3 (what WSL installed in November 2026), and a cluster may have an older one (Nova had 5.1 in November 2026). If nothing prints, you are not in bash: go back to Chapter 1.

The prompt. A prompt such as you@laptop:~/bioinf-computing$ tells you who you are (you), which machine you are on (laptop), and which folder you are in (~/bioinf-computing), then $: ready. Clusters set theirs up for you; the host name tells you whether you are on a login node (Chapter 10). Yours may look different; Chapter 7 shows how to change it.

Check yourself. Why can’t cd be a separate program, like mkdir?

TipAnswer

A program runs as its own process. If it changed folder, only its own folder would change, and your shell would stay where it was. type cd says cd is a shell builtin.

Figure 5.2 shows the same moves on the folder tree.

Now name the parts (Figure 5.3). Every file on the machine sits in one tree that starts at /, the root. Your home folder is one branch of it, /home/you, and ~ is short for it. A path names a place in the tree:

  • An absolute path starts at the root, with /: /home/you/bioinf-computing/data/meta. It means the same thing from anywhere. A path starting with ~ is absolute too, since bash turns ~ into /home/you (step 2 above).
  • A relative path starts from where you are, the current working directory that pwd prints. From data/raw, ../meta means “up one folder, then into meta”.
  • . is the current folder and .. the one above it.

Where your home folder is depends on the system (Table 5.4).

Names are case-sensitive, as Chapter 3 said: Data and data are different folders on Linux and on clusters.

Relative to what? A relative path always means “from where I am now”, even inside a script. The setup block made a two-line script, ~/bioinf-computing-ch05/where.sh, that prints the current folder and lists data/raw:

Terminal (laptop)
cat ~/bioinf-computing-ch05/where.sh
cd ~/bioinf-computing
bash ~/bioinf-computing-ch05/where.sh
cd ~
bash ~/bioinf-computing-ch05/where.sh
pwd
ls data/raw
/home/you/bioinf-computing
checksums.md5  SRR6357070_1.fastq.gz  SRR6357070_2.fastq.gz
/home/you
ls: cannot access 'data/raw': No such file or directory

The same script, run by the same absolute path, gives two results, because data/raw is looked up from the folder you ran it in. From ~ it looked for ~/data/raw, which does not exist. Chapter 4’s wrong-folder case was related but failed earlier: pixi run itself looks for pixi.toml in the current folder and the folders above it, and found none.

CautionMisconception: “A relative path is relative to the script that contains it”

Reality. It is relative to the current working directory of the shell that runs the command, wherever the script is stored. Run project scripts from the project folder, as the book does, or cd there first.

Errors you will meet:

Terminal (laptop)
cd nowhere
cd ~/bioinf-computing/README.md
bash: cd: nowhere: No such file or directory
bash: cd: /home/you/bioinf-computing/README.md: Not a directory

Note that the second message shows ~ already expanded: cd never saw the ~.

TipPress Tab

Type cd ~/bioi and press TabTab. Bash completes as far as the name is certain, here ~/bioinf-, because several folders start that way (bioinf-computing…, bioinf-shared). Press TabTab twice to list the choices, type a few more letters, and press it again. Tab saves typing and catches typos: more in Section 5.8.

Project and scratch areas are Chapter 10 and Appendix A; moving files between machines is Chapter 9.

In the project folder, try each option:

Terminal (laptop)
cd ~/bioinf-computing
ls -a
ls -F
ls -lh data/raw
ls -ld data/raw
ls -lt logs
.   .pixi  logs         notes.txt  pixi.toml  results
..  data   NOTEBOOK.md  pixi.lock  README.md  src
data/  NOTEBOOK.md  pixi.lock  README.md  src/
logs/  notes.txt    pixi.toml  results/
total 4.3M
-r--r--r-- 1 you you  112 Nov 17 11:22 checksums.md5
-r--r--r-- 1 you you 2.2M Nov 17 11:22 SRR6357070_1.fastq.gz
-r--r--r-- 1 you you 2.2M Nov 17 11:22 SRR6357070_2.fastq.gz
dr-xr-xr-x 2 you you 4096 Nov 17 11:22 data/raw
-rw-r--r-- 1 you you 369 Nov 17 12:28 01_count_reads_2026-11-17T122821_jlSC.log
-rw-r--r-- 1 you you 399 Nov 17 12:24 01_count_reads_2026-11-17T122453_7WFs.log

Your dates, sizes of logs, and log names will differ, and you may have more logs. What each option did:

  • -a (all) shows names starting with a dot. .pixi is the hidden folder where Chapter 2’s environment lives: do not edit it by hand; pixi install rebuilds it. . and .. are the current and the parent folder. A leading dot hides a name by convention; it does not protect it. (-A shows hidden names without . and ...)
  • -F adds / after folders (and @ after links, * after programs).
  • -l (long) gives one line per file, and -h prints sizes in human units (2.2M instead of 2239317). Options combine: -lh is -l -h, as in Chapter 4.
  • -d lists a folder itself instead of its contents (Chapter 3 used it to check data/raw was locked).
  • -t sorts by time, newest first: the quickest way to find the latest log.

With names as arguments, ls lists only those. Most systems colour names by type in the terminal (folders blue, links cyan); the book shows output without colour. When a name contains a space, GNU ls puts it in quotes, as in 'Run 3 final' in the setup block’s output: the quotes show where the name starts and ends and are not part of it.

Read one long line with Figure 5.4.

A folder’s size in ls -l (4096 above) is the size of its list of names, not of what is inside; du measures that (Chapter 7).

Check yourself. ls shows nothing in a folder, but the disk-usage tool says the folder holds 2 GB. What do you try first?

TipAnswer

ls -a: the space is probably in hidden files or folders, names that start with a dot, such as .pixi.

5.6 Creating, copying, moving, and deleting

5.6.1 Three surprises

cp and mv overwrite without asking. Make two small files and copy one over the other (> writes a command’s output into a file, as in Chapter 1; Chapter 6 explains it):

Terminal (laptop)
echo "version 1" > old.txt
echo "version 2" > new.txt
cp new.txt old.txt
cat old.txt
echo "version 3" > newer.txt
mv newer.txt old.txt
cat old.txt
ls
version 2
version 3
new.txt  notes  old_notes  old.txt

No question, no warning: version 1 is gone, then version 2. -i (interactive) asks first, and -n (no-clobber) never overwrites:

Terminal (laptop)
echo "version 4" > new.txt
cp -n new.txt old.txt
cat old.txt
cp -i new.txt old.txt
version 3
cp: overwrite 'old.txt'? n

cp -n skipped the copy without a message; cp -i asked, and n kept the old file. (On Ubuntu 24.04 and later, cp -n also prints cp: warning: behavior of -n is non-portable and may change in future; use --update=none instead. The copy is still skipped, so ignore it: --update=none does not exist on older systems such as many clusters.)

rm has no trash folder and no undo. A file removed with rm is gone at once; nothing on the command line puts it back. rm -i asks before each file. rm -r on the wrong folder is the classic disaster.

A trailing slash matters for links. Chapter 3 showed that rm -r data/ref/ follows the link and deletes the shared files. Remove a link with unlink name or rm name: no slash, no -r.

WarningPitfall: no undo

rm deletes for good, and cp and mv overwrite silently. Before you delete, list exactly the names the command will get, with ls -d -- <the same names>. Keep raw data read-only and backed up (Chapter 3): those are the only undo.

5.6.2 The safe habit: preview, then delete

Go to the practice tree and list what a wildcard would hand to rm (wildcards are explained in Section 5.8; run* means “names starting with run”):

Terminal (laptop)
cd ~/bioinf-computing-ch05/share
ls run*
ls -d -- run*
run1:
sample_A_R1.fastq.gz  sample_A_R2.fastq.gz

run2:
sample_B_R1.fastq.gz  sample_B_R1.fastq.gz.tmp  sample_B_R2.fastq.gz
run1  run2

Plain ls run* showed what is inside the two folders. But rm -r run* would get the folders themselves, run1 and run2, and ls -d -- run* lists exactly those. So the habit is:

  1. Run ls -d -- with the names or pattern you mean to delete.
  2. If the list is right, press UpUp, change ls -d to rm -i (Section 5.11 shows the editing keys), and run it.

-- means “no more options after this”. Quotes keep a name with spaces as one argument, but they do not stop a name that starts with - from being read as an option. Try it on a throw-away file named -n:

Terminal (laptop)
cd ~/bioinf-computing-ch05/practice
touch -- -n
rm -n
rm -i -- -n
rm: invalid option -- 'n'
Try 'rm ./-n' to remove the file '-n'.
Try 'rm --help' for more information.
rm: remove regular empty file '-n'? y

rm itself suggests the other way out: ./-n starts with ., so it cannot be an option. That was your first real deletion, of a file you made a minute ago, with -i asking first.

CautionMisconception: “Deleted files go to a trash folder I can restore from”

Reality. rm removes the name at once. There is no trash on the command line; only backups, or snapshots that some sites keep of some storage (Appendix A), can bring a file back. Ask before you count on snapshots.

More habits, one line each:

  • Never run rm -rf on a path built from a variable or a wildcard you have not previewed (variables are Chapter 8).
  • Keep raw data read-only: in Chapter 3, chmod a-w turned a slip into Permission denied.
  • The book does not suggest making rm always ask (an alias for rm -i): the habit stops protecting you the day you work on a machine without it.

5.7 Symbolic links, revisited

Chapter 3 made data/ref, a link to the shared reference folder. Here are four ways to ask where a link points:

Terminal (laptop)
cd ~/bioinf-computing
ls -l data/ref
readlink data/ref
readlink -f data/ref
realpath data/raw/../ref
lrwxrwxrwx 1 you you 53 Nov 17 11:22 data/ref -> /home/you/bioinf-shared/references/yeast_R64-1-1_test
/home/you/bioinf-shared/references/yeast_R64-1-1_test
/home/you/bioinf-shared/references/yeast_R64-1-1_test
/home/you/bioinf-shared/references/yeast_R64-1-1_test

readlink prints the path the link stores; readlink -f and realpath print where it finally leads, after following every link and every ... Here they agree because the link stores an absolute path. (For reference: you will rarely need readlink -f and realpath, but they are the tools for “where does this really go?”)

A broken link. The practice folder’s ref points to a path that does not exist:

Terminal (laptop)
cd ~/bioinf-computing-ch05/share
ls -l ref
cat ref
find . -xtype l
lrwxrwxrwx 1 you you 15 Nov 17 11:40 ref -> /no/such/genome
cat: ref: No such file or directory
./ref

ls -l still shows the link and its arrow (often in red), but anything that opens it fails with No such file or directory, although ref is right there in the listing. find . -xtype l lists broken links; it comes back in Section 5.9.

Relative targets. A link can store an absolute path or a relative one, and a relative one is read from the link’s own folder, not from the folder where you ran ln -s. This is the most common way to make a broken link (Figure 5.5). Try it from share, making links in a new folder tidy next to it:

Terminal (laptop)
cd ~/bioinf-computing-ch05/share
mkdir -p ../tidy
ln -s run1/sample_A_R1.fastq.gz ../tidy/wrong.fastq.gz
ln -s ../share/run1/sample_A_R1.fastq.gz ../tidy/right.fastq.gz
file -h ../tidy/wrong.fastq.gz ../tidy/right.fastq.gz
../tidy/wrong.fastq.gz: broken symbolic link to run1/sample_A_R1.fastq.gz
../tidy/right.fastq.gz: symbolic link to ../share/run1/sample_A_R1.fastq.gz

wrong.fastq.gz stores run1/sample_A_R1.fastq.gz, which is read from tidy/, where there is no run1. right.fastq.gz stores a path that goes up from tidy/ and into share/. (file names the kind of thing a path is, more in Section 5.10; -h makes it describe the link itself instead of following it, which Linux does by default but a Mac does not.) Now name it. echo did not do any matching. Bash replaces an unquoted pattern with the matching names before the command starts (called globbing, or filename expansion). The program receives a list of names and never sees the *. When nothing matches, bash’s default is to pass the pattern on unchanged (changing that default is Chapter 8). That explains Chapter 4’s case 2, [ERRO] stat data/raw/*.fq.gz: no such file or directory: seqkit was handed the literal data/raw/*.fq.gz and looked for a file with that name. ls does the same:

Terminal (laptop)

ls: cannot access '*.fq.gz': No such file or directory

Figure 5.6 shows all three cases.

CautionMisconception: “The program reads the * and finds the matching files itself”

Reality. For an unquoted pattern, bash does the matching first, and the program gets names, or the unchanged pattern when nothing matches. Only a quoted pattern reaches the program, which some programs, such as find -name, want.

One argument per name, spaces included. echo joins its arguments with spaces, so it cannot show where one ends and the next begins. In share/analysis, plot 1.png is one name, but echo makes it look like two. printf '<%s>\n' prints each argument on its own line, between < and >:

Terminal (laptop)

analysis/counts FINAL.txt analysis/plot 1.png analysis/plot 2.png

<analysis/plot 1.png>
<analysis/plot 2.png>

Three arguments, spaces kept: a name that comes from a wildcard is not split again. That is why ls analysis/* handles these names fine, and why echo is only a quick preview for simple names like the ones in run1. To see the exact list a command would get, use ls -d -- or printf '<%s>\n'.

5.8.1 Quoting

Step 1 of Figure 5.1 reads a line into words at spaces. So a name with a space, typed plainly, becomes two arguments:

Terminal (laptop)
ls analysis/plot 1.png
ls: cannot access 'analysis/plot': No such file or directory
ls: cannot access '1.png': No such file or directory

Three ways to keep it one word, all of which work:

Terminal (laptop)
ls "analysis/plot 1.png"
ls 'analysis/plot 1.png'
ls analysis/plot\ 1.png

The backslash form is what TabTab inserts for you. Double and single quotes differ in one way that matters later: inside double quotes bash still expands $… (variables, Chapter 8), and inside single quotes it expands nothing. Quoting also turns off wildcards and ~ (Table 5.8):

Terminal (laptop)
ls "run1/*.fastq.gz"
ls "~/bioinf-computing"
ls: cannot access 'run1/*.fastq.gz': No such file or directory
ls: cannot access '~/bioinf-computing': No such file or directory

The first looked for a file literally named *.fastq.gz. In the second, ~ was not expanded, so the path is relative: a folder literally named ~ inside the current folder, then bioinf-computing inside that (the / still separates folders). Leave ~ outside the quotes, or use $HOME, which double quotes do expand:

Terminal (laptop)
ls ~/"bioinf-computing-ch05/share/Run 3 final"
ls "$HOME/bioinf-computing-ch05/share/Run 3 final"
sample_C_R1.fq.gz  sample_C_R2.fq.gz
sample_C_R1.fq.gz  sample_C_R2.fq.gz
WarningPitfall: ~ and wildcards inside quotes

"~/data" is a relative path: a folder literally named ~, then data inside it. Write ~/"My Data" or "$HOME/My Data". And "*.fastq.gz" is the name *.fastq.gz, not a pattern.

Curly quotes copied from a PDF or a word processor (“…”, ‘…’) are not quotes to bash: they become part of the name, the same trap as Chapter 4’s en dash.

5.8.2 Tab completion

TabTab completes as far as the name is unique; a second TabTab lists the choices. It completes command names and paths, and with the bash-completion package (installed on most Linux systems) often options too. It is also a typo detector: if Tab will not complete a name you are sure of, check with ls. It would have flagged Chapter 4’s SRR6357070_l at once. Treat it as a clue, not proof: a prefix may match several names, permissions can get in the way, and completion differs between commands.

ImportantKey idea

Bash expands an unquoted wildcard; the program sees the matching names, each as one argument. No match means the pattern is passed on as it is. Quote a pattern when the program should match it itself (find -name).

5.8.3 Why careful names pay off

Experienced users name files 2026-11-17_read_counts.tsv rather than Read Counts (final).txt. This is not a matter of taste. On the command line, names are typed, matched by wildcards, and split into words, not clicked. The practice tree is messy on purpose: Run 3 final breaks three of the naming rules in Table 3.2 at once (a space, a capital letter, and the vague word “final”). This chapter has made you pay for each one. Table 5.9 gathers the costs in one place.

What about CamelCase or MyData? Capital letters work, and nothing breaks the first time you use them. The cost comes later. You have to remember which letters were capitals every time you type a name or press Tab. On Linux and the cluster, MyData and mydata can sit side by side as two folders. On a Mac or in a Windows folder they are the same name, so copying a project between them can overwrite one with the other. All lowercase removes the question. Join words with _ (read_counts.tsv), and use - inside a single part, such as a date or a version (2026-11-17, R64-1-1), as Table 3.2 does. For code, prefer _: Python cannot import a file named with a hyphen, such as count-reads.py (Chapter 13).

Two kinds of names keep their capitals. IDs from an archive or a sample sheet stay exactly as given (SRR6357070, WT_REP1), so they still match the records. A few files are capitalized by long convention so that people and tools find them first: README.md, LICENSE, Makefile, and your NOTEBOOK.md.

The structure is find <where> <tests> [action]:

  • Tests written next to each other must all be true (an implicit AND): -type f -name "*.tmp" means “an ordinary file and named *.tmp”.
  • -o means OR, and \( … \) groups. The backslashes stop bash from reading the parentheses itself; the spaces around them are needed. Without the group, -type f -name A -o -name B means “(file and A) or B”.
  • The default action is to print each name.

Two tests for reference, useful on real data:

Terminal (laptop)
find share -type f -size +1k
find share -mtime +30
share/analysis/counts FINAL.txt
share/notes.txt
share/.old_settings

-size +1k means larger than 1 kilobyte: only the counts file, since the toy FASTQ files are under 50 bytes each. -type f keeps it to files: on Linux every folder takes 4 KB, so without it share and its folders would be listed too (a Mac’s folders are smaller). On a .gz file, -size measures the compressed file. -mtime +30 means last changed more than 30 days ago: the two files the setup block back-dated to 2025-03-01. -mtime -1 would find files changed in the last day.

WarningPitfall: quote the pattern after find -name

5.11 History and shortcuts

Bash remembers what you type. Press UpUp a few times: earlier commands come back, ready to run with EnterEnter or to edit first. To see a numbered list of recent ones:

Terminal (laptop)
history | tail

(The | passes the list to tail, which keeps the last 10; Chapter 6 explains it.) Faster for an old command is reverse search: press Ctrl-RCtrl-R and type seqkit. The prompt changes to (reverse-i-search) and shows the newest command containing seqkit. Press Ctrl-RCtrl-R again for older matches, EnterEnter to run the one shown, or RightRight (or EscEsc) to put it on the line to edit first.

Editing a recalled line without the arrow keys (Table 5.13): jump to the start or end, move a word at a time, delete a word. The most useful one for this chapter’s habit is Alt-.Alt-., which inserts the last argument of the previous command. Preview with ls -d -- run2/*.tmp, then type rm -i -- and press Alt-.Alt-.: the same pattern appears, without retyping it.

Ctrl-CCtrl-C stops a running program; stopping and managing programs properly (processes, Ctrl-ZCtrl-Z, kill) is Chapter 7. Ctrl-DCtrl-D at an empty prompt closes the shell: on a cluster that logs you out, so press it with care.

On a Mac, the AltAlt keys need the Option key to act as Meta: in Terminal, Settings → Profiles → Keyboard → Use Option as Meta key; in iTerm2, Settings → Profiles → Keys, Left Option key: Esc+. VS Code’s built-in terminal may keep some shortcuts for itself.

You may also see !! (run the previous command again) and !$ (its last argument) in other people’s notes. They run without showing you the command first, so this book does not use them.

Where history lives. Bash keeps it in ~/.bash_history. Each shell normally loads that file when it starts and saves its own commands when it exits, so a terminal that is already open will not show commands typed in another one, even after that one is closed; a new terminal will. Anything you type on the command line is stored there, so never put a password or a token in a command (Chapter 4). How much history is kept is a setting in ~/.bashrc (Chapter 7).

TipSearch, don’t scroll

Ctrl-RCtrl-R finds an old command by any part of it, and Alt-.Alt-. inserts the last argument of the previous one.

Check yourself. Name two ways to rerun yesterday’s seqkit stats command without retyping it.

TipAnswer

5.12 Summary

  • Before a program starts, bash reads the line into words (respecting quotes), expands ~, wildcards, and $… where quoting allows, removes the quotes, and starts the command with the resulting arguments. Builtins such as cd are part of bash; most commands are programs.
  • Paths are absolute (from / or ~) or relative (from the current working directory, which pwd prints), even inside a script. . is here, .. is up one, cd - goes back, cd goes home.
  • cp and mv overwrite silently and rm has no undo: preview with ls -d --, then use -i. A relative link target is read from the link’s own folder; remove links with unlink, no trailing slash.
  • An unquoted wildcard is matched by bash, each name one argument; no match passes the pattern on unchanged. Quote names with spaces, and quote patterns meant for the program, such as find -name "*.fq.gz". Tab completes names and catches typos. Lowercase names without spaces or special characters need none of this care.
  • find <where> <tests> finds files by name, type, depth, size, and age. head, tail, less, and file look inside files without loading them whole; zless reads compressed text. Ctrl-RCtrl-R and the editing keys bring back and fix earlier commands.

The other three print nothing. Six working links that all point to the same file would pass the second check but not the first, which is why the first lists every target. Read a link to be sure it works: gunzip -c sample_C_R1.fastq.gz | head -n 4 in tidy/fastq prints the first record, @C.1.

The most common mistake is a relative target, such as ln -s run1/sample_A_R1.fastq.gz ~/bioinf-computing-ch05/tidy/fastq/ run from share: the link stores run1/…, which is read from tidy/fastq/, and the second check lists it as broken. Remove it with unlink and make it again with the absolute path.
