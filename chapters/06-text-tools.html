6  Text tools and pipes

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Connect commands with pipes, and send output to a file with >, >>, and tee, without overwriting an input.
  2. Keep results (standard output) and messages (standard error) apart, and capture or discard each on purpose.
  3. Count, sort, and summarise columns with cut, sort, uniq -c, and wc, and find lines with grep.
  4. Write a basic regular expression and use it in grep and sed, and select and compute on fields with awk.
  5. Read and write gzipped files through a pipe, and say when a format-aware tool is safer than a text tool.

6.1 What this chapter does

Most bioinformatics files are plain text with one record per line: sample sheets, annotation (GTF), tables of counts. FASTQ is text too, with one read per four lines in the book’s files. So a dozen small tools, each doing one job, answer most quick questions about these files when you join them with |: how many reads, how long, how many of each kind, which lines match. That is the whole “Unix philosophy” this chapter needs: small tools, joined together.

You have run pipes already. In Chapter 1 you typed gunzip -c … | wc -l and wrote a result with >; Chapter 3’s script ends in 2>&1 | tee "$log"; Chapter 5 used history | tail. This chapter explains each piece, so you can change those commands and write your own.

Commands run on your laptop, from the project folder. You only read the project’s files here. Everything you write goes to a scratch folder, ~/bioinf-computing-ch06, never into data/; the one exception is your notes in NOTEBOOK.md, as in earlier chapters. Make the scratch folder and go to the project:

Terminal (laptop)
mkdir -p ~/bioinf-computing-ch06
cd ~/bioinf-computing

Stay in ~/bioinf-computing for the whole chapter: pixi run finds the book’s environment from there, and the commands use paths such as data/raw/… that start from it. Every file the chapter writes is named with its full scratch path, ~/bioinf-computing-ch06/….

The outputs shown were captured with GNU grep 3.12, GNU sed 4.10, GNU Awk 5.4.1, GNU coreutils 9.11, GNU gzip 1.15, and seqkit 2.14.0, in the en_US.UTF-8 locale. Other versions give the same results except where a block says otherwise.

6.2 Pipes

Rerun two commands from Chapter 1, this time on the project’s copy of the file:

Terminal (laptop)
gunzip -c data/raw/SRR6357070_1.fastq.gz | head -n 8
gunzip -c data/raw/SRR6357070_1.fastq.gz | wc -l
@SRR6357070.25017281 25017281/1 kraken:taxid|4932
CCTGAATCGAGAAGGAGGTGTCCAGGGAGTTCATCATCAGAATGATTAGTATGATTTACTGTAGATTCAGTAAGTTTCTGGCCTAAGATGAAGGTCGTGCT
+
BBBBBFFFFFFFBFFFFFFFFFFFFFFFFFFFFFFFFFFFFBFFFBFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFBFFBFFFFFFF
@SRR6357070.6710070 6710070/1 kraken:taxid|4932
GTCAGATTGGAAGTCATGGTCAGATTCTATGTTAAGATCATCGGATTGTTGGATCTCATTTGACGCAATGAACGATTGATATGAAGCAGTTAAACGGTTTA
+
BBBBBFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFB
200000

Take the pipe apart. gunzip -c on its own decompresses the file and prints all 200,000 lines to the screen: do not run it alone, or you will watch reads scroll past for a while (stop it with Ctrl-CCtrl-C). head -n 8 on its own, with no file name, waits for you to type lines; press Ctrl-CCtrl-C to get the prompt back (stopping programs properly is Chapter 7). Joined by |, the first program’s output becomes the second one’s input, and you see only what you asked for.

Now name it. Every program has one standard input (stdin) and one standard output (stdout). By default stdin is your keyboard and stdout is your screen. The pipe | connects the stdout of the program on its left to the stdin of the program on its right. No file is written in between, and both programs run at the same time: head starts printing while gunzip is still working.

A pipe saves you an intermediate file, not all memory or disk use. sort, for example, must read all its input before it can print the first line, and for big inputs it writes temporary files of its own (where, on a cluster, is Chapter 10).

Programs that read stdin when you give them no file name are called filters: head, wc, sort, cut, grep, sed, awk, and gzip all are. That is what [FILE]... meant in the usage line of gzip in Chapter 4: with no file, it reads stdin.

Build a pipeline one step at a time. Ask a real question: how long are the reads? Start with the sequence lines, which in this file are line 2 of every 4, and look at the result before adding the next step:

Terminal (laptop)
gunzip -c data/raw/SRR6357070_1.fastq.gz | awk 'NR % 4 == 2' | head -n 3
CCTGAATCGAGAAGGAGGTGTCCAGGGAGTTCATCATCAGAATGATTAGTATGATTTACTGTAGATTCAGTAAGTTTCTGGCCTAAGATGAAGGTCGTGCT
GTCAGATTGGAAGTCATGGTCAGATTCTATGTTAAGATCATCGGATTGTTGGATCTCATTTGACGCAATGAACGATTGATATGAAGCAGTTAAACGGTTTA
GGAATAGTATATGTTGAGCAAGTGTGTTGATGTAGTATAGTAAGTCAAATCTAAATTTATATCCAACATATGAAGCTAGACCAATCAACTTTTGCATTTCA

Sequences only. Now print each length, sort the lengths, and count each value:

Terminal (laptop)
gunzip -c data/raw/SRR6357070_1.fastq.gz \
  | awk 'NR % 4 == 2 {print length($0)}' \
  | sort \
  | uniq -c
  50000 101

Every one of the 50,000 reads is 101 bases long. A long pipeline can be broken over lines with \ at the end of each line, one step per line, as here; it is still one command. Figure 6.1 shows what each step passes on, on a toy file of three reads.

awk 'NR % 4 == 2' means “print line 2, 6, 10, …”: NR is the line number and % the remainder after division. Section 6.8 explains awk. For now, note the assumption: this works because this file has exactly four lines per read, as you checked in Chapter 1. FASTQ in general does not promise that (Chapter 15), which is why format-aware tools exist (Section 6.10).

Two more things are worth knowing now. First, head stops reading after 8 lines, so gunzip is stopped too, before it reaches the end of the file. That is normal. Bash records each program’s exit status in the array PIPESTATUS:

Terminal (laptop)
gunzip -c data/raw/SRR6357070_1.fastq.gz | head -n 8 > /dev/null
echo "${PIPESTATUS[@]}"
141 0

141 means gunzip was stopped because nobody was reading any more; 0 is head’s success. (> /dev/null throws the output away; Section 6.4.) The exact number can vary with the program and the timing. It matters in scripts that stop on any error (set -o pipefail, Chapter 8). Second, because it stops early, gunzip -c … | head says nothing about whether the rest of the file is intact. Checking the whole file is gzip -t, from Chapter 1.

ImportantKey idea

A pipe | joins one program’s standard output to the next program’s standard input. Build pipelines one step at a time, and look at the output after each step before adding the next.

Check yourself. What does gunzip -c data/raw/SRR6357070_1.fastq.gz | head -n 4 | wc -l print?

TipAnswer

4. wc counts only the four lines head passed on; it never sees the rest of the file.

6.3 Redirection and the > trap

Chapter 1 saved a read count with > and added the second file’s count with >>. Do the same into the scratch folder, running the > line twice:

Terminal (laptop)
echo "SRR6357070_1 reads: $(( $(gunzip -c data/raw/SRR6357070_1.fastq.gz | wc -l) / 4 ))" > ~/bioinf-computing-ch06/fastq_summary.txt
echo "SRR6357070_1 reads: $(( $(gunzip -c data/raw/SRR6357070_1.fastq.gz | wc -l) / 4 ))" > ~/bioinf-computing-ch06/fastq_summary.txt
cat ~/bioinf-computing-ch06/fastq_summary.txt
SRR6357070_1 reads: 50000

One line: the second > replaced the first. Now the R2 line, with >>, also twice:

Terminal (laptop)
echo "SRR6357070_2 reads: $(( $(gunzip -c data/raw/SRR6357070_2.fastq.gz | wc -l) / 4 ))" >> ~/bioinf-computing-ch06/fastq_summary.txt
echo "SRR6357070_2 reads: $(( $(gunzip -c data/raw/SRR6357070_2.fastq.gz | wc -l) / 4 ))" >> ~/bioinf-computing-ch06/fastq_summary.txt
cat ~/bioinf-computing-ch06/fastq_summary.txt
SRR6357070_1 reads: 50000
SRR6357070_2 reads: 50000
SRR6357070_2 reads: 50000

>> adds to the end every time, so the R2 line is there twice. Rerunning a command that appends is a common way to get duplicated rows. > replaces a file’s contents; >> appends. Both create the file if it does not exist.

< goes the other way: it connects a file to a program’s stdin.

Terminal (laptop)
wc -l ~/bioinf-computing-ch06/fastq_summary.txt
wc -l < ~/bioinf-computing-ch06/fastq_summary.txt
3 /home/you/bioinf-computing-ch06/fastq_summary.txt
3

Given a file name, wc prints the name too; reading stdin, it has no name to print. That makes < handy when you want only the number.

6.3.1 The trap: cmd file > file

Make a three-line toy file and try to sort it “in place”:

Terminal (laptop)
printf 'b\na\nc\n' > ~/bioinf-computing-ch06/toy.txt
cat ~/bioinf-computing-ch06/toy.txt
sort ~/bioinf-computing-ch06/toy.txt > ~/bioinf-computing-ch06/toy.txt
wc -c ~/bioinf-computing-ch06/toy.txt
b
a
c
0 /home/you/bioinf-computing-ch06/toy.txt

Zero bytes: the file is empty, with no error and no warning. The reason is the order of events (Figure 6.2). Bash sets up the redirection before it starts the program, and setting up > opens the file for writing, which empties it. Only then does sort start, read the now empty toy.txt, and write nothing. The same happens with grep, cut, awk, and any other command whose input and > output are the same file.

The fix is the route in the figure: write to a new name, check it, then move it into place.

Terminal (laptop)
printf 'b\na\nc\n' > ~/bioinf-computing-ch06/toy.txt
sort ~/bioinf-computing-ch06/toy.txt > ~/bioinf-computing-ch06/toy.sorted.txt
cat ~/bioinf-computing-ch06/toy.sorted.txt
mv ~/bioinf-computing-ch06/toy.sorted.txt ~/bioinf-computing-ch06/toy.txt
a
b
c

This is exactly what Chapter 3’s script does: seqkit writes results/read_counts.tsv.tmp, and only after that succeeds does mv put it in place of read_counts.tsv. Now you can see why.

WarningPitfall: cmd file > file empties the file

The shell empties the output file before the command reads it. Write to a new name, check the result, then mv it over the original.

CautionMisconception: “sort data.txt > data.txt sorts the file in place”

Reality. The shell empties data.txt before sort starts, so you are left with an empty file. Redirection never edits a file in place.

A safety net: noclobber. Chapter 5 showed cp -n, which refuses to overwrite. Bash has the same idea for >. Try it inside ( … ), which runs the commands in a separate copy of the shell, so the setting goes away afterwards:

Terminal (laptop)
( set -o noclobber; echo x > ~/bioinf-computing-ch06/toy.txt )
echo $?
bash: /home/you/bioinf-computing-ch06/toy.txt: cannot overwrite existing file
1

With noclobber on, > refuses to replace an existing file, and >| forces it. It guards > only: >>, tee, cp, mv, and sed -i still overwrite. You could turn it on for good in your ~/.bashrc (Chapter 7), but this book does not, because later chapters overwrite files on purpose. The habits that protect you are the .tmp-then-mv route and Chapter 3’s read-only data/raw/:

Terminal (laptop)
echo test > data/raw/notes.txt
bash: data/raw/notes.txt: Permission denied

The same message stops sort data/raw/SRR6357070_1.fastq.gz > data/raw/SRR6357070_1.fastq.gz before it can empty the file. (What permissions are is Chapter 7.) Note the two quieter dangers of >: on a mistyped name it silently makes a new file, and on the right name it silently replaces the old contents.

6.3.2 tee: save and see

Sometimes you want a result in a file and on the screen. tee copies its stdin to a file and to its stdout:

Terminal (laptop)
pixi run seqkit stats -T \
  data/raw/SRR6357070_1.fastq.gz \
  data/raw/SRR6357070_2.fastq.gz \
  | tee ~/bioinf-computing-ch06/counts.tsv \
  | cut -f1,4
file    num_seqs
data/raw/SRR6357070_1.fastq.gz  50000
data/raw/SRR6357070_2.fastq.gz  50000

The full eight-column table went into counts.tsv, and the screen shows only columns 1 and 4 (cut, Section 6.5). -T makes seqkit print a tab-separated table, which cut needs; seqkit’s default table is laid out for people to read. You will also see a processed files line, which the next section explains. tee -a appends instead of replacing; Chapter 3’s script used tee "$log" to save its messages while showing them.

Check yourself. You run grep -v '^#' notes.txt > notes.txt. What is in notes.txt now?

TipAnswer

Nothing. The shell emptied notes.txt before grep started, so grep read an empty file. Write to notes.clean.txt, check it, then mv.

6.4 Standard output and standard error

Send the seqkit table into a file:

Terminal (laptop)
pixi run seqkit stats -T data/raw/SRR6357070_1.fastq.gz \
  data/raw/SRR6357070_2.fastq.gz > ~/bioinf-computing-ch06/counts.tsv
processed files:  2 / 2 [======] ETA: 0s. done

The table went into counts.tsv, but a line still appeared on the screen. If > sends “the output” to a file, where did this line come from?

Two output streams. Every program has a second output, standard error (stderr). By convention, programs write their results to stdout and their messages, progress, warnings, and errors to stderr. Both go to your terminal by default, so they look the same until you redirect one of them (Figure 6.3). > and | carry stdout only; stderr still reaches the screen. seqkit’s progress line is on stderr, which is why it stayed. (On screen it updates itself in place; saved to a file, it shows the cursor codes it uses for that. Chapter 3’s script runs seqkit stats --quiet, which turns the line off.)

To send stderr somewhere, put its number in front of >. Stdin is stream 0, stdout 1, and stderr 2, so 2> redirects stderr. Go back to Chapter 4’s truncated file. Make a copy in the scratch folder and run seqkit on it, with each stream to its own file:

Terminal (laptop)
head -c 1000000 data/raw/SRR6357070_1.fastq.gz > ~/bioinf-computing-ch06/broken.fastq.gz
pixi run seqkit stats -T ~/bioinf-computing-ch06/broken.fastq.gz \
  > ~/bioinf-computing-ch06/out.tsv \
  2> ~/bioinf-computing-ch06/err.txt
cat ~/bioinf-computing-ch06/out.tsv
cat ~/bioinf-computing-ch06/err.txt
file    format  type    num_seqs    sum_len min_len avg_len max_len
[ERRO] /home/you/bioinf-computing-ch06/broken.fastq.gz: unexpected EOF
[ERRO]

The header row (a result) is in out.tsv; the error is in err.txt. Nothing reached the screen. cat shows [ERRO] in red, as seqkit printed it. cat -A, which shows every invisible character, reveals how:

Terminal (laptop)
cat -A ~/bioinf-computing-ch06/err.txt
^[[31m[ERRO]^[[0m /home/you/bioinf-computing-ch06/broken.fastq.gz: unexpected EOF$
^[[31m[ERRO]^[[0m $

^[[31m and ^[[0m are colour codes: “red on”, “colour off”. $ marks each line’s end. Colour codes end up in log files this way; they are harmless, but they are why a log can look odd in an editor. (cat -A returns in Section 6.5 for tabs, and Chapter 7 uses it for Windows line endings.)

Both streams into one file. 2>&1 means “send stderr to wherever stdout is going now”. So the order matters:

Terminal (laptop)
pixi run seqkit stats -T ~/bioinf-computing-ch06/broken.fastq.gz \
  > ~/bioinf-computing-ch06/both.txt 2>&1

puts both streams in both.txt. Written the other way round, 2>&1 > both.txt, stderr is pointed at the screen (where stdout was at that moment) and only stdout goes to the file. Bash’s shorthand &> does the first version. Use these for logs, never for results: a results table with error lines in it breaks the next tool that reads it. Chapter 3’s script wrapped its commands in { … }, then sent 2>&1 | tee "$log", so its log keeps the messages from both streams, while the results went to their own file with >.

/dev/null is a special file that discards whatever is written to it. 2> /dev/null hides messages. Use it only for messages you have read and know you do not need, such as seqkit’s progress line; never to make a screen of errors look clean.

The pipe carries stdout only. Count the lines of the broken file:

Terminal (laptop)
gunzip -c ~/bioinf-computing-ch06/broken.fastq.gz | wc -l
echo $?

gzip: /home/you/bioinf-computing-ch06/broken.fastq.gz: unexpected end of file
89515
0

Read this carefully. Decompression failed partway, after producing some text. The error went to stderr, around the pipe, to your screen. wc successfully counted the text it received: 89,515 lines. That count is incomplete and cannot be used as a read count. And echo $? says 0, because a pipeline’s exit status is the status of its last command, wc, which did its job. "${PIPESTATUS[@]}" here would show 1 0: gunzip failed, wc succeeded. (The exact count depends on the gzip version: Apple’s gzip on a Mac stopped at 89,253. Either way, it is partial.)

Do not try to spot damage by checking whether a line count divides by 4: another cut could land on a multiple of 4 and still be wrong. Know your expected count (50,000 reads here), and read the messages. set -o pipefail (Chapter 8) makes a pipeline fail when any stage reports failure, but it cannot help when a tool reports success despite an error, as seqkit 2.14.0 did in Chapter 4. That is why the result checks from Chapter 4 still matter.

ImportantKey idea

By convention, results go to stdout and messages to stderr. > and | carry only stdout, so errors still reach the screen, and a pipeline can “succeed” on broken input. This is a convention tools follow, not a rule the shell enforces: some tools mix the two or write their own log files.

Check yourself. A command prints a table and some warnings. You want the table in out.tsv and the warnings in run.log. Write the redirection. And after seqkit stats … > counts.tsv, why was a progress line still on the screen?

TipAnswer

cmd > out.tsv 2> run.log. The progress line is on stderr, and > redirects only stdout.

6.5 Counting and summarising: wc, cut, sort, uniq

Start with a table small enough to check by eye: the practice sample table from Chapter 5. If you built Chapter 5’s practice folder, it is ~/bioinf-computing-ch05/share/meta/samples.tsv. Either way, make the chapter’s own copy with this block (the same lines Chapter 5 used; the list and printf are explained in Chapter 8):

Terminal (laptop)
rows=(sample run_folder condition reads
  sample_C "Run 3 final" treated 12
  sample_A run1 control 9
  sample_B run2 control 30
  sample_E run5 treated 105
  sample_B run2 control 30
  sample_D run4 control 8)
printf '%s\t%s\t%s\t%s\n' "${rows[@]}" > ~/bioinf-computing-ch06/samples.tsv
md5sum ~/bioinf-computing-ch06/samples.tsv
971d8f742cb76a8d181d3bdc3dcbceaa  /home/you/bioinf-computing-ch06/samples.tsv

If you have Chapter 5’s file, md5sum on it gives the same checksum. From here on the chapter uses the copy in ~/bioinf-computing-ch06. (It is not the project’s data/meta/samples.tsv, which has different columns.) Look at it:

Terminal (laptop)
cat ~/bioinf-computing-ch06/samples.tsv
wc -l ~/bioinf-computing-ch06/samples.tsv
cat -A ~/bioinf-computing-ch06/samples.tsv | head -n 3
sample  run_folder  condition   reads
sample_C    Run 3 final treated 12
sample_A    run1    control 9
sample_B    run2    control 30
sample_E    run5    treated 105
sample_B    run2    control 30
sample_D    run4    control 8
7 /home/you/bioinf-computing-ch06/samples.tsv
sample^Irun_folder^Icondition^Ireads$
sample_C^IRun 3 final^Itreated^I12$
sample_A^Irun1^Icontrol^I9$

A header and six rows, separated by tabs (cat -A shows each tab as ^I). By eye: sample_B is listed twice, on rows 3 and 5. Can the tools find that?

uniq only merges neighbours. cut -f1 takes column 1; uniq -c counts repeated lines:

Terminal (laptop)
cut -f1 ~/bioinf-computing-ch06/samples.tsv | uniq -c
      1 sample
      1 sample_C
      1 sample_A
      1 sample_B
      1 sample_E
      1 sample_B
      1 sample_D

sample_B appears twice, each with count 1. uniq compares each line only with the line before it, and the two sample_B lines are not next to each other. Sort first, so equal values become neighbours:

Terminal (laptop)
cut -f1 ~/bioinf-computing-ch06/samples.tsv | sort | uniq -c
cut -f1 ~/bioinf-computing-ch06/samples.tsv | sort | uniq -d
      1 sample
      1 sample_A
      2 sample_B
      1 sample_C
      1 sample_D
      1 sample_E
sample_B

2 sample_B. uniq -d prints only the lines that occur more than once. sort | uniq -c is the habit: it counts equal values wherever they sit in the file.

CautionMisconception: “uniq removes or counts all duplicate lines”

Reality. uniq only merges identical lines that are next to each other. Sort first: sort | uniq -c.

Skip the header. Count the conditions:

Terminal (laptop)
cut -f3 ~/bioinf-computing-ch06/samples.tsv | sort | uniq -c
tail -n +2 ~/bioinf-computing-ch06/samples.tsv | cut -f3 | sort | uniq -c
      1 condition
      4 control
      2 treated
      4 control
      2 treated

The first version counted the header as a value. tail -n +2 prints from line 2 onwards, which drops it. (tail -n 2, without the +, would print the last two lines.)

Numbers sort as text. Sort the rows by the reads column, as text and then as numbers:

Terminal (laptop)
tail -n +2 ~/bioinf-computing-ch06/samples.tsv | sort -t$'\t' -k4,4
tail -n +2 ~/bioinf-computing-ch06/samples.tsv | sort -t$'\t' -k4,4n
sample_E    run5    treated 105
sample_C    Run 3 final treated 12
sample_B    run2    control 30
sample_B    run2    control 30
sample_D    run4    control 8
sample_A    run1    control 9
sample_D    run4    control 8
sample_A    run1    control 9
sample_C    Run 3 final treated 12
sample_B    run2    control 30
sample_B    run2    control 30
sample_E    run5    treated 105

As text, 105 comes first, because sort compares character by character and 1 comes before 3, 8, and 9. With n, the column is compared as numbers: 8, 9, 12, 30, 30, 105. The pieces: -t$'\t' says the fields are separated by tabs ($'\t' is how you type a tab character in bash); -k4,4 sorts on field 4 only, from field 4 to field 4; the n after it makes that key numeric.

The duplicate matters. sort -u keeps one copy of each identical line:

Terminal (laptop)
tail -n +2 ~/bioinf-computing-ch06/samples.tsv | sort -u
sample_A    run1    control 9
sample_B    run2    control 30
sample_C    Run 3 final treated 12
sample_D    run4    control 8
sample_E    run5    treated 105

Five samples. The header was removed with tail -n +2 before sorting, so it cannot end up among the data. The reads column adds up to 194 with the duplicate and 164 without it (you will compute both with awk in Section 6.8): a duplicated metadata row inflates totals silently. sort -u removes only rows that are identical in every column. Two rows with the same sample name and different values are a conflict to resolve, not a duplicate to drop (Chapter 14). Note also that sample_D and sample_E have no read files in Chapter 5’s practice folder: a sample table and the files on disk can disagree, which Chapter 14 checks properly.

6.5.1 The real sample sheet

Now name the parts. Most characters match themselves (literals). A few have special meanings (Table 6.4):

  • . matches any one character; \. matches a real dot. The backslash turns a special character back into a literal.
  • [0-9] matches one character from a class, here any digit; [12] matches 1 or 2; [^ACGT] matches any character except those listed.
  • * means “zero or more of the item before it”, + “one or more”, ? “zero or one”, and {10,} “10 or more”.
  • ^ and $ anchor the match to the start and end of the line.
  • ( ) groups, and | means “or”: ^(WT|RAP1_IAA) matches lines that start with either.

Basic and extended syntax. grep and sed use basic regular expressions by default, where +, ?, { }, ( ), and | are ordinary characters unless you put a backslash before them. grep -E, sed -E, and awk use extended syntax, where they are special without one. So the same pattern behaves differently:

Terminal (laptop)
grep -c 'SRR[0-9]+_' data/meta/samplesheet_upstream.csv
grep -Ec 'SRR[0-9]+_' data/meta/samplesheet_upstream.csv
0
7

In basic syntax, + was a literal plus sign, and no line contains one. This book uses -E whenever a pattern needs +, ?, |, or groups. (GNU grep -P adds Perl-style patterns; you will meet it in other people’s commands.) Always put a regex in single quotes, so bash does not treat *, ?, [ ], or $ as its own special characters first.

6.7.2 Globs are not regular expressions

Chapter 5 promised this. A wildcard (glob) and a regex can look alike and mean different things:

Terminal (laptop)
grep -c '*.fastq.gz' data/meta/samplesheet_upstream.csv
grep -c '.*\.fastq\.gz' data/meta/samplesheet_upstream.csv
grep -o '[^/]*\.fastq\.gz' data/meta/samplesheet_upstream.csv | head -n 3
0
7
SRR6357070_1.fastq.gz
SRR6357070_2.fastq.gz
SRR6357071_1.fastq.gz

*.fastq.gz as a glob means “any name ending in .fastq.gz”. As a regex it means something else: a * at the very start has nothing before it to repeat, so grep reads it as a literal *, then any character, then fastq, any character, gz. No line contains a *, so 0. In a regex, “anything” is .* and a real dot is \.: .*\.fastq\.gz matches the 7 data rows. The third line prints the file names themselves: [^/]* is “any run of characters that are not /”, so the match starts after the last / of each URL. (In a regex, “ends in .fastq.gz” would be \.fastq\.gz$; no line of this sheet ends that way, because each row ends with its strandedness.)

CautionMisconception: “* means the same in grep as in ls”

Reality. In a glob, * is “any characters”. In a regex, * is “zero or more of the previous character”, and . is “any character”. The regex for “anything” is .*.

The same regexes in R and Python. Simple patterns like ^SRR[0-9]+ work the same in R, grepl("^SRR[0-9]+", x) (base R uses extended syntax), and in Python, re.search(r"^SRR[0-9]+", s). But they are separate engines, not one universal regex: base R, R’s stringr package, Python’s re, JavaScript, and GNU grep differ in details such as backslashes (R needs "\\." inside a string; Python’s raw strings r"\." avoid that) and which alternative wins in a|ab. Chapter 12 and Chapter 13 use them. One warning for all languages: regexes for structured formats, such as quoted CSV fields or GTF attributes, get fragile fast; use a parser for those.

Chromosome names differ between sources: chr1 in one, 1 in another (Chapter 15). Make a two-line toy file in the BED format and strip the chr:

The family. gzip file compresses file into file.gz and removes the original; gunzip file.gz does the reverse. -c writes to stdout instead and leaves the input alone, which is what you want almost always. zcat file.gz is the same as gunzip -c file.gz in GNU gzip, and you will see it in other people’s scripts. This book writes gunzip -c because the zcat built into macOS does not read .gz files:

zcat: can't stat: data/raw/SRR6357070_1.fastq.gz (data/raw/SRR6357070_1.fastq.gz.Z): No such file or directory

(It looks for a .Z file, an older format.) On Linux, zcat works the same as gunzip -c.

Rules for big files.

  • Do not decompress a large file to disk to read it: stream it with gunzip -c … |. A 10 GB .fastq.gz is 40 GB or more uncompressed.
  • Many tools read .gz directly, including seqkit and most aligners, so a decompressed copy is rarely needed.
  • Reading a 10 GB file through a pipe is real work: on a cluster, do it in a job, not on the login node (Chapter 10).
  • bgzip is a variant of gzip that allows jumping to a position inside the file; indexed genomics files use it (Chapter 17). pigz is a parallel gzip that uses several cores (Chapter 35).
WarningPitfall: decompressing to disk

gunzip big.fastq.gz writes the full uncompressed file and deletes the .gz. Stream instead with gunzip -c big.fastq.gz | …, or give the .gz file to a tool that reads it directly.

Check yourself. Why stream a 10 GB .fastq.gz with gunzip -c … | instead of running gunzip file.fastq.gz first?

TipAnswer

No 40 GB or larger uncompressed copy on disk or in your quota, and the file is read once instead of twice.

6.10 Text tools and format-aware tools

You did several jobs in this chapter with text tools. Each has a tool that understands the file format (Table 6.9).

The format-aware tool wins once files are real: records that span several lines (every NR % 4, head -n 400, and 1~4 in this chapter assumed four lines per read), comment and header lines, quoted fields, binary formats such as BAM, variants of compression, and the @ trap. Text tools stay the best way to look at a file and to check a result quickly: count lines, find the odd one, compare two columns. Part IV opens with the same principle.

ImportantKey idea

Use text tools to look and to check; use format-aware tools to process.

6.11 Summary

  • A pipe | joins one program’s stdout to the next one’s stdin, with no file in between. Build pipelines one step at a time and look at each step’s output.
  • > replaces a file and >> appends; the shell empties a > target before the command runs, so never redirect onto your input: write a new file, check it, mv it. tee saves and shows at once.
  • Results go to stdout and messages to stderr, by convention. 2>, 2>&1, and /dev/null route stderr on purpose; a pipeline’s status is its last command’s, so read the messages and check counts against what you expect.
  • cut, sort, uniq -c, and wc count and summarise columns; sort before uniq, use sort -n for numbers and LC_ALL=C for a reproducible order. grep finds lines and -c counts them.
  • A regular expression describes text (., [ ], *, +, ^, $, \); it is not a glob. sed 's/…/…/' substitutes; awk -F'\t' selects fields and computes. Stream .gz files with gunzip -c, and use format-aware tools to process real FASTQ, BAM, and annotation.
