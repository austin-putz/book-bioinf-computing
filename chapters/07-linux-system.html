7  The Linux system

Core. Work through it, with the exercises.

NoteLearning goals

By the end of this chapter you should be able to:

  1. Read a permission string such as -rw-r--r-- or drwxr-x---, say who may read, change, or enter, and change it with chmod.
  2. Make a script run as a command with a shebang line and the executable bit, and explain Permission denied and command not found when it does not.
  3. Explain how the shell finds a command through PATH, find which copy runs with type -a, and set environment variables for one command, one session, or every new terminal.
  4. Find, stop, and end your own processes with Ctrl-CCtrl-C, ps, top, and kill, and find what is filling a disk with df and du.
  5. Recognise when a command depends on GNU (Linux) or BSD (macOS) tools, and detect and fix Windows (CRLF) line endings.

7.1 What this chapter does

Part I asked you to run several “system” commands on trust. In Chapter 1 you pasted a block into ~/.bash_profile (Mac) that put the GNU tools first on your PATH. In 1 the pixi installer added a line to ~/.bashrc, bare seqkit said command not found while pixi run seqkit worked, and export EDITOR=nano lasted only until the terminal closed. In Chapter 3, chmod a-w made the raw reads read-only, yet rm -f could still delete a read-only file in a writable folder. This chapter explains each of these, so that when one goes wrong you know where to look.

The chapter has two halves, and it works well as two sittings. The first is about who may do what and how commands are found: permissions, making a script run, PATH, environment variables, and the startup files that set them. The second is about the running system: processes, disk space, the differences between Linux and macOS tools, and Windows line endings.

Commands run on your laptop. Everything that changes files happens in a scratch folder, ~/bioinf-computing-ch07; in the project, ~/bioinf-computing, you only look (ls -l, du). Two things you will deliberately change outside scratch: a few lines in your ~/.bashrc (Section 7.6, with a backup first) and your notes in NOTEBOOK.md. Make the scratch folder:

Terminal (laptop)
mkdir -p ~/bioinf-computing-ch07 && cd ~/bioinf-computing-ch07

Two sections and the first exercise also read the practice folder ~/bioinf-computing-ch05/share/ from Chapter 5, without changing it. If you do not have it, paste the setup block from Section 5.2 first.

The Linux outputs shown were captured on Ubuntu 24.04 (bash 5.2.21, GNU coreutils 9.4, grep 3.11, sed 4.9, file 5.45), on a machine named laptop with the user you; macOS outputs on macOS 15 with the Mac’s own tools, where the text says so. Ubuntu 26.04, which WSL installs in late 2026, replaces most GNU core tools with a rewrite called uutils (Section 7.9); where its output differs, the text says so. Process numbers, dates, and sizes on your machine will differ.

7.2 Who may do what: permissions

Every file and folder belongs to one user (its owner) and one group, and carries three sets of permissions. Start with who you are, then look at the raw reads you protected in Chapter 3:

Terminal (laptop)
whoami
id
cd ~/bioinf-computing
ls -ld data/raw
ls -l data/raw
you
uid=1000(you) gid=1000(you) groups=1000(you)
dr-xr-xr-x 2 you you 4096 Nov 17 11:22 data/raw
total 4372
-r--r--r-- 1 you you     112 Nov 17 11:22 checksums.md5
-r--r--r-- 1 you you 2239317 Nov 17 11:22 SRR6357070_1.fastq.gz
-r--r--r-- 1 you you 2232117 Nov 17 11:22 SRR6357070_2.fastq.gz

id gives your user, your main group, and every group you belong to (on your own laptop it may list more, such as sudo; on a cluster, your lab’s project groups). In ls -l, the two you columns are the owner and the group (Figure 5.4 in Chapter 5 named them). The first column is what this section explains.

Now name the parts (Figure 7.1). After the type letter (d folder, - file, l link) come three groups of three letters: for the user who owns it, for members of its group, and for other users. In each group, r is read, w is write, x is execute, and - means “not allowed”.

On a file the letters mean what you would guess: read its contents, change its contents, run it as a program. On a folder they mean something else, and that is where most surprises come from. Try it in scratch, on a folder d holding one readable file, with the owner’s x removed:

Terminal (laptop)
mkdir -p ~/bioinf-computing-ch07/perm && cd ~/bioinf-computing-ch07/perm
mkdir d && echo hello > d/f
1chmod u-x d
ls -ld d
2\ls d
\ls -l d
cat d/f
cd d
3chmod u+x d
1
chmod changes permissions: u-x removes (-) execute (x) for the user (u). The full syntax follows below.
2
The backslash runs ls without any alias your system defines (Section 7.4); a colouring alias can change what ls tries to read.
3
Put x back, so the folder works again. 
drw-r-xr-x 2 you you 4096 Nov 17 14:02 d
f
ls: cannot access 'd/f': Permission denied
total 0
-????????? ? ? ? ?            ? f
cat: d/f: Permission denied
bash: cd: d: Permission denied

(Ubuntu 26.04’s ls shows the ? line without the cannot access message.) ls d still lists the name f: reading a folder means reading its list of names, and you kept r. Everything about the entry fails: ls -l cannot read its details (the question marks), cat cannot open it although the file itself is readable, and cd cannot go in. On a folder, x (often called search permission) is what lets you reach the entries and pass through to anything below. The reverse also holds: with x but no r, ls d says cannot open directory 'd', yet cat d/f works if you know the name. Table 7.1 collects the cases.

Two rules make the letters predictable:

  • The classes are chosen, not added up. If you own the file, only the user triplet counts. An owner without x is refused even when “other” has x.
  • You need x on every folder on the way. cat ~/a/b/c/file.txt needs x on a, b, and c as well as r on the file.

Deleting is a change to the folder. Now Chapter 3’s surprise has its explanation. Removing a file takes its name out of the folder’s list, so rm needs w and x on the folder; the file’s own permissions do not matter. Creating a new file is also a change to the folder. Changing an existing file is not:

Terminal (laptop)
mkdir locked && echo old > locked/data.txt
chmod a-w locked
echo new > locked/data.txt; cat locked/data.txt
echo x > locked/new.txt
rm locked/data.txt
chmod u+w locked
new
bash: locked/new.txt: Permission denied
rm: cannot remove 'locked/data.txt': Permission denied

The folder is read-only, yet data.txt was overwritten, because the file itself was still writable: only a new name or a removed name changes the folder. That is why Chapter 3 protected the files and the folder with chmod a-w data/raw/* data/raw. It also explains Chapter 6’s redirect into data/raw/: echo test > data/raw/notes.txt makes a new name, which the folder refuses; sort … > data/raw/SRR6357070_1.fastq.gz targets an existing file, which the file’s missing w refuses.

ImportantKey idea

On a folder, r lists the names, x lets you reach the entries, and w (with x) lets you add, remove, or rename them. A file’s own permissions do not protect it from deletion; its folder’s do.

These are the ordinary permissions on your own disk. On a cluster, two more things can explain a refusal the letters do not: access control lists (ACLs), which grant extra users or groups access, and storage mounted so that nothing on it may run as a program, which turns ./script.sh into Permission denied whatever its letters say. If the string looks right and you are still refused, ask the help desk (Chapter 4).

7.2.1 Changing permissions with chmod

chmod takes a change and one or more names. The symbolic form says who, how, and what:

  • who: u (user), g (group), o (other), a (all three);
  • how: + add, - remove, = set exactly;
  • what: r, w, x.

You have used it twice already: chmod a-w (remove write for all, Chapter 3) and chmod 700 ~/.ssh (1). The second is the octal form: one digit per class, each the sum of r = 4, w = 2, x = 1 (Figure 7.1). So 7 = rwx, 6 = rw-, 5 = r-x, 4 = r--, 0 = ---, and 700 means the owner may do everything and nobody else anything. GNU stat prints both forms:

Terminal (laptop)
touch notes.txt && mkdir private
1stat -c '%A %a %n' notes.txt private
chmod u+x notes.txt && ls -l notes.txt
chmod 644 notes.txt && ls -l notes.txt
chmod go-rx private && stat -c '%A %a %n' private
umask
1
-c gives a format: %A the string, %a the octal number, %n the name. (macOS’s own stat has different options: Section 7.9.) 
-rw-r--r-- 644 notes.txt
drwxr-xr-x 755 private
-rwxr--r-- 1 you you 0 Nov 17 14:04 notes.txt
-rw-r--r-- 1 you you 0 Nov 17 14:04 notes.txt
drwx------ 700 private
0022

A symbolic change modifies the current permissions (u+x added one letter to whatever was there); an octal number sets all nine at once. So the same chmod a-w gave 555 on Chapter 3’s folder and 444 on its files only because they started at 755 and 644. Why do new files start at 644 and folders at 755? Your umask, 0022, removes w for group and other from every new file and folder. Sites can set a different umask: Nova’s is 0002, which leaves w for the group, so new files start at 664 and folders at 775, and your lab can edit them. SCINet’s Ceres and Atlas set 0027, so new files start at 640 and folders at 750: your group can read them but not change them, and other users cannot see them. On a cluster that does this, a labmate who must edit your file in a shared project folder needs you to run chmod g+w on it (Table 7.2). Check yours with umask; you rarely need to change it.

There is no general “undo” for chmod: note the old mode first if you might want it back. Two more details for whole trees:

  • -R applies a change to a folder and everything inside it. chmod -R a+x folder makes every data file “executable” too (try it on a scratch folder and ls -l shows -rwxr-xr-x on plain files).
  • A capital X adds x only to folders and to files that are already executable for someone, and leaves ordinary data files alone. That is why g+rX in the table is safe on a tree of data.
WarningPitfall: chmod -R 777 is not a fix

777 lets every user on the machine change or delete your files. When you get Permission denied, read the permission string, find which letter is missing for whom, and add only that.

CautionMisconception: “When I get Permission denied, chmod 777 or sudo fixes it”

Reality. It hides which permission was missing and removes the protection for everyone. On a cluster you cannot use sudo at all. Read the string, then change one letter.

7.2.3 Groups and shared folders

On a cluster, a lab shares files through a Unix group: a project folder such as /project/<name> on SCINet or /work/<group> on Nova belongs to the lab’s group, and members get the group’s permissions (Appendix A has each site’s details). When a labmate cannot read your file, check two things: which group owns it (ls -l) and whether that group may read it (the middle triplet). id shows which groups you are in; chgrp <group> file changes a file’s group to one of yours.

Two special settings appear on shared folders. You will mostly meet them, not set them; the site usually does:

Setgid decides the group of a new file, not whether the group may read it: the new file’s permissions still come from your umask (and any default ACLs). If files you create in a project folder come out unreadable to your lab, check their group and permissions with ls -l and ask the help desk what the site expects.

Here is what this looks like on Nova, in a group folder and a lab folder inside it (names replaced by <group>, <lab>, and you):

ls -ld /work/<group> /work/<group>/<lab>
cd /work/<group>/<lab>
touch group_test && ls -l group_test
umask
drwxrws--T. 43 root its-hpc-nova-<group> 44 Nov 18 12:11 /work/<group>
drwxrwsr-x. 16 you  its-hpc-nova-<group> 16 Nov 16 18:24 /work/<group>/<lab>
-rw-rw-r--. 1 you its-hpc-nova-<group> 0 Nov 20 12:34 group_test
0002

Both folders have the setgid s, so the new file belongs to the lab’s group, not to your main group (domain users on Nova). It is rw-rw-r-- because Nova’s umask is 0002, so your labmates can edit it. The group folder also has a capital T. That is the sticky bit on a folder that others can’t enter (no x for other); a lowercase t means the sticky bit plus x. The . after each permission string means the file has an SELinux security label, which you can ignore. Delete the test file with rm group_test when you are done.

SCINet’s Ceres follows the same pattern in /project/<name>, owned by root and the group proj-<name>, with two differences. Your main group there is a personal group named after you, so without the setgid s your files would belong to a group nobody else is in. And the umask is 0027, so the same touch gives -rw-r-----, and a folder you make gives drwxr-s---: your lab can read and enter, but not edit or add files, until you run chmod g+w on them. Atlas, SCINet’s other cluster, gives the same results; its project folder is drwxrws---, without the sticky T and without the SELinux ..

The GNU coreutils manual describes all of this in full.

Administrators and sudo. On your laptop, sudo runs one command as the administrator (root), for changes to the system itself, such as installing packages with apt. Never use it to fix permissions on your own files: files created by root in your home folder are a new problem. On a cluster you are not an administrator and this book never needs sudo: the book environment and later ones install into your own folders (1, Chapter 23).

Check yourself. (a) A folder is drwxr-xr-x and owned by you; a file in it is -r--r--r--. Can you delete the file? (b) What does chmod 640 notes.txt give, as a string? (c) A folder you own is drw-r--r--. Can you cat a readable file inside it?

TipAnswer
  1. Yes. Deleting changes the folder, where you have w and x; the file’s own permissions do not matter. rm asks first because the file is read-only; rm -f does not ask. (b) -rw-r-----: you read and write, the group reads, others get nothing. (c) No. Without x on the folder you can list the names but not reach the entries.

7.3 Making a script run

Chapter 3 ran its script as pixi run bash src/01_count_reads.sh: bash read the file. Scripts can also run as commands of their own. Make a one-line script in scratch (with nano or VS Code, or paste this) and try four ways to run it:

Terminal (laptop)
cd ~/bioinf-computing-ch07
1printf 'echo "hello from $0"\n' > hello.sh
bash hello.sh
./hello.sh
chmod u+x hello.sh
./hello.sh
hello.sh
1
$0 is the name the script was started as (Chapter 8). 
hello from hello.sh
bash: ./hello.sh: Permission denied
hello from ./hello.sh
bash: hello.sh: command not found

The exit statuses join Chapter 4’s echo $?: 126 means “found but cannot run”, 127 “not found”. ./hello.sh works because . is the current folder, so ./hello.sh is a path, and a name with a / in it is run directly, with no search.

The shebang line. Add one line at the very top of the file:

hello.sh
#!/usr/bin/env bash
echo "hello from $0"

When a file with the x bit is run, the kernel reads its first line. If it starts with #! (said “shebang”), the rest names the program that should read the file, and the kernel starts that program with the file’s name (Figure 7.3). Without a shebang, bash happens to run the file as a bash script, but other programs that start it may not; always write one. It must be the very first line, starting at the first character.

This book’s scripts use #!/usr/bin/env bash, as Chapter 3’s script already does. env looks bash up on your PATH, so on a Mac it finds the current bash from Chapter 1 instead of Apple’s /bin/bash, which is version 3.2 from 2007 (/bin/bash --version on a Mac prints GNU bash, version 3.2.57). Inside pixi run or pixi shell it finds the environment’s programs the same way. R and Python scripts follow the same pattern, #!/usr/bin/env Rscript and #!/usr/bin/env python3 (Chapter 12, Chapter 13).

CautionMisconception: “To run a script I must type bash script.sh”

Reality. With a shebang line and the x bit, a script runs as ./script.sh, and by name alone once its folder is on PATH. bash script.sh ignores the shebang: bash plot.py tries to read Python as shell commands and fails.

ImportantKey idea

A command runs as a program when the shell can find it (a path, or a folder on PATH), the file has the x bit, and its first line names an interpreter that exists.

Check yourself. ./run.sh says Permission denied, but bash run.sh works. What is missing, and what is the fix?

TipAnswer

The x bit. bash run.sh only needs to read the file; ./run.sh needs permission to run it. chmod u+x run.sh.

7.4 How the shell finds a command: PATH

When you type a name without a /, such as ls or seqkit, bash looks for a program file with that name in a list of folders. The list is the variable PATH:

Terminal (laptop)
1echo "$PATH" | tr ':' '\n'
1
PATH is one line with folders separated by :; tr turns each : into a newline (Chapter 6). 
/home/you/.pixi/bin
/usr/local/sbin
/usr/local/bin
/usr/sbin
/usr/bin
/sbin
/bin

Bash searches these folders in order, top to bottom, and runs the first match. ~/.pixi/bin is first because 1’s pixi installer added it to the front. Your list will be longer or ordered differently: Ubuntu adds /usr/games and /snap/bin, and on a Mac after Chapter 1 the GNU folders come first.

Which copy runs? type -a asks bash for every match, in the order bash would use them:

Terminal (laptop)
type -a ls
type cd
ls is aliased to `ls --color=auto'
ls is /usr/bin/ls
ls is /bin/ls
cd is a shell builtin

Three kinds of answer appear here. An alias is a shortcut bash expands before anything else: on Ubuntu, and on Nova, typing ls really runs ls --color=auto, which colours the names. Then come the program files on PATH: two here, because current Ubuntu keeps /bin as another name for /usr/bin, so both entries reach the same file. And cd is a builtin, part of bash, with no file at all (Chapter 5). On a Mac after Chapter 1 the answer differs:

ls is /usr/local/opt/coreutils/libexec/gnubin/ls
ls is /bin/ls

The GNU ls comes first, then Apple’s own (/opt/homebrew/… on Apple silicon). That order is what Chapter 1’s gnubin lines arranged.

So the full order is: aliases, then functions (named groups of commands, Chapter 8), then builtins, then the folders of PATH. Changing PATH cannot override an alias or builtin of the same name. alias alone lists your aliases; a backslash (\ls) or command ls runs the program without the alias, as you did in Section 7.2.

The book’s environment. Now the explanation 1 promised. From the project folder:

Terminal (laptop)
cd ~/bioinf-computing
type -a seqkit
pixi run bash -c 'type -a seqkit; echo "$PATH" | tr ":" "\n" | head -n 3'
bash: type: seqkit: not found
seqkit is /home/you/bioinf-computing/.pixi/envs/default/bin/seqkit
/home/you/bioinf-computing/.pixi/envs/default/bin
/home/you/.pixi/bin
/usr/local/sbin

No folder on your PATH holds seqkit, hence Chapter 4’s command not found. pixi run starts one command with the environment’s bin folder put first on PATH, so the environment’s copy is found and wins over any other. pixi shell does the same for a whole new shell, until you type exit (Figure 7.4).

The wrong copy. If two copies are on PATH, the first wins, even if it is older. This is what Chapter 4 warned about: a bare seqkit might run some other installation, with a different version. Check with type -a seqkit and seqkit version; inside the book, pixi run makes the environment’s copy win. On a cluster, module load also works by changing PATH (Chapter 10), so a module loaded beside pixi shell can put a second copy in front. Exercise 3 sets up a fake seqkit to show this safely.

which seqkit is a common alternative, but it is a separate program, its versions behave differently, and its answer need not match what bash will run. Usually it knows nothing of your aliases; on Nova which ls shows the alias too, because there type which reports which is a function: the site wraps the real /usr/bin/which in a shell function that passes it your aliases and functions. Use bash’s own type -a. Table 7.5 collects the commands.

The last row: bash remembers where it found each command, so after you move or install a program, hash -r (or a new terminal) makes it look again.

Changing PATH. Put a folder of your own in front of the existing list:

Terminal (laptop)
export PATH="$HOME/bin:$PATH"

$PATH on the right is the old list, so this adds one folder and keeps the rest. It is the same shape as the gnubin line in Chapter 1’s ~/.bash_profile and the line the pixi installer added to ~/.bashrc. It lasts for this terminal only; Section 7.6 makes such lines permanent. Two mistakes to avoid:

  • Replacing instead of adding. PATH=~/bin leaves only one folder, and every ordinary command fails with command not found. Open a new terminal to recover, or run export PATH=/usr/bin:/bin to get the basics back.
  • Putting . (the current folder) on PATH. Then whatever folder you are in can supply a program called ls. Type ./script.sh instead.
ImportantKey idea

For a name without a /, bash checks aliases, functions, and builtins, then searches the PATH folders top to bottom and runs the first match. type -a shows every match in that order.

CautionMisconception: “Once I install a tool, it works in every terminal”

Reality. (From 1, now with the mechanism.) A tool runs by name only if its folder is on that shell’s PATH. The book environment’s folder is added by pixi run and pixi shell, for that command or shell only; a module’s by module load.

Check yourself. type -a samtools prints samtools is /home/you/bin/samtools, then samtools is /usr/bin/samtools. Which runs when you type samtools, and how would you run the other one?

TipAnswer

The first, ~/bin/samtools, because ~/bin comes earlier on PATH. Run the other by its path, /usr/bin/samtools.

7.5 Environment variables

PATH is one of many variables the shell keeps. Look at a few:

Terminal (laptop)
echo "$HOME"
echo "$USER"
echo "$SHELL"
/home/you
you
/bin/bash

env | sort | less lists the dozens of variables that every program started from this shell receives, one NAME=value per line (q quits). Now see the difference between a variable that stays in the shell and one that is passed on. bash -c '…' starts a second bash, a child of this one, that runs one line and exits:

Terminal (laptop)
x=1
bash -c 'echo "child sees x=[$x]"'
export x
bash -c 'echo "child sees x=[$x]"'
child sees x=[]
child sees x=[1]

Now name it. x=1 makes a shell variable, which lives only in this shell. export turns it into an environment variable, which is copied into every program this shell starts: scripts, R, Python, seqkit. Copies only go down, from parent to child. A script cannot change the variables of the shell that started it, which is why pixi shell has to start a new shell rather than change yours. A second terminal opened separately is not a child of the first, so it never sees an export you typed in the first. Once a variable is exported it stays exported: a later x=2 changes the value children see, without a second export. That is why PATH, already exported when your shell starts, can be changed with a plain assignment.

Two details. No spaces around =: x = 1 runs a command called x (bash: x: command not found); quoting and the rest are Chapter 8. And SHELL names your configured login shell, not necessarily the shell you are typing in; to check you are in bash, use Chapter 1’s echo "$BASH_VERSION".

A variable can last for one command, one terminal, or every new terminal (Table 7.6).

TipA setting for one command

Write the variable in front of the command, with no export: TMPDIR=~/bigtmp sort big.txt gives sort a different folder for its temporary files, for that run only.

Table 7.7 lists the variables you will meet in this book.

Your locale settings. Chapter 6 used LC_ALL=C sort to get the same sort order everywhere. The locale is the group of LANG and LC_* variables that sets language, sort order, and number format; locale prints yours:

Terminal (laptop)
locale | head -n 6
LANG=en_US.UTF-8
LANGUAGE=
LC_CTYPE="en_US.UTF-8"
LC_NUMERIC="en_US.UTF-8"
LC_TIME="en_US.UTF-8"
LC_COLLATE="en_US.UTF-8"

LC_COLLATE is the one that decides sort order; LC_ALL, if set, overrides all the others. This book leaves your default alone and sets LC_ALL=C in front of a single command when the order must be reproducible. A cluster may use a different default (often C or en_US.UTF-8), so check locale there too. Text encodings themselves are Chapter 36.

Check yourself. You run export THREADS=4 in one terminal, then open a second terminal and run echo "$THREADS". What prints, and what would make the setting reach every new terminal?

TipAnswer

An empty line. export reaches the shell it was typed in and the programs that shell starts; a separately opened terminal is not one of them. A line export THREADS=4 in ~/.bashrc reaches every new terminal.

The book’s setup. Login and non-login shells read different files, which would mean writing every setting twice. Instead, the login file reads ~/.bashrc:

7.6.1 Changing ~/.bashrc safely

Make 1’s EDITOR setting permanent. First a backup, with cp -n so that a second try never overwrites the first backup (Chapter 5; ignore the non-portable warning Ubuntu’s cp prints):

Terminal (laptop)

1echo 'export EDITOR=nano' >> ~/.bashrc
tail -n 2 ~/.bashrc
1
>> appends. A single > would replace your whole ~/.bashrc with this one line (Chapter 6).

Then open a new terminal and check with echo "$EDITOR". (To apply the file to the terminal you are in, source ~/.bashrc reads it again; a new terminal is the honest test.) Rules for every change:

  • Back up first, and keep one working terminal open while you test in a new one. If a broken file stops new terminals from working, bash --noprofile --norc starts a clean shell to fix it from, or restore the backup.
  • Nothing in ~/.bashrc should print text. A command run over SSH may read it (Table 7.8), and output there can break rsync and older scp (Chapter 9). Put anything that prints inside if [[ $- == *i* ]]; then … fi, which runs only in interactive shells.
  • On a cluster, keep the site’s lines, and do not load modules or start environments from startup files: they would change every terminal and every remote command without asking, and make a job’s software depend on your dotfiles (Chapter 10, Appendix A).
WarningPitfall: a .bashrc that prints text

Output from ~/.bashrc can break rsync and scp. Back up before editing, keep a working terminal open, and test in a new one.

Things worth putting there. A few settings earlier chapters pointed here:

Start a command that takes a while, and stop it:

Terminal (laptop)

sleep waits for the given number of seconds and does nothing else: a safe stand-in for a long analysis. Press Ctrl-CCtrl-C while it waits.

Then check its exit status with echo $?: 130, the number a command gets when Ctrl-CCtrl-C stops it. Now run it in the background by ending the line with &, so the prompt comes back at once, and look at what is running:

Terminal (laptop)

[1] 3219

[1] 3219 is the job number (1, for this terminal) and the process ID (PID, 3219, for the whole machine). jobs lists this terminal’s jobs; ps lists the processes started from this terminal: your shell, the sleep, and ps itself. kill %1 ended job 1; kill 3219 would have done the same by PID. (On a Mac, bash prints Terminated: 15.)

Now name it. A process is a running program, with a PID, an owner, and a parent: the process that started it, here your shell. Every program you have run, from ls to seqkit, ran as a process and ended. Your shell is a process too, and runs builtins such as cd and export inside itself, without starting a new one (Chapter 5). Figure 7.6 shows the states a process can be in, and how you move it between them.

A program in the foreground has your keyboard; one in the background runs while you type other commands. To stop a program, the shell sends it a signal (Table 7.9).

Ctrl-CCtrl-C and kill ask: a well-written tool deletes its half-written files and exits. kill -9 cannot be caught, so the program gets no chance to clean up: look for and delete partial output files afterwards. You can signal only your own processes.

Stopped is not ended. Ctrl-ZCtrl-Z pauses the foreground program and gives you the prompt back. It looks like a way out, but the program is still there:

Terminal (laptop)
sleep 600

Press Ctrl-ZCtrl-Z, then:

Terminal (laptop)

1ps -o pid,stat,rss,command
exit
1
-o chooses columns: stat the state (T stopped, S sleeping, R running), rss the memory it holds, in kB, command the command line. Linux also accepts cmd, but the Mac’s ps does not. 
^Z
[1]+  Stopped                 sleep 600
[1]+  Stopped                 sleep 600
    PID STAT   RSS COMMAND
   3217 S     4776 bash
   3221 T     1952 sleep 600
   3222 R+    4152 ps -o pid,stat,rss,command
exit
There are stopped jobs.

Bash refuses the first exit to warn you. (In a login shell, such as a WSL window or a Mac Terminal, exit prints logout first.) Resume the job with fg (foreground) or bg (background), or end it with kill %1. A large analysis stopped with Ctrl-ZCtrl-Z keeps all its memory until then.

WarningPitfall: Ctrl-ZCtrl-Z does not stop a program for good

It pauses it, still holding its memory. Use Ctrl-CCtrl-C to stop a command; if you pressed Ctrl-ZCtrl-Z, finish with fg or kill %1.

Some clusters switch Ctrl-ZCtrl-Z off (SCINet’s Ceres and Atlas leave it on). Press Ctrl-CCtrl-C instead, which still works there.

On a cluster. TipAnswer

These are the BSD versions of ls, cat, stat, and sed that come with macOS (captured on macOS 15 with /bin/bash 3.2 and the system’s own tools). They do not know --version, -A, or -c. BSD sed -i expects a suffix for a backup copy right after -i, so it took s/x/y/ as that suffix and the file name as the script: a confusing message about something you did not mean. With GNU tools first on PATH, the same commands work (ls --version prints ls (GNU coreutils) 9.11).

Now name it. The Linux systems you will use come with the GNU versions of the core tools this book uses: ls, cp, stat, sed, grep, find, awk, sort. (Not every Linux tool is GNU: ps and top usually come from a package called procps.) macOS comes with BSD versions: same names, mostly the same basic use, different options and messages. Chapter 1’s gnubin lines put GNU first on your Mac’s PATH, so the book’s commands work as written. To see which you have, use type -a (Section 7.4) or --version: GNU tools print a version, BSD tools usually reject the option.

A third family on new Ubuntu. From Ubuntu 25.10, and in 26.04 LTS (what WSL installs in late 2026), ls --version prints ls (uutils coreutils) 0.8.0. uutils is a rewrite of GNU’s core tools in the Rust language that aims to accept the same options; Ubuntu keeps GNU’s cp, mv, rm, and df, and grep and sed are still GNU (release notes). The book’s commands work there; a few messages read differently, as noted where they appear. Clusters still run GNU.

It still matters in three places:

  • Scripts from a colleague’s Mac, written for BSD tools (sed -i '', date -v), fail on Linux, and the book’s GNU commands fail on a Mac without the setup. The installed manual page (man sed) is the authority for what a Mac’s own tool does.
  • #!/bin/bash on a Mac means Apple’s bash 3.2, which lacks features from 2009 on that Chapter 8 may use. This book’s #!/usr/bin/env bash avoids it.
  • Minimal containers (Chapter 24) often have a third set, BusyBox, with fewer options still.

(Captured on macOS 15. Some older differences are gone: recent macOS has readlink -f, sort -h, and sort -V.)

Tip--version is a quick test

$'\t' is bash’s way to write a tab; $ in the pattern is the end of the line (Chapter 6). 
2
0

No error, and the CSV gives the wrong answer. cat shows nothing odd:

Terminal (laptop)

cat -A (Chapter 6 used it to show tabs as ^I) marks each line end with $. In the CSV every line ends in ^M$: an invisible carriage return character (\r) before the newline. So the line ends in 30\r, not 30, and ,30$ does not match (Figure 7.7).

The damage sticks to the last field. Fields in the middle are clean; the last one carries the \r:

Terminal (laptop)

2printf '%q\n' "$f"

1
Store the reads field of line 3 in f. $( ) and variables are Chapter 8; copy this as it is.
2
%q prints a value with invisible characters spelled out. 
run_folder$
Run 3 final$
run1$
$'9\r'
different

The value is 9\r, so a comparison with 9 is silently false. When the last column holds file names, the result is a “missing” file that is plainly there. A two-line sheet in scratch shows it:

Terminal (laptop)
cd ~/bioinf-computing-ch07
printf 'sample,fastq_1\r\nWT_REP1,SRR6357070_1.fastq.gz\r\n' > sheet.csv
ls ~/bioinf-computing/data/raw/$(tail -n 1 sheet.csv | cut -d, -f2)
ls: cannot access '/home/you/bioinf-computing/data/raw/SRR6357070_1.fastq.gz'$'\r': No such file or directory

GNU ls spells out the $'\r'; many tools print a name that looks exactly right. And a script saved with CRLF fails on its first line, because the shebang now names a program called bash\r:

Terminal (laptop)
printf '%s\r\n' '#!/usr/bin/env bash' 'echo "hello"' > crlf.sh
chmod u+x crlf.sh
./crlf.sh
/usr/bin/env: ‘bash\r’: No such file or directory
/usr/bin/env: use -[v]S to pass options in shebang lines

(The second line is env guessing at a different problem; ignore it. Older env, such as Nova’s, prints only the first line. Ubuntu 26.04’s env writes it as env: $'bash\r': No such file or directory; on a Mac it is env: bash\r: No such file or directory. With #!/bin/bash instead, bash 5.1 (Nova) and 5.3 say /bin/bash^M: bad interpreter: No such file or directory, with status 126 instead of 127: the ^M is the carriage return. Bash 5.2 says only cannot execute: required file not found, which is even less helpful.)

How to detect it. Look with cat -A (for ^M), and count with grep -c $'\r' file, which prints how many lines contain a carriage return: 7 for the CSV, 0 for the TSV. Do not rely on file: it reports with CRLF line terminators for some text (file crlf.sh does), but once it recognises a CSV it says only CSV ASCII text, with or without carriage returns (Ubuntu’s file 5.45; macOS’s and Nova’s 5.39 say CSV text). On a two-line CSV saved by Excel, file did mention CRLF; on the seven-line sheet it did not, so its answer depends on the file.

Now name it. Linux and macOS end each line with one character, a line feed (LF, \n). Windows ends lines with two, carriage return + line feed (CRLF, \r\n). CRLF is normal in CSV files, and proper CSV readers in R and Python handle it (Chapter 14); what breaks is a shell tool or simple script that keeps the \r as part of the last field. Files get CRLF endings from Windows editors, Excel’s “Save as CSV”, and email attachments. In WSL, files under /mnt/c (Chapter 1’s pitfall) are often edited with Windows programs, which is where the CRLF comes from; the folder itself does not change the bytes. Excel’s CSV UTF-8 format also puts three invisible bytes, a byte order mark, before the first column name: cat -A shows M-oM-;M-?sample,reads^M$, and a shell tool then sees a first column called something other than sample. sed '1s/^\xEF\xBB\xBF//' removes it; R’s and Python’s CSV readers handle it.

Fix it by deleting the \r at each line end. Write a fixed copy first and check it:

Terminal (laptop)
sed 's/\r$//' ~/bioinf-computing-ch05/share/meta/samples_from_excel.csv > samples_lf.csv
grep -c $'\r' samples_lf.csv
echo $?
grep -c ',30$' samples_lf.csv
0
1
2

No carriage returns left, and the count is right. The 1 from echo $? is not a failure: grep exits with 1 when it finds no matching lines, which is what you wanted here (Chapter 8 returns to this). Once you trust the command, GNU sed -i 's/\r$//' file fixes a file in place: on your own copy, never on data/raw/ (Chapter 6). Two other tools you will see: tr -d '\r' < in > out deletes every carriage return, not only those at line ends (fine for a sample sheet), and dos2unix file, where installed, does the same job as sed. Line-ending fixes are for text files only, never for compressed or binary data.

Prevent it where you can. VS Code shows LF or CRLF in the status bar at the bottom of the window; click it to change a file, and set "files.eol": "\n" in your settings to make LF the default (VS Code docs). Git can convert line endings for you (Chapter 21). Before a pipeline run, check sample sheets with grep -c $'\r' (Chapter 26). One more invisible character from Excel, the byte-order mark at the start of a file, is Chapter 36.

WarningPitfall: CRLF from Windows or Excel

Files from Windows or Excel can end lines in CRLF. Shell tools then see a \r stuck to the last field, and matches and comparisons fail silently. Check with cat -A (look for ^M) or grep -c $'\r' before a script reads them.

CautionMisconception: “A CSV file is a CSV file; where it was saved doesn’t matter”

Reality. The program and system that saved it decide its line endings (and whether it starts with an invisible byte-order mark). A \r at each line end sticks to the last field, so matches and comparisons on it fail without an error.

Check yourself. cat -A samples.csv shows ^M$ at every line end. Name one way it got that way and one fix.

TipAnswer

It was saved by Excel or a Windows editor. Fix: sed 's/\r$//' samples.csv > samples_lf.csv, check with grep -c $'\r' samples_lf.csv (prints 0), then use the new file.

7.11 Summary

  • A permission string is a type letter and three triplets (user, group, other) of r, w, x; each triplet is also one octal digit (4 + 2 + 1). On a folder, r lists names, x reaches the entries, and w with x adds or removes them, so deleting a file depends on its folder. chmod changes permissions; read the string and change one letter, never 777.
  • A script runs as a command with a shebang line (#!/usr/bin/env bash) and the x bit. Permission denied (126) means found but not runnable; command not found (127) means not on PATH.
  • Bash checks aliases, functions, and builtins, then searches the PATH folders in order and runs the first match; type -a shows them all. pixi run and module load work by putting a folder first on PATH.
  • export passes a variable to the programs a shell starts; a line in ~/.bashrc sets it for every new terminal. Login shells read the first of ~/.bash_profile, ~/.bash_login, ~/.profile; in the book’s setup that file reads ~/.bashrc. Back up before editing, and keep it silent.
  • A process has a PID and a parent. Ctrl-CCtrl-C and kill ask it to end, kill -9 forces it, Ctrl-ZCtrl-Z only pauses it. df shows how full a disk is, du what is in folders; on a cluster your limit is a quota. GNU and BSD tools share names but not options. Windows line endings leave a \r on the last field: find it with cat -A or grep -c $'\r', remove it with sed 's/\r$//'.

Exercise 1. Make a broken tool run. A labmate’s script, count_lines.sh, prints a file’s name and its number of lines. It arrived from a Windows laptop with a sample sheet. Set up the copy (the printf writes the script with Windows line endings, and chmod 644 makes sure it starts out not executable):

Terminal (laptop)

  1. Run ./bin/count_lines.sh samples.csv. Fix what the message says.
  2. Run the same command again. Fix what the new message says.

Exercise 2. Read and set permissions. In ~/bioinf-computing-ch07/perm2/, make notes.txt, run.sh, and a folder private/. Set them to -rw-r--r--, -rwxr-xr-x, and drwx------: once with symbolic chmod, then again from the start with octal. Check with ls -l and stat -c '%A %a %n'. Then explain, from ls -ld ~/bioinf-computing/data/raw, why rm on a raw file fails.

TipAnswer 
Terminal (laptop)
mkdir -p ~/bioinf-computing-ch07/perm2 && cd ~/bioinf-computing-ch07/perm2
touch notes.txt run.sh && mkdir private
chmod u+x,go+rx run.sh              # from -rw-r--r--: add x for all, r for group and other
chmod go-rx private                 # from drwxr-xr-x
stat -c '%A %a %n' notes.txt run.sh private
chmod 644 notes.txt && chmod 755 run.sh && chmod 700 private
-rw-r--r-- 644 notes.txt
-rwxr-xr-x 755 run.sh
drwx------ 700 private

notes.txt already had 644 from the umask. data/raw is dr-xr-xr-x: nobody has w on the folder, and removing a file changes the folder, so rm is refused even with -f.

Exercise 4. Make a setting permanent. Back up ~/.bashrc with cp -n, then add export EDITOR=nano (and, on a cluster where 1 told you to, the PIXI_CACHE_DIR line) if it is not there yet. Prove it works in a new terminal and, if you have a cluster account, in a new SSH login. Record in NOTEBOOK.md which of ~/.bash_profile, ~/.bash_login, ~/.profile, and ~/.bashrc exist on each machine, and which one reads ~/.bashrc.

TipAnswer 
Terminal (laptop)
cp -n ~/.bashrc ~/.bashrc.bak-ch07
1grep -n 'EDITOR=' ~/.bashrc
grep -qxF 'export EDITOR=nano' ~/.bashrc ||
2  echo 'export EDITOR=nano' >> ~/.bashrc
ls -a ~ | grep -E '^\.(bash|profile)'
grep -n bashrc ~/.bash_profile ~/.bash_login ~/.profile 2>/dev/null
1
Look first. If an active line (not starting with #) already sets EDITOR to something else, change that line in nano rather than adding a second one.
2
-x matches whole lines only, -F treats the text as plain text, not a pattern, and -q prints nothing. The || adds the line only if that exact line is missing, so running it twice does not add it twice. A commented-out # export EDITOR=vim does not count.

A later line wins over an earlier one, so the real check is a new terminal, where echo "$EDITOR" prints nano. On Ubuntu and WSL you will usually find ~/.profile reading ~/.bashrc; on a Mac, ~/.bash_profile from Chapter 1. If the SSH login does not see the setting, the cluster’s login file does not read ~/.bashrc (see the check in Section 7.6).
