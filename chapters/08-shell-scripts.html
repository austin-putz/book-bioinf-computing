8.1 What this chapter does

In Chapters 1 to 7 you typed commands one at a time and pasted the occasional block. A script is those commands saved in a file. Saved, they run the same way every time, they record exactly what was done, and you can share them, keep their history, and, in Chapter 10, hand them to a cluster to run as a job. You have already run one: Chapter 3 asked you to paste src/01_count_reads.sh into your project and run it on trust. By Section 8.9 you will be able to explain every line of it.

Several earlier chapters left loose ends here. Chapter 1’s read count $(( $(gunzip -c … | wc -l) / 4 )) was copied without explanation, and so was its warning that the shell does not stop on errors unless told to. Chapter 4 said that whether a script stops after a failing command “depends on the program and the script”. Chapter 6 promised set -o pipefail and said that grep’s exit status 1 matters “in scripts that stop on any nonzero status”. Chapter 7 gave you the shebang line and the x bit. This chapter ties them together.

It is the longest chapter in Part II, so it comes in two sittings, marked in the text:

  • A. Writing scripts (Section 8.2 to Section 8.6): saving commands in a file, variables and quoting, loops, tests, and arguments. Exercise 1, part A, fits at the end.
  • B. Making them dependable (Section 8.7 to Section 8.12): stopping on errors, logging, reading Chapter 3’s script line by line, chaining scripts into a small pipeline, finding bugs, and saving scripts with git.

Practice happens in a scratch folder, ~/bioinf-computing-ch08. Make it now, with a bin/ folder inside for the exercise scripts:

Most examples in sitting A read the practice folder ~/bioinf-computing-ch05/share/ from Chapter 5: the run folders, the one with spaces in its name, the stray .tmp file, and the two sample tables. Nothing in this chapter changes, renames, or deletes anything there, so later chapters still find it as they expect. Scripts that write files write them in ~/bioinf-computing-ch08. If you do not have the practice folder, paste the setup block from Section 5.2 first.

The project, ~/bioinf-computing, is touched only in sitting B: you read src/01_count_reads.sh, add two scripts beside it, and turn the project into a git repository.

The outputs shown were captured on a Mac (macOS 15, Homebrew bash 5.3.15 with the GNU tools first on PATH, as set up in Chapter 1) and on Ubuntu 24.04 (bash 5.2.21), with GNU gzip. A Mac’s own gunzip words its errors differently (gunzip: can't stat: … where GNU says gzip: …: No such file or directory), and so do other versions; the meaning is the same. Paths start with /home/you on Linux and /Users/you on a Mac.

8.2 From the command line to a script

Start with a command you already know. Chapter 6 counted the feature types in the book’s annotation file with one pipeline:

Terminal (laptop)
gunzip -c ~/bioinf-computing/data/ref/genes.gtf.gz | cut -f3 | sort | uniq -c | sort -k1,1nr
    129 exon
    124 transcript
    118 CDS
    115 start_codon
    114 stop_codon

Typing that again next month means remembering it exactly. Save it instead. Open a new file in VS Code (or nano if you prefer, as in Chapter 2):

Terminal (laptop)
code ~/bioinf-computing-ch08/gtf_types.sh

Paste these lines and save:

~/bioinf-computing-ch08/gtf_types.sh
#!/usr/bin/env bash
# gtf_types.sh: count the feature types (column 3) in the book's GTF file.
# Run:     bash gtf_types.sh   (from ~/bioinf-computing-ch08)
# Input:   ~/bioinf-computing/data/ref/genes.gtf.gz
# Output:  counts on the screen, most common first
gunzip -c ~/bioinf-computing/data/ref/genes.gtf.gz | cut -f3 | sort | uniq -c | sort -k1,1nr

The first line is the shebang from Section 7.3. The lines starting with # are comments: bash skips them, and they are for the next person to read the file, who is usually you. A short header saying what the script does, how to run it, what it reads, and what it writes is worth the four lines in every script you keep.

Run it, first with bash, then as a command of its own:

Terminal (laptop)
cd ~/bioinf-computing-ch08
bash gtf_types.sh
./gtf_types.sh
chmod u+x gtf_types.sh
./gtf_types.sh

bash gtf_types.sh prints the same five lines as before. ./gtf_types.sh then fails with bash: ./gtf_types.sh: Permission denied (exit status 126) until chmod u+x gives the file its x bit, exactly as hello.sh did in Section 7.3. After that, it prints the five lines again.

What a script is. A script is a text file of commands that a new bash process reads and runs from top to bottom. Because it is a new process, it starts fresh: it does not see the aliases you typed or the variables you set without export in your terminal (Table 7.6). It also cannot change your terminal: a cd or a variable set inside the script is gone when the script ends.

Relative paths are read from where you run it. A script does not run “from its own folder”. Every relative path in it is read from the folder you are in when you start it. Chapter 5 left a two-line script for exactly this, ~/bioinf-computing-ch05/where.sh, which runs pwd and then ls data/raw. Run it from your home folder:

Terminal (laptop)
cd ~
bash ~/bioinf-computing-ch05/where.sh
/home/you
ls: cannot access 'data/raw': No such file or directory

The script is stored in ~/bioinf-computing-ch05, but pwd says it runs in ~, and data/raw is looked up there. gtf_types.sh does not have this problem because its one path starts with ~, which is absolute. Project scripts use relative paths on purpose, so a project folder can be moved or copied as a whole. The book’s rule is simple: project scripts live in src/ and are run from the project folder, as pixi run bash src/01_count_reads.sh, and each says so in its header. Section 8.9 adds one line that checks it.

The parts of a script. Longer scripts follow the same order as the header lines above, and Figure 8.1 shows it on Chapter 3’s script: the shebang; a header comment; settings that change how bash behaves; the inputs and checks on them; the work; and the outputs. You will meet each part in this chapter and read that script line by line in Section 8.9.

The script’s paths are relative, so they are read from ~. Its mkdir -p results logs makes those two folders in your home folder, then md5sum cannot find src/01_count_reads.sh and cd data/raw fails with No such file or directory. 8.3 Variables, quoting, and expansions

Go to the practice folder and store a folder name in a variable, then list that folder twice, once without quotes and once with them:

Terminal (laptop)
cd ~/bioinf-computing-ch05/share
d="Run 3 final"
ls $d
ls "$d"
ls: cannot access 'Run': No such file or directory
ls: cannot access '3': No such file or directory
ls: cannot access 'final': No such file or directory
sample_C_R1.fq.gz
sample_C_R2.fq.gz

The first ls exits with status 2 after three errors; the second lists the two files.

What happened. d="Run 3 final" stores the text Run 3 final under the name d (no spaces around =, Section 7.5). When bash meets $d, it replaces it with that value. Without quotes, bash then does two more things to the value, the steps that Figure 5.1 in Chapter 5 set aside:

  1. Word splitting. The value is cut at spaces, tabs, and newlines (the default contents of a setting called IFS) into separate words. Run 3 final becomes three words, so ls received three names.
  2. Wildcard matching. Each piece that holds *, ?, or [ is matched against file names, as if you had typed it (Section 5.8).

Inside double quotes neither happens: "$d" is replaced by its value and stays one word, spaces and all (Figure 8.2). That gives the rule this chapter follows everywhere:

ImportantKey idea

Put double quotes around every $…: write "$d", "$f", "$1". An unquoted value is split at spaces and matched as a wildcard, so a file name with a space becomes several arguments.

Two places do not split, and you will see unquoted variables in them in other people’s scripts: a plain assignment (x=$y copies the value whole) and the inside of [[ … ]] (Section 8.5). Quoting there does no harm, and quoting everywhere is the simpler habit. Single quotes stop all expansion, as in Chapter 5: '$d' is the two characters $d. Use double quotes when you want the value, single quotes when you want the text exactly as typed.

A misspelled variable is empty, not an error. Set a variable and then use it with a typo, through echo so nothing happens:

Terminal (laptop)
outdir=~/bioinf-computing-ch08/out
echo "would delete: $outdri/"
would delete: /

outdri was never set, so bash replaced it with nothing, silently. Inside a real command such as rm -rf "$outdri/", the quotes would faithfully hand rm the one argument /: the wrong path, built by a typo. What rm then does depends on its safeguards and your permissions; the point is that the command was built wrong and nothing warned you. Never run that line. Section 8.7 shows the setting, set -u, that turns an unset variable into an error.

WarningPitfall: a misspelled variable is empty

rm -rf "$outdri/" with outdri unset is handed the argument /. Quotes keep an argument whole, but they do not check that it is the path you meant. Preview any command built from variables by putting echo in front of it, and use set -u in scripts (Section 8.7).

Two naming habits avoid trouble. Use lower-case names for your own variables (d, outdir, sample): upper-case names such as PATH, HOME, and USER belong to the system (Section 7.5), and overwriting PATH inside a script stops it finding any command. And use names that say what the value is: fastq tells the next reader more than x.

8.3.1 The expansions you have already met

Several pieces of syntax from earlier chapters are expansions too, and the quoting rule applies to all of them.

Command substitution, $( ), runs a command and puts its output in its place. Chapter 3’s script names its log with $(date +%Y-%m-%dT%H%M%S), and Chapter 7 stored a field with f=$(…). Quote it like a variable: "$(date +%Y-%m-%d)".

Arithmetic, $(( )), does whole-number arithmetic. Now Chapter 1’s read count can be taken apart. Run the inner part first, then the whole line:

Terminal (laptop)
gunzip -c ~/bioinf-computing/data/raw/SRR6357070_2.fastq.gz | wc -l
echo $(( $(gunzip -c ~/bioinf-computing/data/raw/SRR6357070_2.fastq.gz | wc -l) / 4 ))
200000
50000

The inner $( ) runs the pipeline and becomes 200000, the number of lines; $(( 200000 / 4 )) becomes 50000, one read per four lines. Bash arithmetic is integers only: $(( 7 / 2 )) is 3. Anything with decimals belongs in R or Python (Chapter 12, Chapter 13) or awk (Chapter 6).

Braces, ${name}, mark where a variable’s name ends. Compare:

Terminal (laptop)
sample=WT_REP1
echo "$sample_R1.fastq.gz"
echo "${sample}_R1.fastq.gz"
.fastq.gz
WT_REP1_R1.fastq.gz

In the first line, bash read the longest name it could, sample_R1, which is unset and so empty. Braces end the name where you mean it to: use "${sample}_R1.fastq.gz" whenever a name is followed by a letter, digit, or _.

Trimming a value. Inside braces, #, %, and / cut or replace part of a value without starting another program. On a path from the practice folder:

Terminal (laptop)
f="Run 3 final/sample_C_R1.fq.gz"
echo "${f##*/}"
echo "${f%.gz}"
echo "${f/_R1/_R2}"
basename "$f"
sample_C_R1.fq.gz
Run 3 final/sample_C_R1.fq
Run 3 final/sample_C_R2.fq.gz
sample_C_R1.fq.gz

${f##*/} removes everything up to the last /, which leaves the file name, the same as the basename command. ${f%.gz} removes .gz from the end. ${f/_R1/_R2} replaces the first _R1 with _R2, which Section 8.4 uses to find the partner of each R1 file. Table 8.1 collects these forms.

8.3.2 Lists

Chapter 5 and Chapter 6 built the sample table from a list, rows=(…), and promised an explanation. A list (bash calls it an array) holds several values under one name. Paste the same list again:

Terminal (laptop)
rows=(sample run_folder condition reads
  sample_C "Run 3 final" treated 12
  sample_A run1 control 9
  sample_B run2 control 30
  sample_E run5 treated 105
  sample_B run2 control 30
  sample_D run4 control 8)
echo "${#rows[@]} items"
echo "${rows[5]}"
28 items
Run 3 final

The quotes around "Run 3 final" in the list made it one item, so the list has 28 items, not 30. Items are numbered from 0: ${rows[5]} is the sixth, Run 3 final. "${rows[@]}", in double quotes, gives every item as its own word, spaces kept. The table itself came from one printf:

Terminal (laptop)
printf '%s\t%s\t%s\t%s\n' "${rows[@]}"

printf takes a format and fills each %s with the next item. When it has more items than %s slots, it reuses the format until the items run out: four slots, 28 items, so seven lines of four tab-separated columns. A small case shows the rule:

Terminal (laptop)
printf '%s-%s\n' a b c d e
a-b
c-d
e-

Prefer printf to echo for anything with tabs, backslashes, or a format: printf treats \t and \n the same way everywhere, while echo’s handling of them differs between shells and systems. echo is fine for a plain message.

Check yourself. (a) sample=WT_REP1; echo "$sample_R1.fastq.gz". What prints? (b) f="Run 3 final/a.fq.gz"; ls $f: how many names does ls receive?

TipAnswer
  1. .fastq.gz. Bash read a variable called sample_R1, which is unset, so it became nothing. Write "${sample}_R1.fastq.gz". (b) Three: Run, 3, and final/a.fq.gz, because the unquoted value is split at its spaces. ls "$f" receives one.

8.4 Loops

Count the reads in every R1 file of the practice folder. Here is the version most people write first. It has two bugs; run it and look for them in the output:

Terminal (laptop)
cd ~/bioinf-computing-ch05/share
for f in */*_R1*; do n=$(gunzip -c $f | wc -l); echo "$f $((n/4))"; done
gzip: Run.gz: No such file or directory
gzip: 3.gz: No such file or directory
gzip: final/sample_C_R1.fq.gz: No such file or directory
Run 3 final/sample_C_R1.fq.gz 0
run1/sample_A_R1.fastq.gz 2
run2/sample_B_R1.fastq.gz 3
run2/sample_B_R1.fastq.gz.tmp 3

The exit status is 0. Sample C really has 4 reads, and the last line is the stray temporary copy from Chapter 5, counted as if it were a sample. Neither bug stopped the loop or changed its exit status; the three error lines are the only hint, and in a long run they scroll past. (GNU gunzip tries adding .gz to a name it cannot find, which is why it reports Run.gz; a Mac’s gunzip prints gunzip: can't stat: Run and so on.)

Fix one bug at a time. First quote "$f":

Terminal (laptop)
for f in */*_R1*; do n=$(gunzip -c "$f" | wc -l); echo "$f $((n/4))"; done
Run 3 final/sample_C_R1.fq.gz 4
run1/sample_A_R1.fastq.gz 2
run2/sample_B_R1.fastq.gz 3
run2/sample_B_R1.fastq.gz.tmp 3

Sample C now arrives as one name and gives 4. Then tighten the pattern so it only matches names that end the way FASTQ files end, .fastq.gz or .fq.gz:

Terminal (laptop)
for f in */*_R1.f*q.gz; do n=$(gunzip -c "$f" | wc -l); echo "$f $((n/4))"; done
Run 3 final/sample_C_R1.fq.gz 4
run1/sample_A_R1.fastq.gz 2
run2/sample_B_R1.fastq.gz 3

Three samples, three correct counts. (The lines may come out in a different order on your system: the order of a wildcard’s matches depends on the language settings. On these machines Run 3 final sorted first; on several Linux clusters it sorts last. The counts are what matter.)

What a for loop does. The general form is:

the form of a for loop
for name in list; do
  commands that use "$name"
done

Bash expands the list once, before the loop starts: here the wildcard became the list of matching file names. Then it runs the commands once per item, with f set to each in turn. The one-line version above just puts ; where the line breaks would be. In a script, write it on several lines and indent the body, as in the box.

Loop over a wildcard, never over the output of ls: for f in $(ls) splits the names at their spaces, exactly like an unquoted variable.

Preview first. A loop repeats a command many times, so a mistake is repeated too. Before a loop that changes files, put echo in front of the command and read what it would do:

Terminal (laptop)
for f in */*_R1.f*q.gz; do echo cp "$f" ~/bioinf-computing-ch08/; done
cp Run 3 final/sample_C_R1.fq.gz /home/you/bioinf-computing-ch08/
cp run1/sample_A_R1.fastq.gz /home/you/bioinf-computing-ch08/
cp run2/sample_B_R1.fastq.gz /home/you/bioinf-computing-ch08/

This is Chapter 5’s habit with rm, now for loops. The list is right, so the real loop would copy three files. (echo joins its arguments with spaces, so it cannot show that Run 3 final/… is one argument; the quotes in the loop make sure it is.) When the list looks right, remove echo and run it.

8.4.1 When nothing matches

Try a pattern that matches nothing in the practice folder:

Terminal (laptop)
for f in */*.bam; do echo "got: $f"; done
got: */*.bam

When a wildcard matches nothing, bash passes the pattern unchanged (Section 5.8), so the loop ran once with f set to the literal text */*.bam. The next command would fail with a confusing No such file or directory for a file called */*.bam. Bash can be told to drop a pattern that matches nothing instead:

Terminal (laptop)
shopt -s nullglob
for f in */*.bam; do echo "got: $f"; done
shopt -u nullglob

With nullglob set the loop runs zero times and prints nothing; shopt -u unsets it again in your terminal. In a script that loops over a wildcard, put shopt -s nullglob near the top. But zero passes is not a success either: a script that “processes” no files and exits 0 looks exactly like one that worked. So store the matches in a list and stop if it is empty:

in a script
shopt -s nullglob
files=(*/*_R1.f*q.gz)
if (( ${#files[@]} == 0 )); then echo "no R1 files found" >&2; exit 1; fi
for f in "${files[@]}"; do
  echo "would count $f"
done

These are script lines: typed into a terminal, the exit would close it. if is explained in Section 8.5 and >&2 in Section 8.6; here they read “if the list has zero items, print a message and stop”.

Numbered ranges. Brace ranges from Chapter 5 work as a loop list: for i in {01..03}; do echo "sample_$i"; done prints sample_01, sample_02, sample_03.

8.4.2 Paired files

Paired-end reads come as R1 and R2 files with matching names. From each R1 name, build the R2 name with the replacement from Table 8.1 and check that the file exists (-e, “exists”, is one of the tests in Section 8.5):

Terminal (laptop)
for r1 in */*_R1.f*q.gz; do
  r2="${r1/_R1/_R2}"
  if [[ -e "$r2" ]]; then echo "pair: $r1 + $r2"; else echo "no R2 for $r1"; fi
done
pair: Run 3 final/sample_C_R1.fq.gz + Run 3 final/sample_C_R2.fq.gz
pair: run1/sample_A_R1.fastq.gz + run1/sample_A_R2.fastq.gz
pair: run2/sample_B_R1.fastq.gz + run2/sample_B_R2.fastq.gz

${r1/_R1/_R2} replaces the first _R1 in the whole path. A folder called run_R1_old/ would break it, which is one more reason for Chapter 3’s naming rules: _R1 and _R2 appear only once, just before the file ending.

8.4.3 Rows of a table

A sample table and the files on disk can disagree, as Chapter 6 warned. Check each row of the practice table against the folders:

Terminal (laptop)
1tail -n +2 meta/samples.tsv | while IFS=$'\t' read -r sample folder cond reads; do
  if [[ -d "$folder" ]]; then echo "$sample: folder '$folder' found"
  else echo "$sample: folder '$folder' MISSING"; fi
done
1
tail -n +2 skips the header line; read takes one line at a time from the pipe. 
sample_C: folder 'Run 3 final' found
sample_A: folder 'run1' found
sample_B: folder 'run2' found
sample_E: folder 'run5' MISSING
sample_B: folder 'run2' found
sample_D: folder 'run4' MISSING

Two rows point at folders that do not exist. Three details make this loop work:

  • while … read …; do … done runs once per line of its input, and stops when there are no more lines.
  • IFS=$'\t' sets, for this read only, the characters it splits a line at: tabs only. So Run 3 final arrives whole in folder, spaces and all. ($'\t' is bash’s way to write a tab character.)
  • read -r keeps backslashes as they are, instead of treating them as escapes. Always use -r.

read puts the first field in sample, the second in folder, and so on; the last name gets whatever is left.

The tempting alternative loops over the table’s words:

Terminal (laptop)
for line in $(tail -n +2 meta/samples.tsv | head -n 2); do printf '[%s] ' "$line"; done; echo
[sample_C] [Run] [3] [final] [treated] [12] [sample_A] [run1] [control] [9]

$( ) unquoted is split at spaces, tabs, and newlines alike, so the “lines” arrive one word at a time, and Run 3 final falls apart.

WarningPitfall: loop over files with a wildcard, over lines with while read

for f in $(ls) and for line in $(cat file) split at every space. Loop over files with a wildcard (for f in */*_R1.f*q.gz), and over the lines of a table with while IFS=$'\t' read -r …; do … done.

CautionMisconception: “for line in $(cat file) goes through a file line by line”

Reality. It goes word by word, split at spaces and tabs, and it matches wildcards. Read lines with while IFS= read -r line.

A loop at the end of a pipe forgets. Bash runs each part of a pipe in its own process (a subshell), including a while loop at the end. Variables set inside the loop disappear with that process. It matters as soon as a loop must remember something, such as “did any row fail?”:

Terminal (laptop)
bad=0
tail -n +2 meta/samples.tsv | while IFS=$'\t' read -r sample folder _; do
  if [[ ! -d "$folder" ]]; then bad=1; fi
done
echo "bad after the loop: $bad"
bad after the loop: 0

Two folders are missing, yet bad is still 0: the bad=1 happened in the subshell. A script that ended with exit "$bad" would report success. (_ is the usual name for “a value I don’t need”; here it takes the rest of the line.) The repair feeds the file to the loop with < instead of a pipe, so the loop runs in the script’s own shell. You will use it, ready-made, in exercise 2:

in a script
bad=0
{
  IFS= read -r _   # skip the header line
  while IFS=$'\t' read -r sample folder rest || [[ -n "$sample$folder$rest" ]]; do
    if [[ ! -d "$folder" ]]; then
      printf '%s: missing folder %s\n' "$sample" "$folder" >&2
      bad=1
    fi
  done
} < "$table"
exit "$bad"

The < "$table" after the closing } feeds the file to everything inside the braces. The first read takes the header line; the while loop gets the rest. Because nothing here is a pipe, bad=1 survives the loop and the script can exit with it. The extra || [[ -n "$sample$folder$rest" ]] handles a last line with no newline at its end: read still fills the variables but reports failure, so a plain while read would skip that row without a word. The test says “or the line was not empty”, so the last row is checked too. (When you only need a total, awk from Chapter 6 is simpler than a loop.)

Limits of read. This way of reading a table is for simple, tidy tables like the practice one, where every field is filled in. A tab counts as “white space” to read, so two tabs in a row do not give an empty field. A row with an empty folder field, sample_C<TAB><TAB>control<TAB>12, gives folder=control, cond=12, and an empty reads, silently shifted. && runs the next command only if the one before it succeeded (status 0); || runs the next only if it failed. a && b || c looks like “if a then b else c”, but it is not quite: c also runs when b fails. true && false || echo "c ran anyway" prints c ran anyway. For anything more than a one-liner, use if.

if tests a command’s exit status, and nothing else. The form is:

the form of if
if command; then
  commands to run when it succeeds
elif other_command; then
  commands when the first failed and this one succeeds
else
  commands when all of them failed
fi

elif and else are optional. Any command can follow if:

Terminal (laptop)
if grep -q sample_D meta/samples.tsv; then echo "sample_D is in the table"; else echo "no sample_D"; fi
sample_D is in the table

Tests with [[ … ]]. Most ifs ask a question about a file, a string, or a number. [[ … ]] is a command that does nothing except answer such a question with its exit status:

and is not empty
no folder run5

The spaces inside [[ and ]] are required: [[-f "$f"]] is an error. Table 8.3 lists the tests you will use most.

The trap in the table. Inside [[ ]], < and > compare text, in dictionary order, not numbers:

Terminal (laptop)

[[ 9 -lt 30 ]]; echo "status $?"
status 1
status 0
status 0

As text, 9 comes after 3, so [[ 9 < 30 ]] is false, the same mistake as sort without -n in Chapter 6. For numbers, use (( )) or the letter tests (-lt, -gt, …).

You will also meet the older single-bracket test, [ … ] (for example [ 9 -lt 30 ], also true). It works in every shell, not only bash, but every variable inside it must be quoted, and it lacks some features. This book uses [[ ]] in bash scripts.

case, for matching patterns. When one value can match several patterns, case is tidier than a chain of elifs. You will see it in other people’s scripts; recognising it is enough here:

Terminal (laptop)
f="Run 3 final/sample_C_R1.fq.gz"

  *.fq.gz|*.fastq.gz) echo "FASTQ: $f" ;;
  *)                  echo "skip: $f" ;;
esac
FASTQ: Run 3 final/sample_C_R1.fq.gz

Each pattern ends in ), | means “or”, ;; ends a branch, and *) catches everything else.

A script’s own exit status. A script exits with the status of the last command it ran, unless it calls exit first. exit 0 reports success; any other number, usually exit 1, reports failure. The next program, or you with echo $?, can then tell whether it worked. Scripts that stop early on a problem use exactly this, as the next section shows.

big. Inside [[ ]], < compares text, and 9 sorts after 1. if (( n < 10 )) or if [[ "$n" -lt 10 ]] prints small. The unquoted $n is not the problem: [[ ]] does not split its contents (Section 8.3).

8.7 Stopping on errors: set -euo pipefail

In Chapter 1, a pitfall said that the shell does not stop on errors unless told to. Here is what that means inside a script. Make a five-line script, count.sh: open it with code count.sh (or nano count.sh), paste, and save.

count.sh

# count.sh: count the reads in one gzipped FASTQ file.
n=$(gunzip -c "$1" | wc -l)
echo "$1: $(( n / 4 )) reads"

# count.sh: count the reads in one gzipped FASTQ file.

Now name each letter. set changes how bash behaves for the rest of the script. The three settings are independent, and each has its own demonstration (all are small scripts you can make the same way as count.sh).

  • -e: stop when a command fails. A command “fails” when its exit status is not 0 (Chapter 4). By default bash just moves on to the next line, which is Chapter 1’s pitfall.

  • -u: an unset variable is an error, not an empty value. This is Section 8.3’s misspelled $outdri, which silently became empty and turned "$outdri/" into /. With set -u:

    typo.sh
    #!/usr/bin/env bash
set -u
outdir=~/bioinf-computing-ch08/out
echo "would delete: $outdri/"
    ./typo.sh: line 4: outdri: unbound variable

    The script stops (exit status 1) and names the misspelled variable.

  • -o pipefail: a pipeline fails if any command in it fails. Without it, a pipeline’s exit status is that of its last command. In gunzip -c missing.gz | wc -l, gunzip fails but wc succeeds, so the whole line “succeeds”, and -e alone has nothing to stop on:

    pipe.sh
    #!/usr/bin/env bash
set -e
lines=$(gunzip -c missing.gz | wc -l)
echo "lines=$lines"
echo "still running"
    gzip: missing.gz: No such file or directory
lines=0
still running

    Exit status 0. Change the second line to set -eo pipefail and the script stops after the gzip error, with exit status 1. This is the pipefail that Chapter 6 promised. To see each command’s status yourself, bash keeps them in a list, PIPESTATUS, right after a pipeline: gunzip -c missing.gz | wc -l; echo "${PIPESTATUS[@]}" prints the count (0) and then 1 0, one status per command.

Then what it does not catch. Strict mode is the book’s rule for every script, but it reacts only to exit statuses, and only in some places. Five things to know, each captured from a real run:

1. A “failure” that is not one. grep exits with 1 when it finds no match (Chapter 6). In a strict script, that stops everything, silently:

grep1.sh
#!/usr/bin/env bash
set -euo pipefail
n=$(grep -c ZZZ names.txt)
echo "n=$n"

With a names.txt that does not contain ZZZ, this prints nothing and exits with 1. The tempting fix is n=$(grep -c ZZZ names.txt || true): “if it fails, succeed anyway”. It does print n=0. But grep has a second failure status, 2, for a real error such as a missing or unreadable file, and || true swallows that too. With a misspelled file name:

grep: missing.txt: No such file or directory
n=

Exit status 0, and n is empty. The script carries on with no number, which is exactly what strict mode was meant to prevent. Keep the two statuses apart instead:

grep2.sh
#!/usr/bin/env bash
set -euo pipefail
file=names.txt
1if n=$(grep -c ZZZ "$file"); then
2  :
else
3  status=$?
4  [[ "$status" -eq 1 ]] || exit "$status"
fi
echo "n=$n"
1
A command inside an if does not trigger -e; the if looks at its status instead.
2
: is a command that does nothing and succeeds: here, “a match was found, carry on”.
3
$? is grep’s status; save it before running anything else.
4
Status 1 (no match) is fine; anything else (2, an error) ends the script with that status.

With names.txt it prints n=0 and exits 0. With file=missing.txt it prints grep’s error and exits with 2. When you only need a yes or no, if grep -q ZZZ "$file"; then … is enough, but it treats a missing file as “no”, so check that the file is readable first ([[ -r "$file" ]], Section 8.5).

2. head closing a pipe early. In a strict script, try the Chapter 1 idiom for a first look at a file, on the project’s real reads:

peek.sh
#!/usr/bin/env bash
set -euo pipefail
gunzip -c data/raw/SRR6357070_1.fastq.gz | head -n 1
echo "reached"

It prints the first header line and then stops, without reached, with exit status 141: in all six runs captured on Linux for this book. head read its one line and exited; gunzip, still writing, was stopped by the system (Chapter 6’s 141); and pipefail reported that as a failure. seq 1 1000000 | head -n 1 does the same. On a tiny input, such as the practice folder’s two-read file, the same lines print reached and exit 0, because gunzip finished before head exited. It is a matter of timing, not a guarantee either way, so a script tested on toy data can fail on real data. Keep | head for looking at files in the terminal, not inside strict scripts. (… | head -n 1 || true would also hide a real decompression error, so it is not the fix.)

3. Commands that are being tested. Commands tested by if and while never trigger -e: their status is the test. That includes everything inside a function called from an if:

func.sh
#!/usr/bin/env bash
set -euo pipefail
f() { false; echo "after false in f"; }
if f; then echo ok; fi
after false in f
ok

In a chain with && or ||, only the commands before the last are exempt. false && echo skipped does not stop a strict script (the false is being tested); true && false does, with exit status 1 (the last false is not tested by anything).

4. Masked statuses. local x=$(false) inside a function, and export x=$(false), succeed: the status that -e sees is that of local or export, which worked, not that of the command inside. Declare and assign on separate lines (local x, then x=$(…)), and the failure stops the script again.

5. Tools that report success despite a problem. This is Chapter 4’s finding, now inside a strict script. Give Chapter 3’s script a truncated read file, with a checksum list made after the truncation (the mistake of making checksums from a damaged copy):

checking inputs against data/raw/checksums.md5:
SRR6357070_1.fastq.gz: OK
SRR6357070_2.fastq.gz: OK
command:  seqkit stats -T data/raw/*.fastq.gz
[ERRO] data/raw/SRR6357070_2.fastq.gz: unexpected EOF
[ERRO]
output:   db1d8098fba21ca3be9934a6cc0dde37  results/read_counts.tsv
finished: 2026-11-22 15:45:39 -0600

seqkit 2.14.0 prints [ERRO] but exits 0, so strict mode sees nothing wrong. The script finishes with exit status 0, and results/read_counts.tsv holds only the header line. In the same way, a gzip file that is valid but holds no reads gives 0 reads and passes both strict mode and gzip -t.

Strict mode only sees exit statuses. The remedy is to check what you expect: a results file with more than a header line, a read count above zero (or equal to the expected one), gzip -t before counting (it catches a damaged stream, not a valid but empty one), and md5sum -c against checksums made from the source (Chapter 3). Section 8.9 adds the first of these to Chapter 3’s script. Table 8.6 sums up the section.

ImportantKey idea

set -euo pipefail stops a script when a command reports failure. It cannot see a wrong result from a command that reports success, so check the outputs too. Every script in this book starts with it: a seatbelt, not a guarantee.

CautionMisconception: “With set -euo pipefail my script stops on every error”

Reality. It stops on a nonzero exit status, except in conditions, functions called from conditions, all but the last command of an &&/|| chain, and masked assignments such as local x=$(…). Now name it. Results go to stdout; messages (progress, warnings, errors, the usage line) go to stderr, in every script you write. Then > results.tsv captures only results, and the messages still reach your screen or a log.

A message to stderr is echo "…" >&2. For a script with several messages, define two short functions once, near the top. A function is a named group of commands (Chapter 7); this is the book’s first use of one:

part of a script
log() { printf '[%s] %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2; }
die() { log "ERROR: $*"; exit 1; }

log "counting reads" prints [2026-11-22 14:26:50] counting reads to stderr; die "missing input" logs ERROR: missing input and ends the script with status 1. Inside a function, $* is all its arguments joined into one string: the one place this book joins arguments on purpose. A function must be defined before the line that uses it. Writing your own reusable functions is Chapter 34.

Keeping a log of a whole run. Chapter 3’s script keeps everything it prints in a log file, with this form:

part of a script
log="$(mktemp "logs/01_count_reads_$(date +%Y-%m-%dT%H%M%S)_XXXX.log")"
{
  …the commands…
} 2>&1 | tee "$log"

The { … } group collects the output of all its commands; 2>&1 joins stderr to stdout; tee shows that stream on the screen and writes it to the log. The log name holds the date and time in the ISO form of Chapter 3, and mktemp replaces XXXX with random characters and creates the file, so two runs in the same second never share a log. (This needs GNU mktemp, which fills in X’s that come before a suffix such as .log. The Mac’s own /usr/bin/mktemp only replaces X’s at the very end, so without Chapter 1’s GNU tools the log is literally named …_XXXX.log every run.) Section 8.9 takes this form apart line by line.

Write to a temporary name, then mv. Chapter 6 showed that > empties a file before the command starts, so a failed command can leave a half-written result under the real name. Scripts in this book write each output to name.tmp and move it into place only when the step has succeeded:

part of a script
seqkit stats --quiet -T data/raw/*.fastq.gz > results/read_counts.tsv.tmp
mv results/read_counts.tsv.tmp results/read_counts.tsv

With set -e, a failure stops the script before mv, so a new result is published only after the step succeeds, and a good result from an earlier run is never replaced by a partial one. What this does not do: after a failed rerun, the earlier run’s finished file is still there, and the half-written .tmp may be there too. So the rule is: publish a new result only after the step succeeds; on failure, an older result may still exist, so use the run’s exit status and log to decide whether a result belongs to this run. Section 8.10 shows this on a real rerun. One assumption is built in: a fixed name.tmp is fine while one run at a time writes that output, as in this book’s pipeline. Two runs at once would share the .tmp (unique log names do not help with that), which needs unique temporary names and more care than this chapter covers.

Now name it. A numbered pipeline is a set of scripts with three habits (Figure 8.4):

  • Each step reads only raw inputs or earlier steps’ results, and writes only its own outputs.
  • Each step can be rerun safely: it overwrites its own result, never an input (assuming one run at a time).
  • The number is the order; the name says what the step does (Chapter 3’s naming rule).

run_all.sh lists the steps by name, not with a pattern such as for s in src/[0-9]*.sh, so a stray 03_old_try.sh never runs by accident. The pattern version is shorter, and some people prefer it; listing by name means you must add each new step to run_all.sh yourself.

Its limits are why Part VI exists. A numbered pipeline reruns every step even when nothing changed; runs one step at a time, even when two steps could run side by side; cannot resume after a failure from where it stopped; and does not know which result came from which version of its inputs. Workflow managers (Chapter 25) solve these, as does the older make (see the GNU make manual); nf-core (Chapter 26) is the one you will use. Running each step as a cluster job is Chapter 10.

8.13 Summary

  • A script is commands saved in a file and run, top to bottom, by a new bash process. Start it with #!/usr/bin/env bash and a header comment that says what it does, how to run it, and what it reads and writes. Relative paths are read from where it is run, so project scripts are run from the project folder.
  • $name is replaced by its value; unquoted, that value is split at spaces and matched as a wildcard. Put double quotes around every expansion: "$f", "$@", "${sample}_R1.fastq.gz". $( ) captures a command’s output and $(( )) does whole-number arithmetic.
  • Loop over a glob, never over ls or $(cat file); read table rows with while IFS=$'\t' read -r. Preview a loop with echo before it changes anything, and check that a list of files is not empty.
  • if tests an exit status; [[ ]] tests files, text, and numbers (< compares text, -lt and (( )) compare numbers). Take file names as arguments with "$@", and stop with a usage message (exit 2) when they are missing. set -euo pipefail stops on a reported failure, an unset variable, or a failed pipe stage; it cannot see a tool that reports success on bad input, so check results too.
  • Send results to stdout and messages to stderr, and keep a log of each run. Write each output to name.tmp and mv it into place only after the step succeeds. Numbered scripts run in order by run_all.sh make a small pipeline. Commit each script once it works, look with git status and git diff, and bring back an old version with git restore.

A template to start every script from. Delete the lines you do not need; keep set -euo pipefail.

template.sh
#!/usr/bin/env bash
# NAME.sh: what this script does, in one line.
# Run:    bash NAME.sh FILE [MORE ...]   (from the project folder)
# Input:  what it reads
# Output: what it writes (results on stdout or in results/, messages on stderr)
set -euo pipefail
shopt -s nullglob     # only if the script loops over a glob

log() { printf '[%s] %s\n' "$(date '+%Y-%m-%d %H:%M:%S')" "$*" >&2; }
die() { log "ERROR: $*"; exit 1; }

if [[ $# -lt 1 ]]; then
  echo "usage: NAME.sh FILE [MORE ...]" >&2
  exit 2
fi

out="results/NAME.tsv"
mkdir -p results
log "start"
for f in "$@"; do
  [[ -s "$f" ]] || die "missing or empty: $f"
  printf '%s\t%s\n' "$(basename "$f")" "something about $f"
done > "$out.tmp"
mv "$out.tmp" "$out"
log "wrote $out"
